## 1. 인기 가게가 이 서비스에서 "부족한 가게"로 나오는 문제

### 1-1. 문제
네이버에서 상위 노출·인기(리뷰·블로그 많음)인 가게가 AEOlab 결과 화면에서 낮은 단계("시작 전", 0점, "찾지 못했다")로 나오면 사용자가 서비스를 신뢰하지 않는다("미끼 상품" 인상). 실사례: 어니언 성수(2026-10-26 07:23 스캔이 `PLAYWRIGHT_QUEUE_TIMEOUT`으로 네이버 측정 실패 — 저장값 통합 9.4·Track1 34.6, 현재 코드로 재계산하면 근사 32.5·48.8이며 저장값은 소급되지 않음), 하라식당(저장 49.0인데 공개 공유 경로가 0점·D등급으로 보임), 홍뮤직스튜디오(별점 없음 → 리뷰 품질 11.2), 대호흑돼지(20).

- **남음**: ① 평균 별점 공개 ON/OFF에서 크롤러가 평균을 못 읽을 때 "확인 불가"로 처리하는지 코드 점검(0 저장·점수화 금지) ② 이름 변형 산식(보류) ③ 성장 단계 알림 경계 히스테리시스 ④ 알림톡 시험 발송 ⑤ 배지 SVG 등급 문자(`ab0d2f1`에서 제거했으나 정책 확정은 사용자) ⑥ `/badge`·`BusinessManager`(설정)에는 별점 안내 없음 ⑦ `docs/popular_shop_trust_improvement_handoff_v1.0.md`의 "남은 약점 8개" 재대조.
- **검증 방법(필수)**: 화면·점수·알림을 고친 뒤 유명 가게(어니언 성수·하라식당)로 실제 결과 화면을 끝까지 눌러 대조하고, 저장된 과거 값 vs 현재 코드 재계산을 비교(저장값은 옛 코드 결과일 수 있고 소급되지 않는다).

## 3. 사용자가 증가하면 (용량 판단)

### 3-1. 결론
- **수용량은 서버 사양이 아니라 네이버 차단 위험이 정한다.** 서버는 Playwright 동시 1개(4GB)지만 하루 수천 페이지는 처리 가능 — 600/일은 네이버를 의식한 숫자. 서버를 올려도 같은 IP 총량은 그대로.
- **현실 한계: 활성 사업장 약 35~50곳**(모델, 70% 알림=35곳, 판매 한도 기본 `NAVER_CAPACITY_BUSINESSES=50`). 대시보드 동시 접속 약 30명(2026-08-23 측정, 병목=Supabase, 이후 개선했으나 재측정 안 함).
- 100곳은 결정 없이 정기 잡 몫(420)에 안 들어오고, **300곳은 모든 절감책+제품 결정 4가지(E~H)가 있어야 겨우 들어온다.**

### 3-2. 절감책 누적 효과 (정기 잡 하루 최대 / 몫 420) — `python scripts/naver_load_model.py --levers 300`
| 단계 | 300곳 | 100곳 | 구분 |
|---|---|---|---|
| A 슬롯 분산 | 1,817 (433%) | 705 (168%) | 결정(요일 표기는 제거됨, 켜기만 남음) |
| B + AI탭 질의 2 | 1,587 (378%) | 613 (146%) | 약속 영향 없음(문구 전수 미확인) |
| C + 사전 스캔 재사용 | 1,336 (318%) | 515 (123%) | **구현됨·외부 조건부**(GitHub 워크플로 용량) |
| D + 경쟁사 겹침 30% | 1,212 (289%) | 453 (108%) | 미실측 가정 |
| E + 키워드 3·경쟁사 2 | 961 (229%) | 359 (85%) | 결정: 플랜 한도 축소 |
| F + 순위 모바일만 | 730 (174%) | 290 (69%) | 결정: 점수 항목 영향 |
| G + AI탭 끔 | 508 (121%) | 198 (47%) | 결정: 기능 축소 |
| H + 경쟁사 4주 갱신 | 405 (96%) | 149 (36%) | 결정: 공개 문구 변경 |
| I + 경쟁사 겹침 60% | 362 (86%) | 136 (32%) | 미실측 가정 |

- '전체'(수동 스캔 포함)는 I에서도 722로 상한 600 초과. 수동 스캔은 **가정치(곳당 하루 0.2회, 근거 없음)** 이고 줄이는 방법이 모델에 없다 — 가장 큰 미지수.
- 구성(분산 후): 스캔 38%·키워드 순위 33%·경쟁사 크롤 24%·내 가게 통계 5%.

### 3-3. 단계별 대응 (코드 `backend/services/naver_capacity.py` PLAYBOOK = 용량 알림 메일 + `/admin/naver-access` `capacity.next_steps`)
| 시점 | 할 일 | 결정권 |
|---|---|---|
| ~35곳 | 조치 없음, 이력·계측 수집 | — |
| 35곳(70% 알림) | AI탭 질의 4→2(.env 한 줄), 슬롯 분산 켜기 | 질의: 운영자 / 분산: **사용자** |
| 45곳(90%) | `/admin/naver-access` 실측으로 모델 가정 교체, 사전 스캔 워크플로 90분 확인 | 운영자 |
| 50곳(100%) | 신규 가입 대기자 전환 여부 | **사용자** |
| 100곳+ | 위 표 D~H 중 필요한 만큼 | **사용자** |
| 300곳 | 위 전부 + 접속 경로 분산 검토 | **사용자 + 변호사 자문** |

### 3-4. 권고(제안): 목표를 두 단계로
1단계 100곳, 300곳은 구조를 바꾼 뒤의 2단계. 이유: 구독자 20명(BEP)도 전에 300곳용으로 제품 범위를 줄이는 것은 이르고, 실측 없이 줄이면 핵심 가치(네이버 노출 진단)가 약해진다. 구독자 없을 때 약속(요일)을 미리 풀어 두는 것이 가장 싸다 — **요일 표기는 이미 제거함.**

### 3-5. 보류한 설계 (구현 전 사용자 결정/데이터 필요)
- `/stream` 경로 사전 스캔/최근 결과 재사용: ① 사전 스캔 대체(점수 입력 변경 위험, 새벽 값을 방금 측정처럼 보임) ② 같은 형태의 최근(예: 6시간) 결과 재사용(첫 클릭은 절감 없음) ③ 계측 후 판단 — **권고는 ③**(수동 스캔 비중을 먼저 본다).
- 새로고침 전역 예약분: 일일 사용량이 `상한−예약분`(예: 150페이지, 제안값)을 넘으면 새로고침만 먼저 거절 — 35곳 이후 여유가 하루 30회 아래로 줄 때 필요(§3 계산: 3곳 94회, 20곳 59회, 35곳 30회, 50곳 4회/일).
- 수동 새로고침 10분 한도는 3회(제안값). 사용자가 1회/2회/3회 중 선택을 보류 중(2회 권고: 경쟁사 5곳 전체 30분).

- 서버가 진실: 편집 전 로컬/서버 md5 확인(로컬 CRLF·서버 LF라 `tr -d '\r'`), 커밋된 버전(HEAD)과 서버 대조 → 로컬 편집 → scp(LF 변환) → 서버 pytest → `pm2 restart` → 라이브 검증 → git 커밋(**push는 사용자가 지시할 때만**). 프론트는 서버 `npx tsc --noEmit` + `npm run build` 후 `pm2 restart aeolab-frontend`. 커밋 끝에 `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- **서버에서 네이버 점검 함수를 연속 호출 금지**(10-27 IP 차단). 화면 구조 확인은 로컬 Playwright 1페이지, 서버는 공식 API·DB 읽기 전용만. 새로고침 버튼·수동 스캔은 서버가 네이버에 접속하므로 라이브 확인 시 누르지 않는다.
- 새 네이버 접속은 **함수 단위**로 회로·쿼터·속도 확인, 정기 잡은 `@naver_batch_job`, **새 접속량은 `scripts/naver_load_model.py`에 반영**.
- 측정 못 한 것은 0점이 아니라 "확인 전", 점수 숫자·등급 문자 화면 직접 노출 금지, 더미 수치 금지, 프록시·기능 축소·IP 분산은 사용자 결정 없이 실행 금지.
- **테스트는 변이 검증**(수정을 빼면 실패하는지), 픽스처는 실제 외부 응답으로, 구조 감사 테스트가 새 경로를 막는지. 이번에 발견한 약한 테스트: 규칙을 테스트 안에 복사해 검증하던 것(실제 함수를 검증하게 교체함).
- **문서·표의 숫자도 반증한다**: 이번 대화에서 "사전 스캔 재사용 미구현"이라 적었다가 실제로는 야간 스캔에 이미 구현돼 있어 정정했고, 한도 이력이 있다고 전제했다가 서버에 0행임을 발견했다. 단정 전에 서버 DB/로그를 읽기 전용으로 확인.
- 보고 끝에 "오판/오탐/누락 재확인" 1~3줄, 확인 못한 것은 "미확인".
- 로그인 정보·비밀번호는 문서·메모리·커밋에 쓰지 않는다(`.playwright-mcp/` 스냅샷은 gitignore되지만 평문이 남을 수 있음).

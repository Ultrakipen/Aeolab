# 네이버 플레이스 접속 보호 — 사고 정리와 구현 (2026-10-27)

## 1. 사고
- 2026-10-27 19:03:01 KST, 서버 IP(115.68.231.57, 프록시 없이 직접 접속)에서 플레이스 페이지가 `과도한 접근 요청으로 서비스 이용이 제한되었습니다` 화면을 반환.
- 화면에 찍힌 19:03:01은 **내가 그 화면을 받은 요청의 시각**이다. 시작 시각은 그 직전(홍스튜디오 성공 → 어니언부터 차단 화면, 분 단위 추정이며 기록 없음).
- 검색 화면(AI 브리핑·AI탭)이 같이 막혔는지는 **확인하지 못했다**.

## 2. 원인 분석과 정정 (오판 기록)
- 가장 유력한 원인: 소식 판정 수정 검증 중 서버에서 점검 함수·Playwright를 연속 호출(약 65~70페이지, 한 번에 27페이지가 1~2분 안에)해 **운영 보호장치(공유 세마포어, 무작위 대기, 상한)를 우회**한 것. 네이버 임계값은 비공개라 확정 불가.
- **정정 1**: "정기 스캔에 의도적 지연이 없다"는 틀렸다. 브리핑 스캐너 2.8~4.8초, AI탭 스캐너 1.2~4.5초 무작위 대기, 사업장당 AI탭 스캔 전 **20~240초 무작위 시작 대기**와 질의 사이 3~8초가 있다. 지연이 약한 곳은 **플레이스 탭 점검(고정 대기)과 경쟁사 크롤러**였다.
- **정정 2**: "제 검증 ≈ 정기 운영의 하루 전체 요청량(66~90건)"은 근거 없는 비교였다. 그 수치는 테스트 데이터 기반 추정이고 플레이스 탭 접속을 세지 않은 값이다. 결론은 총량이 아니라 **밀도**.
- **정정 3**: "플레이스 접속이 일일 상한에서 빠져 있다"는 틀렸다(별칭 `_check_naver_quota`를 grep이 놓침). 플레이스·검색 Playwright 진입점은 모두 상한을 거친다. 진짜 약점은 **함수 호출 1번을 1건으로 세는 것**(한 번에 2~5페이지)이었다.
- **정정 5 (대응 방안 답변 검토에서)**: "순위 측정은 이미 공식 API로 전환했다"는 **부분적으로만 맞다**. `place_rank`만 공식 API이고 `pc_rank`·`mobile_rank`는 키워드마다 Playwright로 검색 화면을 연다(`naver_keyword_rank.py`, 상한 출처 `naver_keyword_rank.pc/mobile`). 순위 측정이 남은 Playwright 트래픽의 큰 몫일 수 있다(실측 아님).
- **정정 6**: "점검이 스캔마다 반복된다"는 과장. `check_smart_place_completeness`는 사용자가 직접 실행하는 풀스캔(`scan.py:3150`)·스캔 후 백그라운드(`scan.py:2674`)·점검 화면·일부 잡에서만 호출되고, **정기 스캔(`daily_scan_all`)은 호출하지 않는다**(grep 기준). 재사용(TTL) 효과는 사용자 수동 스캔 빈도에 달려 있어 처음 말한 것보다 작다.
- **정정 7 (내가 구현한 값의 오류)**: 경쟁사 크롤 가중치를 5로 잡았으나 `_run_place_crawl`의 goto가 최대 **12회**(탭마다 홈 복귀 포함)라 과소였다 → **10**으로 수정·배포. 경쟁사 크롤은 화·목 새벽 주 2회 정기 잡 + 경쟁사 수만큼 반복되어 **플레이스 도메인 트래픽의 가장 큰 항목일 가능성**이 높다(코드 기준 추정, 실측 아님).
- **정정 4**: "IP 변경이 법적으로 가장 민감한 부분"은 과장. 법적 문서는 로그인 세션 위조 + 자동화 신호 은닉 + IP 로테이션의 **결합**을 쟁점으로 본다.

## 3. 구현 (배포 완료)
1. **회로 차단기** `services/naver_access_guard.py`: 차단 화면 감지 시 플레이스 접속을 자동 중단(3h → 6h → 12h → 24h 상한). 쿨다운 후 **시험 접속 1회**만 허용하고 성공하면 닫음, 또 차단이면 두 배로. 상태는 파일(`backend/.naver_place_breaker.json`)에 저장해 재시작·배포로 초기화되지 않음. 열릴 때 운영자 이메일 알림. 쿨다운 단계는 제안값(실측 근거 없음).
2. **상한을 페이지 수로**: `check_naver_playwright_quota(source, cost)` — 점검 5, 통계 2, 체험 점검 4, 경쟁사 10(처음 5 → 코드 goto 수를 세어 수정). 기본 상한을 250→**600**으로 상향(같은 여유 유지, 근거 없는 제안값 — 운영 사용량을 보고 조정). 환경변수 `NAVER_PLAYWRIGHT_DAILY_CAP`로 재정의 가능.
3. **무작위 대기**: 플레이스 점검 함수 호출 시작 전 0.8~2.5초, 탭 대기에 0~1.5초 추가(렌더 대기는 줄이지 않음).
4. **적용 함수 5곳**: `check_smart_place_completeness`, `fetch_stats`, `auto_check_smart_place`, `fetch_competitor_place_data`, `fetch_competitor_faq_items`. 차단 중에는 **네이버 요청 없이** 즉시 `naver_place_cooldown` 오류, 상한 소모 없음(테스트로 검증).
5. `fetch_stats`에 차단 화면 감지 추가(이전엔 차단 화면을 정상 내용으로 읽음). 차단 보고 지점 7곳.
6. 사용자 점검 화면: 차단·상한 오류를 "URL을 확인해주세요" 대신 "잠시 후 다시 시도해 주세요"(503)로, 내부 오류 코드 비노출.
7. **서버 상태 시드**: 차단 여부를 모르므로 배포 시 3시간 쿨다운을 심어 보수적으로 시작(20:xx 기준, 첫 접속이 시험 접속).

## 속도 기준(사전 예방) — 2026-10-27 추가

회로 차단기는 차단을 당한 뒤 멈추는 장치였다. 차단을 당하기 전에 속도를 제한하는 기준을 `services/naver_access_guard.py`에 추가했다.

| 윈도우 | 기본 최대 페이지 | 평균 | 환경변수 |
|---|---|---|---|
| 1분 | 12 | 12/분 | `NAVER_RATE_PER_MIN` |
| 10분 | 30 | 3/분 | `NAVER_RATE_PER_10MIN` |
| 1시간 | 120 | 2/분 | `NAVER_RATE_PER_HOUR` |

- **근거의 한계**: 네이버는 임계값을 공개하지 않는다. 확인된 사실은 "2026-10-27 서버에서 플레이스 약 65~70페이지를 수 분 안에 연속 요청했을 때 차단 화면"뿐이다. 위 값은 그보다 훨씬 느리게 잡은 **보수적 제안값이며 안전선으로 검증되지 않았다**.
- **동작**: 5개 플레이스 접속 함수가 접속 직전(Playwright 세마포어 전)에 `reserve_place_pages(cost)`로 빈 자리가 나는 시각을 예약하고 기다린다. 기다릴 시간이 사용자 요청은 15초, 정기 잡은 30분을 넘으면 `naver_rate_limited`로 거절(네이버 요청 없음). 정기 잡은 이 오류에서 조기 종료한다.
- **검색 화면 접속**(브리핑·AI탭·순위)은 대기 없이 기록만 해 플레이스 허용량에서 차감된다(같은 IP 총량 기준). 검색 화면 자체는 이 제한기가 늦추지 않는다.
- **자동 조임**: 차단을 감지하거나 회복을 확인하면 48시간 동안 한도를 절반으로 한다.
- 기록은 `backend/.naver_rate_window.json`에 저장되어 재시작 후에도 이어진다. 상태는 `GET /admin/naver-access`의 `rate`로 본다.
- 부작용: 경쟁사 크롤(cost 10)은 사업장당 3곳이면 약 10분이 걸린다. 사업장이 늘면 정기 잡이 길어지고 30분 이상 밀리는 요청은 그날 건너뛴다 — 운영 사용량으로 보정할 것.

## 검색 화면 차단 회로 — 2026-10-27 추가

- 대상: search.naver.com 접속(AI 브리핑·AI탭·PC/모바일 순위). 플레이스 회로와 **별개**다 — 플레이스 차단이 검색 화면에도 같이 적용되는지는 확인되지 않았다(미확인).
- 감지: 브리핑 스캐너는 기존 CAPTCHA 감지에 연결. **키워드 순위는 기존에 차단 감지가 전혀 없었다** — 차단·CAPTCHA 화면은 가게 카드가 0개라 "미노출(0점)"로 저장될 수 있었다(코드 근거: `_place_card_rank`에 감지 없음, 점수는 error 없는 전부-None 행을 0점으로 평균). 이제 카드가 없을 때만 현재 화면(URL·제목·본문 앞부분)을 읽어 차단이면 `NaverSearchBlocked` → 해당 키워드는 `error: naver_search_blocked`(측정 불가, 점수 평균에서 제외).
- 쿨다운: 60분 → 180분 → 360분 → 24시간(제안값). 쿨다운 중 브리핑·AI탭·순위는 네이버 요청 없이 측정 불가로 반환(`naver_search_cooldown`). 정상 화면을 읽으면 단계 초기화 + 속도 기준 48시간 절반.
- 상태 파일 `backend/.naver_search_breaker.json`, 관리자 `GET /admin/naver-access`의 `search_breaker`.
- **한계**: 실제 차단 화면의 모양은 확인하지 못했다(감지 문구는 기존 브리핑 스캐너의 것과 플레이스 차단 문구 재사용). 실제 검색 차단이 다른 모양이면 감지하지 못한다. AI탭의 "잘못된 접근" 응답은 프록시/접근 방식 문제와 구분되지 않아 회로에 연결하지 않았다. 플레이스 ID 확정에는 아직 회로가 없다.

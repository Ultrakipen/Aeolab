# 인기 가게 체험 결과 화면 점검 — 어니언 성수 (2026-10-28)

> 핸드오프 `popular_shop_trust_improvement_handoff_v1.0.md` §4 P1(유명 가게 시나리오 검증)의 첫 사례.
> 방법: 라이브(`https://aeolab.co.kr`)에서 랜딩 히어로("성수" + "어니언 성수") → 후보 선택 → "이 가게 맞아요" → 체험 1회 실행, PC(1280)·모바일(390) 화면 전체와 본문 텍스트를 저장해 대조.
> 한계: 1개 가게·1회 실행. 하라식당 등 다른 사례와 비인기 가게는 미점검. 체험은 플레이스 ID 없는 후보 경로(네이버 플레이스 접속 없음)로 실행했다.

## 후속: 리뷰 수·평점 직접 입력 (D의 대응, 같은 날 구현·배포)
- **방식**: 결과 화면 "리뷰 수와 평점을 알려 주세요"(선택 입력, `TrialReviewInputCard`) — AEOlab이 방문자 리뷰 수를 읽지 못한 경우에만 노출. 입력값은 첫 화면 카드와 입력 카드에 **"입력하신 값 · AEOlab이 확인한 값이 아니에요"**로 따로 표시하고 "측정으로 확인된 것"에는 섞지 않는다.
- **검증**(`lib/trialReviewInput.ts`, 경계값 17건 통과): 리뷰 수 0 이상 정수·100만 이하(쉼표 허용), 평점 0 초과 5 이하(소수 첫째 자리로 반올림), 빈 입력만 제출하면 안내.
- **저장·반영**: 서버에는 저장하지 않는다(체험 기록은 업종 평균·공유 카드에 쓰여 미확인 값이 집계를 오염시킬 수 있음). localStorage `aeolab_trial_review_input` → 가입 온보딩이 읽어 사업장 생성 요청의 `review_count`·`avg_rating`으로 전달, 생성 성공 시 삭제. 가입 후 플레이스 실측이 생기면 실측이 우선(`scan.py` 플레이스 통계 동기화).
- **라이브 확인**(어니언 성수): 잘못된 값 3종 거절·미저장, 정상 입력 저장, 확인된 것 블록에 미혼입, 지우기, 모바일 가로 스크롤 없음, 페이지 오류 0. **온보딩 이어받기는 로그인 계정이 없어 라이브 미확인**(코드 경로·백엔드 스키마 `ge=0`/`le=5`로 확인).
- **체험 점수에는 영향 없음**: 체험 화면은 점수 숫자를 노출하지 않으며 입력값은 점수 계산에 넣지 않았다. 효과는 가입 후 첫 스캔부터.

## 후속 2: "유명 가게가 약해 보이는" 원인을 실데이터로 반증·정량화 (같은 날)
가설을 먼저 세우고 공식 API(블로그·지역검색)로 검증했다. 네이버 사이트 접속 없음.

| 가설 | 검증 | 결론 |
|---|---|---|
| 블로그 건수 28건은 **지역 규칙**(`성동구` 필요) 때문에 과소집계 | 어니언 성수: 상위 100건 중 이름 등장 31, 확인 28, 지역 제외 3 | **기각** — 영향 3건뿐 |
| **이름 변형**(순서 뒤집음·브랜드만) 때문에 과소집계 | 이름 통째 31 / 순서 뒤집음 9 / 브랜드만 93(한입베이글 50→55, 도토리오븐 변화 없음) | **부분 맞음, 규칙 변경 보류** — 브랜드만 세면 "어니언링" 같은 일반 단어 오탐 위험이 커서 건수 산식은 그대로 두고 화면의 "하한값" 안내를 유지 |
| 유사도순 5곳에 없어도 **후기 많은 순** 5곳엔 있다 | 어니언 성수 "성동구 베이커리" 2위·홍대 육지 "마포구 음식점" 3위 / 어니언 "성동구 카페"·하라식당 두 검색어는 없음 | **부분 맞음 → 있을 때만 표시로 구현** (git 6b9e216) |
| 등록 사업장은 리뷰 미수집이 0건으로 점수에 들어간다 | `review_count DEFAULT 0`, 생성 `or 0`. 실측: 활성 8곳 중 ID 없음 2곳(둘 다 전부 0), **구독자 사업장 0곳** | **맞음, 영향은 현재 0곳** → 좁은 조건으로 수정 (git 5df9c24) |

- **후기 많은 순 인기 신호**: `naver_visibility`에 `sort=comment` 지역검색을 같은 호출 묶음에 병렬 1회 추가(지연 없음). 네이버 문서상 "카페·블로그 후기 개수 순"이라 화면에도 "블로그·카페 후기 기준"으로 쓴다. 내 가게가 상위 5곳 안에 있을 때만 `review_sort_rank`를 채워 체험의 "측정으로 확인된 것"과 네이버 카드 문구에 표시한다. **없다고 감점하지 않고, 조회 실패는 '확인 못 함'.** 서버 실 API 확인(키워드 "카페"만이면 없음, "카페+베이커리"면 2위).
- **등록 사업장 리뷰 기본값**: `_is_review_unmeasured`가 `naver_place_id` 키가 있고 비었으며 리뷰 값(리뷰 수·평점·영수증·방문자)이 전부 0일 때만 미측정으로 제외 후 재정규화. 플레이스 ID가 있으면(스캔이 수집) 0은 실측으로 유지, 키가 없는 dict는 기존 동작. 빠른 스캔 조회에 `naver_place_id` 컬럼 추가. 변이 검증 3건.
- **운영자 메일 문구**: 차단 알림의 "직전 성공 결과가 날짜와 함께 보입니다"는 근거 화면 코드를 찾지 못해 확인된 내용으로 교체(git b90af35).
- **report.py 경로 확인(누락 재확인)**: 진단·시뮬레이션 2곳은 `naver_place_id`를 조회해 새 규칙이 적용된다. 대행 30일 재스캔(`jobs.py`)은 `review_count`도 조회하지 않아 기존 규칙(None=미측정)으로 이미 제외 — 변경 불필요.
- **체험 리뷰 수 자동 수집은 구현 보류**(수요 없음 — 일 5건 이하·점검돼도 리뷰 수 수집 29%): 판단·트리거·설계는 `docs/trial_review_autocollect_design_2026_10_28.md`.
- **확인하지 못한 것**: 새 체험 화면(후기순 문구)은 오늘 IP 체험 한도(3회)를 다 써서 **라이브로 다시 만들지 못했다**(빌드 산출물 포함·페이지 로드 오류 0·백엔드는 실 API로 확인). 내일 어니언 성수("카페+베이커리")로 한 번 더 확인할 것.

## 발견했지만 손대지 않은 것
- ~~**등록된 사업장은 리뷰 미수집이 0건으로 취급될 수 있다.**~~ → **후속 2에서 좁은 조건으로 수정됨(git 5df9c24).** 아래는 발견 당시 기록:
- **등록된 사업장은 리뷰 미수집이 0건으로 취급될 수 있다.** `businesses.review_count`는 `INTEGER DEFAULT 0`이고 `business.py` 생성이 `req.review_count or 0`을 저장하므로, 플레이스 ID도 입력도 없는 사업장은 `_is_review_unmeasured`(None 기준)에 걸리지 않고 "리뷰 0건 실측"으로 점수에 들어간다. 체험·ID 미확정에서 고친 편향이 등록 사업장에는 남아 있다. 고치려면 컬럼 NULL 허용 여부·프론트 `BusinessQuickEditPanel`(NaN 합산) 등 영향 확인이 필요해 별도 과제로 남김.

## 확인했더니 이미 있어서 만들 필요 없던 것
- ChatGPT 분모("50번 중") 표시 — 이미 모든 위치에 있음.
- 체험 화면에는 총점 라벨("AI 검색 준비도 · …")과 점수 숫자가 없음 → "측정된 범위 기준" 라벨 과제는 이 화면에서는 해당 없음(대시보드 쪽은 별도).

## 남은 것
- 구글 지도 항목의 리뷰가 4개인 것은 구글(Serper) 응답 그대로의 실측값이다(영문 이름 검색에서도 같은 항목 하나뿐). 유명 가게인데 리뷰 4개로 보일 수 있으나 지어낼 수 없다. 화면은 "구글 지도 평점·리뷰 수는 네이버와 별개"라고 안내 중.
- D(리뷰 수 미수집), 다른 인기 가게 사례(하라식당 등)·비인기 가게 점검, 로그인 대시보드 실화면 점검.
- ChatGPT 횟수는 같은 가게 연속 두 번 실행에서 18→16, 21→22로 달랐다(화면이 "몇 번 정도는 달라질 수 있다"고 안내하는 범위).

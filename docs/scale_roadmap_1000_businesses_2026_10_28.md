# 사업장 1,000곳 확장 로드맵 (2026-10-28)

> 질문: 사업장이 1,000곳을 넘으면 서비스가 멈추지 않는가, 유료 서비스를 쓰면 원활해지는가.
> **이 문서의 수치는 코드 기준 모델·추정이며 실측이 아니다.** 구독자 0명 상태에서 작성했다(실측 후 §6 지표로 교체할 것).
> 법적으로 민감한 항목(프록시·주기 차등·기능 축소)은 **사용자 결정 없이 실행하지 않는다**(CLAUDE.md 작업 지침 8번).

## 1. 결론 요약

1. **"모든 기능이 멈춘다"는 과장이다.** 멈추는 것은 **네이버 화면 접속(Playwright)에 의존하는 기능**이고, 그것도 보호 장치(회로·쿼터·속도)가 있어 먼저 **갱신이 늦어지는** 쪽으로 나타난다. 상한을 무리하게 올려 IP가 차단되면 그때는 네이버 의존 기능 전체가 일시 정지한다(2026-10-27 실제 경험).
2. **네이버 접속과 무관한 기능은 영향이 없다**: AI 스캔(ChatGPT·Gemini, 비용만 비례), 지역검색·블로그·DataLab·검색광고 공식 API, 카카오, 결제.
3. **유료 서비스는 병목 일부만 푼다.** 대시보드 동시접속(Supabase)과 서버 처리량은 돈으로 풀리지만, **네이버 차단 위험은 유료 프록시로도 "확실히" 풀리지 않는다**(§5). 가장 확실한 해법은 **측정 대상·횟수를 줄이고, 같은 측정을 공유하고, 사용자 쪽에서 수집하는 구조**다.

## 2. 병목 지도

| 병목 | 현재 값 | 1,000곳에서 | 근거 |
|---|---|---|---|
| 네이버 접속 일일 상한 | 600페이지, 정기 잡 몫 70%, 경쟁사 크롤 몫 60% → **경쟁사 하루 252페이지**(모두 근거 없는 제안값, `.env`로 조정) | 필요량 약 **4,700페이지/일**(20곳 주간 660페이지=곳당 33페이지를 단순 확장, 모델) → 약 8배 | `ai_scanner/__init__.py:243,256`, `scan_scheduling.py:147`, `scripts/naver_load_model.py` |
| 경쟁사 크롤 | 곳당 6페이지, 2주 주기 | 겹침 0%이면 200곳부터 간격 증가, 300곳 약 21일(시뮬레이션) | `tests/test_competitor_stale_first.py` |
| Playwright 동시 실행 | 1개(`PLAYWRIGHT_MAX_CONCURRENCY`) | 처리 속도 한계(미측정) | CLAUDE.md 운영 서버 주의사항 |
| 대시보드 동시접속 | Supabase 무료 플랜, 동시 50명 부근에서 응답 붕괴(서버 CPU는 유휴) | 병목 | `docs/dashboard_load_test_and_capacity_v1.0.md` |
| 백엔드 worker | 1개, 메모리 락 9개 | 다중 worker 전환 시 락 이전 필요 | `docs/backend_worker_scaling_trigger_v1.0.md` |
| AI API 비용 | 스캔 1회당 Gemini·ChatGPT 각 100회 | 사업장 수에 비례(실측 전 상단 불확실) | CLAUDE.md API 비용 관리 |

## 3. 규모별 단계

| 사업장 수 | 상태(모델) | 할 일 |
|---|---|---|
| ~100곳 | 경쟁사 일정·상한 모두 여유. 접속 상한은 약 50곳에서 넘을 수 있다(경쟁사 분산 시나리오, 겹침 미반영이라 비관적) | **현 구조 유지.** §6 지표 실측 시작 |
| 100~300곳 | 접속 상한이 먼저 부족해짐, 대시보드 동시접속도 위험 | **A(측정 대상 축소) + B(공유 확대)**, Supabase 유료 플랜 검토, 갱신 주기 문구를 현실에 맞춤 |
| 300~1,000곳 | 중앙 서버 IP 접속으로는 한계 | **C(사용자 쪽 수집) + D(인프라 확장)**, E(공식 API)는 가능한 범위에서 병행 |
| 1,000곳 이상 | 구조 전환이 전제 | 위 전부 + 큐 기반 작업 분산 |

## 4. 대책 상세

| # | 대책 | 효과 | 법적 민감 | 사용자 결정 | 선행 확인 |
|---|---|---|---|---|---|
| A | **측정 대상 축소**: 로그인하지 않은 지 오래된 사업장·무료 플랜은 자동 측정 중지(접속 시·수동 요청 때만). 무료는 이미 자동 측정 없음 | 큼(측정 대상이 활성 유료 사업장으로 한정) | 낮음 | 플랜별 주기 차등은 **공개 문구·요금제 약속을 바꾸므로 필요** | 활성 사용자 비율(실측) |
| B | **공유 확대**: 같은 업종·지역은 키워드·경쟁사가 겹침 → 검색어 단위 순위 캐시(6시간, 구현됨)·경쟁사 캐시(구현됨, **2026-10-28 일정 예산에 반영**) | 겹침 비율에 비례(미확인) | 낮음 | 불필요 | `place_cache_snapshot` 일별 적중률, `/admin/naver-access` `rank_card_cache` |
| C | **사용자 쪽 수집(Phase 2, 브라우저 확장)**: 사장님 본인 PC에서 자기 가게 정보를 읽어 전송 | 매우 큼(서버 IP 접속 부담이 사업장 수에 비례하지 않음) | **중간**(별도 법률 검토) | **필요** | 개발 규모·사용자 설치 의향 |
| D | **인프라 확장**: Supabase 유료 플랜, 큐·다중 worker, 서버 사양 상향. Playwright 동시성을 올리면 같은 시간당 네이버 접속이 늘어 차단 위험도 같이 커지므로 **상한 조정과 묶어서** 판단 | 대시보드·처리량 병목 해소 | 낮음 | 비용 승인 | 부하 재측정 |
| E | **공식 API 이전**: 이미 쓰는 것(지역검색·블로그·DataLab·검색광고) 외에 **플레이스 리뷰·통계를 제공하는 외부 개발자용 공식 API는 이번 검색에서 확인되지 않음** | 제한적 | 낮음 | 불필요 | 네이버 개발자센터·스마트플레이스 센터 공지 직접 확인 |
| F | **프록시**(§5) | 차단 확률 일부 감소, 보장 아님 | **높음** | **필요** | 우리 환경에서 장기 시험 |

권장 순서: **A·B → D(필요 시점에) → C → F(마지막)**. A·B는 비용·법적 부담이 거의 없고 효과가 가장 크다.

## 5. 유료 서비스로 원활해지는가

| 유료 서비스 | 풀리는 것 | 안 풀리는 것 | 비용(2차 출처, 공식 페이지 재확인 필요) |
|---|---|---|---|
| **Supabase Pro** | 대시보드 동시접속 병목의 유력 해소책(무료 플랜에서 쿼리 큐잉이 원인이라는 실측 기반. **유료로 올리면 실제로 해소되는지는 미검증**) | 네이버 접속 한계 | 월 $25 + 컴퓨팅 비용(마이크로 $10 크레딧 포함이라는 설명 있음), 컴퓨팅 크기별 연결 수 한도는 확인 못 함 |
| **한국 주거용 프록시** | IP 기반 차단 확률 감소 가능 | 행동 패턴·브라우저 특성·쿠키 기반 판단은 못 막음, 네이버 대상 차단률 독립 검증 자료 **없음**, 법적 위험 증가, 키워드 순위 측정은 프록시 인자가 없어 현재 **연결 안 됨**(`naver_keyword_rank.py`에 프록시 코드 0건) | GB 단위 과금(업체별 2.5~8달러/GB 수준 광고가 상충, 페이지당 용량은 **미측정**이라 월 비용 산출 불가) |
| **서버 사양 상향** | Playwright 동시 실행 여력 | 네이버 상한·차단은 그대로(오히려 동시성을 올리면 위험 증가) | 서버 요금표 |
| **네이버 데이터 대행·유료 API** | 이번 조사에서 **확인된 제품 없음** | - | - |
| **AI API 상위 요금제(Gemini 결제 연결)** | 무료 티어 한도로 제거했던 기능 복원 | - | 사용량 비례 |

→ **"돈을 쓰면 원활"은 Supabase·서버·AI API 축에서는 맞고, 네이버 접속 축에서는 맞지 않는다.** 네이버 접속 축은 구조(A·B·C)로 풀어야 한다.

## 7. 사용자 결정이 필요한 항목

1. 플랜별 갱신 주기 차등(공개 문구·요금제 변경 수반)
2. Phase 2(브라우저 확장) 착수와 법률 검토 범위
3. 프록시 구매 여부(권장: 마지막 수단, 구매 기준은 차단 사건 기록)
4. Supabase 유료 전환 시점과 비용 승인
5. 네이버 접속 일일 상한(600)·몫(0.7, 0.6) 상향 여부 — 차단 위험과 맞교환

## 8. 미확인·주의

- 하루 4,700페이지는 20곳 구성(키워드 4개·겹침 없음) 단순 확장 모델. 실제 구성은 다를 수 있다.
- Playwright 1페이지 처리 시간, 페이지당 전송량, 1,000곳에서의 Supabase 한계는 **측정한 적 없음**.
- Supabase 컴퓨팅별 연결 수 한도, 프록시 업체 가격은 2차 출처뿐이라 공식 페이지 재확인 필요.
- **네이버 플레이스 평균 별점 노출 ON/OFF 도입(2026-07 시행 예정이라는 보도)**: 사업주가 별점 공개를 끌 수 있다면 우리 수집값이 비어 보일 수 있다. 크롤러·화면이 "확인 불가"를 0으로 처리하지 않는지 **미확인**(점검 필요).
- 플레이스 공식 API 부재는 "이번 검색에서 확인되지 않음"이지 "없음의 증명"이 아니다.

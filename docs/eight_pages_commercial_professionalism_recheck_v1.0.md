## §0. 배경

같은 날 이미 완료된 8개 페이지 재점검(git `4ded3aa`, **정확성 버그** 중심)을 마친 상태에서, "**상업적 수준의 전문적인 정보 제공**" 관점으로 추가 재점검을 요청받아 진행했다. 대상: 경쟁사 관리·변화 기록·성장 리포트·개선 가이드·소개글/콘텐츠·리뷰 답변·AI 광고 대비·창업 시장 분석.

이 세션의 핵심 교훈: **코드 읽기만으로는 못 잡는 버그가 있다.** 프롬프트 설계·JSON 파싱·D.I.A. 점수 로직·플랜 한도 카운팅 등은 실제로 API를 호출하고 DB에 실측 데이터를 넣어봐야 드러나는 결함이 반복적으로 나왔다.

## §7. 5차 — 잔여 사항 마무리 + 결정론적 테스트로 근본원인 규명

"잔여 사항을 진행해줘" 요청으로 3건 처리:

1. **광고대비·창업분석 월 한도**: `guides.context` CHECK 제약 반영 여부부터 실제 insert로 확인 → 이미 반영됨. DB에 실제 10개 더미 사용 기록을 넣어 `check_ad_defense_limit`/`check_startup_report_limit`이 정확히 경계값(used=limit)에서 `allowed=False`로 전환됨을 **결정론적으로 확인**. 테스트 데이터 정리 완료
2. **D.I.A. 자동재시도 루프**: 자연 변동(57.5~78.8점)으로 처음엔 실제 발동을 못 잡음 → `validate_intro_dia`를 몹(mock)해서 "1차 50점→재시도 85점"을 강제하고, 자체 시뮬레이션이 아니라 **`business.py`의 실제 프로덕션 엔드포인트 함수를 직접 호출**해 로그에 `"D.I.A. 50/100 미달 — 재생성 1/2"`가 실제로 찍히는 것을 확인 — 결정론적 검증으로 한계 극복
3. **소개글 잔여 소프트 허위주장 — 진짜 근본원인 규명**: 위 결정론적 테스트 준비 중 `keyword_taxonomy.py`의 restaurant 업종 LSI 키워드 목록 자체에 "프라이빗룸"·"30명 수용"이 SEO 키워드로 박혀있었고, D(다양성) 요소의 "LSI 4개 이상 자연스럽게 사용" 강제가 이를 사실 단정문으로 바꾸던 것을 발견(§6에서 고친 I·A·O와는 다른 제3의 경로). D 요소에 안전장치 추가, 재테스트로 "확인해 주세요" 유보 표현 전환 확인
4. **부수 발견 — `intro_draft` CHECK 제약 사전 존재 버그**: 위 결정론적 테스트 도중 `context='intro_draft'` insert가 CHECK 위반으로 실패하는 것을 우연히 발견 — `intro_draft`는 이 프로젝트의 **모든 CHECK 제약 이력에서 단 한 번도 허용된 적이 없었음**. 소개글 생성 기능이 생긴 이후 계속 사용량 기록이 조용히 실패해, 소개글·FAQ 합산 한도(`faq_monthly`)가 `faq_draft`만 카운트하고 `intro_draft`는 항상 0으로 집계되어 **소개글 생성이 사실상 무제한 가능했던 사전 존재 취약점**. `intro_draft`를 CHECK 제약에 추가 후, 실제 60개 사용 기록을 채우고 프로덕션 엔드포인트를 직접 호출해 정확히 `HTTP 429 "합산 한도(60회) 도달"`이 발생함을 확인

## §8. 비용 분석 — 소개글 생성 한도의 적정성

## §10. 사용자가 실행한 Supabase SQL (완료)

```sql
-- 1. exposure_freq 실측 표시용
ALTER TABLE score_history ADD COLUMN IF NOT EXISTS sample_size INTEGER;

-- 2. 광고대비·창업분석 월 한도 카운팅용
ALTER TABLE guides DROP CONSTRAINT IF EXISTS guides_context_check;
```

## §11. 검증 방법론 교훈 (향후 세션 참고)

1. **코드 검토 ≠ 라이브 검증**: JSON 파싱 실패, 프롬프트 지어내기, DB 기본값 문제는 전부 실제 API 호출·실제 데이터로만 드러났다
2. **자연스러운 LLM 변동에 기대지 말 것**: D.I.A. 재시도처럼 조건부 분기를 검증할 땐 mock으로 결정론적 테스트를 만들어 확률에 의존하지 않는다
3. **자기 판단도 재검증 대상**: "프롬프트만 읽고 얕다/한계다"라고 판단한 것 중 두 건이 부분적으로 틀렸다(리뷰답변, 경쟁사breakdown) — 실제 호출·실제 인프라 확인이 판단을 뒤집었다
4. **버그 검증 중 다른 버그가 튀어나올 수 있다**: `intro_draft` CHECK 제약 버그는 D.I.A. 재시도 루프를 테스트하다가 우연히 발견됨 — 결정론적 테스트를 만드는 과정 자체가 새로운 발견의 통로가 됐다
5. **DB 컬럼 기본값 vs NULL 구분**: "동기화 여부"·"실측 여부" 같은 boolean 판단은 반드시 "언제 값이 채워지는지"를 나타내는 전용 타임스탬프 컬럼(`*_synced_at`)으로 게이트해야 한다 — 값 자체의 null 체크는 기본값이 0/false인 컬럼에서 항상 실패한다

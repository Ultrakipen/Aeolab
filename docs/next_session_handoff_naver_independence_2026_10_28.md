- `robots.txt`: `pcmap.place`·`m.place`·`search.naver.com` 전체 `Disallow: /`, `map.naver.com`은 루트·`/p/`만 허용. `smartplace.naver.com` **미확인**.

- 우리 쪽 사실: 리뷰 본문은 읽되 **저장하지 않고 별점·리뷰 수 숫자만 추출**(`competitor_place_crawler.py:448-465`). 접속 도메인은 `pcmap.place`·`m.place`·`map`·`search`·`smartplace`.

- 붙여받은 어뷰징 기준 글(출처·날짜 미확인): 검색·클릭·예약 어뷰징 기준이며 별점 수집 정책 아님.

**결정/후속(사용자 몫)**

## 5. 별점 사용자 입력 정책 (미결)

- 사용자 말이 맞다: 사용자 입력은 점수 등 모든 곳에 반영해야 함(지침 7번). 앞선 "측정 없을 때만 반영" 권고는 철회. 분리해야 하는 것은 점수가 아니라 **화면 표기**("입력하신 값").
- 현황: 대시보드 `BusinessQuickEditPanel.tsx`에서 별점·리뷰 수 수정 → `PATCH /api/businesses/{id}`(`routers/business.py:355`). 점수는 다음 스캔에서 `biz.avg_rating` 반영(`score_engine.py:414-418`).
- 어긋남 4가지: ① 저장 직후 점수 즉시 재계산 여부 **미확인**(PATCH 355~415행 밖 미열람) ② 크롤이 읽으면 입력값을 조용히 덮어씀(`naver_place_stats.py:686`, `scan.py:3207-3210`) ③ 측정값/입력값 출처 구분 컬럼 없음(`avg_rating_source` 제안, Supabase SQL 수동 실행) ④ **수정 API에 범위 검증 없음 의심**(생성은 `schemas.py:114` 0~5). 예: 별점 500 입력 시 점수 부풀림 가능 — **후보 결함, 재현·반증 미수행**. 확인 후 서버 검증 추가(작은 변경, 바로 가능).
- 사용자 결정 필요: 측정/입력 우선순위, 점수 반영 방식, 출처 컬럼 추가.

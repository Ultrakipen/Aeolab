# Pro 경량 스캔 유지 판단과 재검토 조건 (2026-11-11)

> 질문: Pro의 풀스캔 주 3회 외에 나머지 날도 경량 스캔이 돌면 운영자 비용·네이버 차단 위험이 크지 않은가?
> 결론: **지금은 유지, 아래 조건 중 하나가 생기면 줄인다.** 사용자 결정 사항(제품·운영)이며 이 문서는 그 판단의 근거다.

## 1. 확인한 사실 (코드·서버)
| 사실 | 근거 |
|---|---|
| Pro는 풀스캔 주 3회({slot, slot+2, slot+4}) 외의 날 `"basic"`(경량) 스캔 | `services/scan_scheduling.py` `decide_scan_mode`(Pro: 풀스캔 요일이 아니면 "basic") |
| 경량 스캔은 `scan_basic`만 쓰고, 이 함수의 실제 호출처는 `jobs.py daily_scan_all` 한 곳 | `scheduler/jobs.py` `_scan_mode == "basic"` 분기 |
| 경량 결과도 풀스캔과 같은 경로로 `scan_results`에 저장 | `jobs.py` `_scan_mode`는 분기 이후 참조 없음, 저장은 `scan_results` insert(공통) |
| 경량일 네이버 접속은 브리핑 1페이지(AI탭 없음), 풀스캔은 1 + AI탭 4질의×3 = 13페이지 | `scripts/naver_load_model.py`(`LIGHT_SCAN_NAVER=1`, `AI_TAB_PER_FULL=4`, `AI_TAB_PAGES_PER_QUERY=3`) |
| 서버 설정: `NAVER_AI_TAB_ENABLED=true`, `NAVER_SCAN_SLOT_SPREAD=true`, `NAVER_AI_TAB_MAX_QUERIES` 미설정(기본 4), `NAVER_CAPACITY_BUSINESSES` 미설정(코드 기본 50) | 서버 `backend/.env` 키 존재 확인 |
| 환불 자격은 구독 후 저장된 스캔 결과가 하나라도 있으면 소멸(경량 포함) | `routers/settings.py _check_refund_eligibility` |

## 2. 크기 (계산 — 가정 포함)
- 네이버: Pro 1곳 주간 접속 = 39(풀 3회) + 4(경량 4회) = 43페이지, 경량의 몫 약 9%. 가게 구성을 basic 70/startup 10/pro 15/biz 5%로 가정하면 전체 스캔 접속에서 경량 비중 약 2%.
- 비용: ChatGPT `gpt-6-luna` 호출당 약 0.018원(`ai_usage_log`, 목적 `trial_recommend`, 11-06~11-11 조회) → 50회 약 1원 → Pro 1곳 월 약 17회 ≈ 15원 안팎. Gemini는 무료 등급(비용 None).
- Gemini 실패 기록: 조회 약 540건 중 `ResourceExhausted` 25건, `TimeoutError` 25건. 경량 스캔은 Gemini 50회를 더한다.

## 3. 유지 이유
1. 접속·비용 몫이 작다(위 계산).
2. 없애면 공짜가 아니다 — 경량일 네이버만 끄면 그날 스캔이 '측정 빠진 스캔'이 되어 변화 비교에서 제외된다(`change_signal_guard`). 경량 스캔 자체를 없애면 Pro의 데이터 점이 주 7개 → 3개가 되고 코드·테스트·문구를 바꿔야 한다.
3. 해를 끼친 증거가 없고 서비스는 오픈 전(실사용자 없음)이다.
4. 랜딩은 "주 1~3회(Biz는 매일)"로 풀스캔 횟수만 약속한다 — 경량은 약속 밖이라 광고하지 않는다("Pro는 매일 측정"이라고 쓰지 말 것: 경량은 표본 50회).
5. 환불 영향은 미미하다 — Pro는 경량 덕에 첫 자동 측정이 다음 새벽이 되지만, 풀스캔만이어도 3요일 중 가장 가까운 날이라 소멸 시점 차이는 평균 1일 안팎. 환불 규칙(07-07 사용자 선택, 11-08 '현행 유지')은 그대로.

## 4. 줄이는 조건 (제안값 — 근거 있는 기준이 아니라 조정 가능)
아래 중 하나라도 해당하면 줄인다. 줄이는 순서: ①경량일 네이버 접속 생략(`skip_naver`) → ②Pro 경량 스캔 자체 중단.
- 네이버 차단 사건이 기록될 때(최우선 지침 8번, 접속량부터 줄인다).
- Gemini `ResourceExhausted`가 눈에 띄게 늘 때(현재 약 4.6%, 약 540건 중 25건).
- 활성 사업장이 운영 용량 기준(50곳)의 60%(약 30곳)에 가까워질 때.
- (확인 결과 현재는 해당 없음 — §6) 경량 스캔 결과가 사용자 화면·알림에 쓰이지 않는 것이 확인될 때.
- ①의 부작용: 경량일 스캔이 변화 비교에서 제외되므로 추이 그래프의 점이 줄고, '측정 빠진 날' 표시가 늘 수 있다 — 적용 전 화면 확인.

## 5. 하지 않은 것
- 경량 스캔 제거, 경량일 네이버만 선제적으로 끄기, "Pro는 매일 측정" 광고.
- `lib/plans.ts:43`의 "Basic: 주 1회(월요일)" — 낡은 주석이 아니라 "v3.5 변경 요약(2026-04-22)" **변경 이력 블록**의 기록이다(같은 블록의 가격도 옛 값). 이력이라 고치지 않는다. (처음에 낡은 주석으로 잘못 판단했다가 정정.)

## 6. 경량 스캔 결과 사용처 추적 (2026-11-11 코드 확인) — 앞서 미확인이던 항목 해소
경량 행은 풀스캔 행과 **같은 저장·알림 경로**를 탄다(`scheduler/jobs.py daily_scan_all`, `_scan_mode`는 스캔 방식 선택 이후 참조 없음).
| 사용처 | 근거 | 경량 행 영향 |
|---|---|---|
| 점수 계산 | `jobs.py:783` `calculate_score` 공통, AI 브리핑 점수는 최근 스캔과 평활화(`attach_prior_naver`, `:782`) | 동일 경로. 표본만 50회(풀스캔 100회)라 AI 노출 항목의 흔들림이 더 클 수 있음(실측 비교는 안 함) |
| AI탭 값 | 경량일엔 AI탭을 안 재서 `get_last_known_visibility`로 최근 실측값을 이어받음(`jobs.py:980-984`, `naver_ai_tab_scanner.py:400`) | "미노출"로 덮어쓰지 않음 — 가짜 하락 방지 설계 |
| 저장 | `scan_results` insert(`jobs.py:987`), `score_history` 기록·upsert(`:1109-1190`) | 일별 추이에 경량일 점이 들어감(주 7점) |
| 스캔 완료 알림 | `jobs.py:1220` `_scan_notify_ok and not _is_naver_retry and _cmp_ok`(네이버 측정·비교 가능일 때만) → 번호당 주 1건 상한 | 경량일도 조건이 맞으면 후보, 상한이 막음 |
| 성장 단계 상승 알림 | `jobs.py:1293-1314` 히스테리시스(`_hysteresis_blocked`) 적용 | 경량일 점수로도 판정되나 히스테리시스가 흔들림을 걸러냄 |
| 점수 변화 알림 | `daily_kakao_notify`(`:1424-1442`) `comparable_scans` + 종류별 간격(7일) | 동일 규칙 |
| 경량일에도 도는 접속 | `jobs.py:756-761` 네이버 검색 API(공식)·카카오 API·웹사이트 SEO 점검, `:788-811` 블로그 재분석(14일마다) | Playwright 아님. 풀스캔과 같은 호출이라 경량이라서 늘어난 양은 없음 |
결론: 경량 결과는 **사용자 화면·이력·알림에 쓰인다**(가치 없음 조건은 현재 미충족). 앞서 §4의 네 번째 조건(경량 결과가 안 쓰임)은 해당 없음으로 확인.
확인되지 않은 것: 스캔 행에 경량/풀 구분 컬럼이 없다(표본 수 `sample_size`로 추정 가능한지는 미확인) — 오픈 후 경량 vs 풀 점수 흔들림을 비교하려면 구분이 필요할 수 있다(DB 컬럼 추가는 SQL 수동 실행이라 필요가 확인될 때만).

## 7. 미확인
- 정기 스캔의 ChatGPT 실측 단가(조회한 행은 체험 용도만 보임).
- Gemini 한도 초과 실패와 경량 스캔의 정확한 인과.
- 네이버 쿼터(`check_naver_playwright_quota`)가 경량 스캔 접속을 차감하는 전체 코드 경로(부하 모델 상수로만 확인).
- 경량 vs 풀 점수 흔들림의 실측 크기(표본 50 vs 100).

# 정기 스캔 워커 분리 설계 (설계만 — 구현은 트리거·사용자 결정 후)

> 인수 문서 `next_session_handoff_2026_10_30_plan.md` §4-8. 근거는 코드 읽기와 모델 계산이며 **실측이 아닌 항목은 표시**했다.
> 기존 보류 문서: `backend_worker_scaling_trigger_v1.0.md`(락 9개·세마포어 1개가 프로세스 메모리, `--workers 1` 고정 이유).

## 1. 먼저 확인한 사실 (코드 근거)
- 스케줄러는 API와 **같은 프로세스**다: `main.py:52,238` `start_scheduler()`. 정기 잡(`daily_scan_all` 02:00 등)과 사용자 요청이 한 이벤트 루프·한 Playwright 세마포어(`multi_scanner.py:40`, 기본 1)를 나눈다.
- `daily_scan_all`은 사업장을 **순차** 처리한다(`jobs.py:541` `for i, biz in enumerate(businesses)`). 사업장 간 병렬이 없다.
- Gemini 호출 간격 제한 `GEMINI_MIN_INTERVAL`(서버 4.5초, `gemini_scanner.py:31`)이 프로세스 전체에 걸려 있다. 정기 스캔은 100표본 그대로이므로 **사업장 1곳의 Gemini 단계만 약 7.5분**(100×4.5초, 모델 계산).

## 2. 병목은 CPU가 아니라 세 가지 직렬 구간
| 구간 | 현재 | 300곳에서의 함의 |
|---|---|---|
| Gemini 간격(무료 등급 대응) | 사업장당 ≈7.5분, 직렬 | 하루 스캔 대상이 N곳이면 N×7.5분. 02:00 시작 → 24곳이면 3시간, **60곳이면 7.5시간(모델)**. 무료 등급 일 한도(flash-lite 500회 ≈ 5곳)가 먼저 막으므로 **유료 전환 없이는 300곳 불가** — 이 항목은 사용자 몫(결제) |
| Playwright 세마포어 1 | 네이버 접속은 모두 한 줄 | 네이버 접속은 어차피 차단 방지 속도 제한이 지배(분 단위 윈도우)라 병렬화로 얻는 것이 적음 |
| 사업장 루프 직렬 | AI 호출(대기 위주)과 네이버(Playwright)가 같은 순서에 묶임 | AI 호출은 I/O 대기라 사업장 간 병렬이 가능(아래 §3) |

> 모델 하루 스캔 대상 수: 300곳 중 Basic 주 2회·Pro 주 3회 혼합이면 하루 약 100곳 안팎(플랜 구성 **미확인**, 가입자 분포 없음).

## 3. 단계별 설계 (작은 것부터, 앞 단계가 효과를 입증해야 다음으로)
1. **같은 프로세스 안 AI 단계 병렬화 (워커 분리 불필요)**: 사업장 루프에서 AI 호출(Gemini/ChatGPT)을 동시 2~3곳 처리하고 네이버 단계는 기존 세마포어·속도 제한 뒤에서 직렬 유지. 유료 Gemini에서 `GEMINI_MIN_INTERVAL=0`이 전제. 락 문제 없음(월 한도 락은 사용자 요청 경로). 위험: 한 사업장 오류가 다른 사업장에 번지지 않게 사업장별 try/except 유지, DB 쓰기 순서 의존 없음 확인 필요.
2. **정기 잡만 별도 프로세스로 (`aeolab-worker`)**: pm2에 두 번째 앱 — 스케줄러 잡 전용, API는 `start_scheduler()` 미호출(환경변수 `RUN_SCHEDULER=0`). **API가 `--workers 1`이면 사용자 요청 락·세마포어는 그대로 한 프로세스라 안전**하고, 정기 잡 쪽 Playwright 세마포어는 워커 프로세스에 따로 생긴다. ⚠️ 이 때문에 **사용자 요청(API 프로세스)과 정기 잡(워커 프로세스)이 각자 Playwright를 최대 1개씩 → 동시 2개**가 되어 RAM(인스턴스당 300~500MB, 4GB 서버)과 **네이버 접속 총량 속도 제한**(현재 파일 기반 상태 공유 여부를 먼저 확인해야 함)에 영향. 그래서 속도·쿼터 상태가 이미 프로세스 간 공유되는지(`.naver_quota_state*` 파일 기반인지)를 구현 전에 코드로 확인해야 한다 — **미확인**.
3. **API 워커 수 증가**: 9개 락을 `pg_advisory_lock` 등으로 옮긴 뒤에만 가능(기존 문서의 트리거 조건 그대로). 대시보드 동시 접속 병목은 Supabase라서(8월 실측) 효과가 제한적.

## 4. 단계 2의 구체 변경점 (구현 시 체크리스트)
- 스케줄러 시작을 환경변수로 분기(`main.py:238`), pm2 `ecosystem.config.js`에 `aeolab-worker` 추가(`RUN_SCHEDULER=1`, API는 0). 기본값은 지금과 동일(1)로 두어 롤백 = 환경변수 한 줄.
- 잡이 API 프로세스의 메모리 상태에 기대는 곳 점검: `naver_status`·쿨다운·`naver_usage_meter`·`probe_cache`·경쟁사 동기화 큐(`competitor_sync_queue`, 프로세스 메모리) — 프로세스가 나뉘면 서로 보이지 않는다. 쿨다운/회로 상태가 **파일**이면 공유, **메모리**면 분리 시 한쪽만 차단을 알게 되는 결함이 생긴다 → 먼저 목록화.
- 헬스·알림: 워커 프로세스 다운 감지(스케줄러 데드맨 스위치 `alert deadman` 이미 있음 — 워커로 옮겨도 동작하는지 확인).
- 배포: deploy.yml의 `pm2 restart` 대상에 워커 포함.

## 5. 지금 하지 않는 이유와 착수 트리거
- 지금 활성 사업장 8곳, 야간 스캔은 사업장당 수 분이라 직렬로 충분. 트리거는 기존 문서(세마포어 대기열 초과 3일 연속, 락 409 반복, 구독자 50명) **또는** 야간 스캔 총 소요가 새벽 시간대(02:00~07:00)를 넘기는 날이 관측될 때. 소요 시간은 `daily_scan_all` 시작·종료 로그로 이미 측정 가능 — 한 줄 집계 스크립트로 주 1회 확인 권장(**미구현**).
- 사용자 결정 필요: Gemini 유료 전환(단계 1의 전제), 단계 2를 켜는 시점.

## 6. 미확인
- 정기 잡 쿼터·속도 제한 상태가 프로세스 간 공유되는지 / 300곳의 플랜 구성 / 병렬 2~3곳이 OpenAI 속도 제한에 걸리는지 / 유료 Gemini의 실제 분당 한도.

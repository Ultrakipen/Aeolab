## 1. 이 작업의 목적

**블로그 진단 페이지의 목적은 두 가지다 — ① 나의 블로그의 상세한 현황/진단, ② AI 노출 현황/진단/개선.** (2026-07-18 사용자 명시 확정) 이 두 축을 기준으로 매 기능·매 수정을 판단한다:

- **①(내 블로그 현황/진단)**: 글 개수·발행 빈도·최신성, 글별 체크리스트(8항목)와 AI(Claude Haiku) 정성판정, 업종 키워드 커버리지(§3-1에서 20개 상한 버그로 무력화돼 있던 바로 그 기능) — "지금 내 블로그가 어떤 상태인가"에 답하는 축.
- **②(AI 노출 현황/진단/개선)**: 4채널(gemini/chatgpt/naver/google) 실제 AI 인용 매칭, 인용 벤치마크(업종 평균 대비), 자기추세(§3-2), 소재/제목 추천(`topic_suggestions_v2`) — "AI 검색에 얼마나 노출되고 있고 무엇을 하면 나아지는가"에 답하는 축.

**2026-07-18 후속 확정 — 경쟁사 대비 포함 원칙**: 사용자가 재확인한 취지는 "AEOlab의 블로그 진단이 NAEO보다 더 전문적인 분석을 하며, 내 블로그 현황과 AI 노출 여부/현황을 알려준다"이며, **여기에 경쟁사 대비를 포함하기를 원함**. 단, 방식은 다음 원칙으로 제한한다(§5-1 판단 근거):

- **방식 A(채택)** — "경쟁사 관리" 페이지가 이미 주간 배치(목요일 03:00 `enrich_competitor_details_job`)로 크롤링해 DB에 저장해둔 `comp_keywords`/`blog_mention_count`를 블로그 진단 페이지에서 재사용. **추가 서버 부하 없음**(DB 조회만), 이미 구현돼 있음(`competitor_blog_comparison`, `competitor_blog_mentions`). 앞으로의 "경쟁사 대비" 개선은 전부 이 방식 안에서 진행한다.
- **방식 B(비채택, 재확인)** — 경쟁사의 "블로그" 자체를 실시간으로 크롤링해 직접 비교. `competitors` 테이블에 블로그 URL 컬럼 자체가 없어 데이터 소스가 없고, 있다 해도 서버(vCPU2/RAM4GB, `PLAYWRIGHT_MAX_CONCURRENCY=1` 전역 공유)에 실제 부하가 걸림 — §2-B(경쟁사 실시간 구조비교, 영구 제외)와 본질적으로 동일한 항목이라 다시 채택하지 않는다.

사용자가 세션 중반에 명시적으로 우선순위를 재확정한 문장이 이 작업 전체의 기준이다:

> "이 창에서 가장 중요한 개선 작업은 사용자의 네이버 블로그 AI 노출 진단이야. 모두 개선이 되었는지?"

이후 다음 요구가 이어졌다:

> "솔직하게 오판과 누락없이 실질적으로 사용자가 블로그 진단을 하면 많은 정보제공과 AI노출의 현재 상황, 어떻게 개선하면 좋은지 알려주는 블로그 진단 페이지로 해줘."
>
> "경쟁사의 격차, 나의 위치를 확인할 필요가 있는지부터 점검을 원함. '블로그 진단' 페이지에서 나의 블로그만 전문적인 진단을 한다면 사용자가 만족도가 높지 않는지? 경쟁사와 비교를 한다면 나의 블로그 vs 경쟁사 블로그 상황인데 비교를 해야하는지?"

즉 목표는 **기능 추가가 아니라 "이미 만든 것이 실제로 정직하고 정확하게 동작하는가"를 실측으로 검증하고, 발견되는 구조적 결함을 그때그때 고치는 것**이었다. 매 라운드마다 사용자가 "오판과 누락이 없었는지?"를 재차 물었고, 그때마다 자체 반증에서 실제 버그를 찾아냈다(아래 §3).

## 5. 현재 페이지가 "전문적 진단"인지에 대한 최종 판단

블로그 진단은 이미 3중 구조다 — "내 블로그만 본다"는 지적은 정확하지 않음:

| 축 | 기능 | 현재 상태 |
|---|---|---|
| ① 절대 기준 | 8항목 체크리스트(항상 노출) + 키워드 커버리지 섹션(**토글 뒤, §5-1**) | 체크리스트는 정상 노출, 키워드 커버리지(§3-1에서 고친 버그의 결과물)는 기본 숨김 |
| ② 자기 자신 대비 추세 | `BlogScoreTrendChart` (**토글 뒤, §5-1**) | §3-2로 데이터는 이제 정상 축적되지만 기본 숨김이라 사용자가 안 누르면 못 봄 |
| ③-a 업종 평균 대비 (AEOlab 구독자 표본) | `citation_benchmark` | 코드 정상, **현재 스케일(7개 사업장)에서 구조적으로 100% 비어있음** — 구독자 늘면 자동 해소, 추가 개발 불필요 |
| ③-b 경쟁사 대비 (경쟁사관리 크롤링 재사용) | `competitor_blog_comparison`, `competitor_blog_mentions` (**토글 뒤, §5-1**) | 코드 정상, 데이터도 정상(§5-1 재검증) — 기본 숨김 |

naeo.kr 대비: 콘텐츠 정성판정(LLM 기반)은 AEOlab이 우위. "AI 랭킹"(업종 내 TOP3 리더보드)은 naeo.kr에 있고 AEOlab엔 없음 — 이것도 ③-a와 동일하게 최소표본 문제라 지금 만들어도 못 채움. 반면 ③-b(경쟁사 대비)는 표본 문제가 없다 — naeo.kr에 없는 AEOlab만의 차별화 지점이 될 수 있음.

즉 "위로 옮기자"는 처방은 부정확했다 — 같은 토글 안에서 순서만 바꿔도 여전히 기본 숨김이다. **오늘 세션에서 고친 두 개의 P0 버그(§3-1 키워드 커버리지, §3-2 자기추세)의 실제 사용자 노출 지점이 전부 이 토글 뒤에 있다는 것이 이번 재점검의 핵심 발견.**

**서버 부하 판단** (2026-07-18 사용자 질문에 대한 답, 재확인 결과 변동 없음): `_fetch_competitor_blog_mentions`(`blog.py:92`) 코드를 직접 읽어 신규 API 호출 없이 DB SELECT만 함을 확인. 방식 A(comp_keywords/blog_mention_count 재사용)는 **추가 부하 없음** — 방식 B(경쟁사 블로그 실시간 크롤링, `competitors` 테이블에 URL 컬럼 자체 없음, §2-B와 동일 항목)는 비채택 유지.

**중복 판단** (재확인 결과 변동 없음): `gap_analyzer.py`(경쟁사 관리, 내 리뷰 기준)와 `blog_analyzer.py`(블로그 진단, 내 블로그 글 기준)는 "내 쪽" 비교 대상이 달라 기능적으로 중복 아님.

**데이터 신뢰도 재검증** (2026-07-18 추가 확인): `competitor_place_crawler.py:28`에 과거(2026-07-14 이전) "블로그 언급수 5곳 모두 296으로 오염" 버그 주석이 남아있어, `BlogMentionBenchmarkCard`를 더 노출시키는 게 나쁜 데이터를 부각시키는 역효과인지 우려해 실 데이터를 재조회함. 결과: 경쟁사별 값이 39/5/97/507/5 등으로 정상 분산 — 해당 버그는 2026-07-14에 이미 해소된 채로 남아있는 과거 주석일 뿐, 지금 노출을 늘려도 안전함을 확인.

## 6. 잔여 개선사항 (우선순위순)

1. **[최우선, 범위 수정됨] `showDetail` 토글 재설계** — §5-1에서 확인했듯 ①의 절반(키워드 커버리지)·②(자기추세)·③-b(경쟁사 대비) 전부가 기본값 `false`인 단일 토글 뒤에 숨어있음. 개별 패널을 위로 옮기는 게 아니라 **토글 자체의 설계를 바꿔야** 함 — 후보: (a) 기본값을 `true`로, (b) 가치가 가장 큰 2~3개(키워드 커버리지·자기추세·경쟁사 대비 중)만 토글 밖으로 빼서 기본 노출하고 나머지만 접기, (c) "요약 vs 상세" 구분 기준 자체를 재설계. **아직 미착수, 방향 결정 필요.**
2. **③-a(업종 평균 대비, citation_benchmark) 신규 개발은 지금 하지 말 것** — 코드가 정상이어도 표본 부족(전체 사업장 7곳)으로 못 채움. 구독자 20명 이상, 업종당 3곳 이상 모이는 시점에 재점검. (③-b 경쟁사 대비는 이 제약이 없음 — 1번 참조)
3. **comp_keywords 백필 자동화 확인** — 목요일 03:00 `enrich_competitor_details_job`이 이번에 수동 백필한 것과 동일하게 stale 데이터를 알아서 재동기화하는지 다음 주 목요일 이후 실측 확인 권장(현재는 코드 로직상 될 것으로 추정만 함, 실측 미확인).
4. **git push** — 이 세션과 별개 작업으로 보류 중(140+ 서버-로컬 diverge 파일, 서버 git HEAD `917b650` 이후 정체). `scripts/check_server_drift.sh`로 방향 판정 후 진행 — 사용자가 별도 요청 시에만.
5. **외부 블로그(Tistory/WordPress) LLM 품질판정** — 의도적 제외 상태(제목만 확보 가능, 본문 텍스트 없음). 크롤링 방식이 바뀌지 않는 한 재검토 불필요.

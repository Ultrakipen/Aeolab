# 대시보드 페이지 부하테스트 및 서버 용량 판단 (v1.0)

> 2026-08-23 실측. "현재 서버 사양으로 몇 명의 접속자를 대응할 수 있는지"라는 질문에 대해, 기존 답변(2026-08-21 경량 정적 페이지 부하테스트 — `/`·`/pricing`·`/login` 등)이 로그인 이후 실제 무거운 화면인 **대시보드**를 포함하지 않았다는 지적을 받아 재실측. 결론이 기존 서버 스펙(iwinv vCPU2/RAM4GB) 중심 판단과 **다른 축의 병목**을 드러냄 — 향후 "서버 업그레이드로 동시접속 대응력 향상" 판단 시 반드시 참고.

## 1. 배경 — 질문의 두 갈래

사용자 질문 "현재 서버 사양으로 몇몇 접속자를 대응할 수 있는지"는 두 가지로 해석 가능:

1. **페이지 동시 접속** — 로그인·대시보드 열람 등 일반 트래픽 (이 문서의 대상)
2. **동시 스캔** — 네이버 AI 브리핑 Playwright 스캔을 여러 명이 동시에 트리거 — 이건 `PLAYWRIGHT_SEMAPHORE=1`(`multi_scanner.py:41`)로 애초에 동시 1건만 처리되도록 설계돼 있어 "몇 명까지 버티나"라는 질문 자체가 성립하지 않음 (순차 대기, 큐 타임아웃 로그 0건으로 실사용 문제없음 확인)

사용자가 ①(페이지 동시 접속) 기준으로 확인 — 2026-08-21 부하테스트는 로그인 불필요한 정적/캐시 가능 페이지만 대상이었어서, **로그인 후 가장 무거운 화면인 대시보드**로 재실측 요청.

## 2. 방법론 — 실제 로그인 세션으로 라이브 대시보드 테스트

인증이 필요한 SSR 페이지를 실측하려면 진짜 로그인 세션이 필요했음. 절차:

1. **QA 임시 계정 생성** — Supabase Admin API(`/auth/v1/admin/users`, service role key)로 `qa-loadtest-20260823@aeolab.internal` 계정 생성 + 최소 사업장 1건(`부하테스트카페`, category=cafe, region=서울 강남구) INSERT. 스캔 데이터는 넣지 않음 — 실제 신규가입 직후 "아직 스캔 안 한" 상태(빈 상태 UI)가 오히려 흔한 실사용 시나리오이자, 임의 JSON 조작으로 백엔드 파싱 오류를 유발할 리스크가 없어 더 안전.
2. **실제 로그인 세션 쿠키 확보** — `/auth/v1/token?grant_type=password`로 access_token 발급 → `@supabase/ssr`(설치버전 `^0.9.0`) 소스(`node_modules/@supabase/ssr/dist/main/utils/chunker.js`, `cookies.js`) 직접 읽어 실제 쿠키 포맷 확인: `sb-<project-ref>-auth-token` 이름 + `base64-` 접두사 + `base64(JSON.stringify(session))` 값 (3180자 초과 시 `.0`,`.1`... 청크 분할 — 이번 세션은 2651자로 단일 쿠키). 이 쿠키를 curl로 `/dashboard`에 직접 실어 200 응답 + 실제 QA 사업장명(`부하테스트카페`)이 HTML에 포함되는지 확인해 진짜 인증된 렌더링임을 검증.
3. **부하테스트 실행** — 서버(iwinv, `/var/www/aeolab/venv`)에서 Python aiohttp로 동시성 5 → 10 → 20 → 30 → 50 → 80 단계적 램프. 각 "동시 사용자"는 `GET https://aeolab.co.kr/dashboard` 1회 요청(실제 브라우저의 최초 페이지 로드에 해당).
4. **서버 리소스 동시 관찰** — 부하테스트 진행 중 `free -m`, `ps -eo pid,pcpu,pmem,comm --sort=-pcpu`를 병행 스냅샷.
5. **정리** — 테스트 후 QA 사업장 DELETE(연쇄삭제) + QA 계정 DELETE, 둘 다 재조회로 0건/404 확인. 서버 `/tmp`의 임시 스크립트·쿠키 파일 전부 삭제.

## 4. 핵심 발견 — 병목은 vCPU2 박스가 아니라 Supabase

30명(p50 4.95s)과 50명(p50 34.72s) 사이에서 응답시간이 급격히 무너지는데, 그 순간 CPU/RAM은 유휴 상태 — **로컬 서버의 연산 능력이 병목이 아니라는 뜻**.

원인으로 유력한 것: 대시보드 1회 로드가 `frontend/app/(dashboard)/dashboard/page.tsx`에서 **약 10개의 병렬 Supabase 쿼리**(사업장·스캔결과·경쟁사·점수이력·벤치마크·최신가이드·오늘스캔횟수·행동로그·갭분석·사진가이드·블로그인용)를 동시에 던짐. Supabase JS 클라이언트는 PostgREST 기반 HTTP 호출이라 로컬에 "커넥션"을 쥐고 있는 게 아니라 **Supabase Cloud 쪽 처리량/큐잉**에 의존 — 동시 사용자가 늘수록 Supabase 인프라(Free Tier)에서 요청이 정체되며 우리 서버는 그저 응답을 기다리기만 함(I/O 대기, CPU 소모 없음). 에러 없이 지연시간만 치솟는 관측 패턴과 일치.

> ⚠️ 이 발견은 CLAUDE.md의 기존 "vCPU/RAM 업그레이드 시 `PLAYWRIGHT_MAX_CONCURRENCY` 상향 검토" 논리와는 **별개 축**임. Playwright/워커=1 이슈는 CPU·RAM 제약이 맞지만, 페이지 동시 접속 성능 저하는 CPU·RAM과 무관하게 Supabase 쪽에서 발생.

## 5. 결론 및 실무 판단 기준

- **동시 접속 10~30명**: 응답 3~9초대 — 느리지만 사용 가능한 수준
- **동시 접속 40~50명 부근**: 응답 30초 이상으로 붕괴 — 실사용에선 사실상 장애
- **서버 스펙(vCPU/RAM) 업그레이드로는 이 한계가 해결되지 않음** — 이미 리소스가 남아돌기 때문. 해결하려면:
  - Supabase 유료 플랜 전환(처리량/커넥션 한도 확대), 또는
  - 대시보드 쿼리 통합/캐싱으로 페이지 1회 로드당 Supabase 왕복 횟수 자체를 줄이기
- BEP 목표(구독자 20명)가 정확히 같은 순간에 대시보드를 열 가능성은 실제로는 낮음(스캔은 대부분 야간 스케줄러 배치라 사용자 간 실시간 충돌이 드묾)이나, "페이지 동시 접속 몇 명까지"를 정량적으로 묻는다면 **현재 구조의 실질적 안전선은 약 30명**

## 6. 잔여 과제 (향후 트리거)

- 이번 QA 계정은 **빈 상태(스캔 데이터 없음)** 기준 테스트 — 실제 스캔 데이터가 채워진 대시보드(경쟁사 차트, 히스토리 그래프 등 더 무거운 렌더링 포함)는 별도 실측 필요. 다만 병목이 "Supabase 왕복 횟수"라는 결론상 방향은 동일할 것으로 판단
- 구독자가 늘어 실제로 동시 접속이 잦아지면(50명 도달 시점과 별개로, 실사용 트래픽 패턴 관찰 필요) 위 재현 절차(§2)로 재검증 권장 — 이번 세션에서 스크립트는 삭제했으므로 재현 시 이 문서의 절차를 그대로 따라 재작성
- Supabase 유료 플랜 전환 여부는 사용자 결정 필요(비용 대비 효과) — 지금은 트리거 미충족(실사용 동시접속이 관측된 적 없음)이라 조치 보류가 합리적

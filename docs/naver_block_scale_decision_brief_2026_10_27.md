## 2. 과제 02-1 — 유료 IP 우회: 구현하지 않음, 권장 결정

**권장: 지금은 켜지 않는다.** 근거 세 가지.
1. **필요성 증거가 없다.** 확인된 차단은 1건(10-27, 서버에서 플레이스 약 65~70페이지를 수 분 안에 연속 요청). 원인이 "IP"가 아니라 "속도·패턴"일 가능성을 배제하지 못했다. 속도 기준을 새로 넣었으므로, 그 아래에서도 차단이 나는지 먼저 봐야 한다.
2. **법적으로 가장 민감한 결합 지점.** 쟁점은 IP 변경 단독이 아니라 쿠키 로그인 + 자동화 은닉 + IP 로테이션의 결합(`naver_scraping_legal_risk_assessment_v1.0.md`). 변호사 자문 전 활성화는 문서가 금지(§7).
3. **구독자 0명 단계에서 비용·위험만 생긴다.**

**기술적으로는 가능하다**(코드 지원, 과거 Decodo 가동 실측 있음). 켠다면 절차: 업체 실결제가 재확인 → 한국 주거용 프록시 → **iwinv 콘솔 아웃바운드 포트 등록**(두 번 재발한 원인) → `backend/.env`(루트 `.env` 아님)의 `NAVER_PROXY_LIST` → `pm2 restart aeolab-backend --update-env` → 로컬 대조 테스트.

### 재검토 트리거 (이번에 만든 사건 기록으로 판정 가능)
`naver_block_events`에서 다음 중 하나가 관측되면 02-1을 다시 연다.
- 속도 기준 아래(시간당 120페이지 미만)에서 `block` 사건이 발생 → 차단 기준이 속도가 아닐 가능성

- 서버 IP 차단이 24시간 이상 지속

## 3-5. 추가 구현 (2026-10-28, 사용자 요청 "경쟁사 분산 최적화·속도 제한 최적 구현")

### ① 경쟁사 요일 분산은 최적화되어 있지 않았다 → 방식을 교체
- **해시 배정(md5 % 7)의 쏠림(시뮬레이션 2000회)**: 사업장 20곳이면 최대일이 균등(3곳)보다 평균 5.3곳(1.78배, 용량 44% 손실), 10~50곳 구간에서 27~38% 손실. 하필 일일 상한에 걸리는 구간.
- **요일을 매일 다시 계산하는 균형 배정은 위험**: 사업장·경쟁사 수가 바뀌면 배정이 바뀌어 한 주를 건너뛸 수 있다 → 채택하지 않음.
- **채택: "마지막 관측이 오래된 사업장부터 + 일일 예산 + 주간 pacing"**(`scan_scheduling.select_stale_first`, 플래그 `NAVER_COMPETITOR_STALE_FIRST`, 서버 켬). 기준 시각은 경쟁사 행의 `naver_place_last_synced_at`(실제 관측 시각). 요일 약속이 없어 사용자 문구 변경 불필요.
- **중간 실패 2건(시뮬레이션이 잡음)**: ① "스스로 분산된다"는 가설이 거짓 — 예산이 주간 평균보다 크면 일별 240·240·120·0·0·0으로 3일에 몰림 → 하루 처리량을 `전체 페이지 ÷ 6일`로 제한하는 pacing 추가. ② pacing을 엄격히 자르면 한도(50)가 한 곳 크기(30)의 1.67배라 한 곳씩만 들어가 8곳+사업장 변경 시 간격 13일 → pacing은 "넘을 때까지 담되 마지막 한 곳은 허용"하는 부드러운 한도로.
- **결과(예산 252, 곳당 30페이지)**: 20곳 일 최대 120페이지(기존 고정 화요일 600, 해시 평균 최대일 159), 간격 7일. 8곳+변경 시 8일. 100곳은 예산 한계로 13~14일(구조적 한계, 굶는 곳 없음).
- **enrich**: 같은 `sync_competitor_place`를 지역 인자만 달리해 호출하고, 캐시가 만료되면 네이버를 새로 크롤한다("요청 없이 보강"은 캐시 유효 시에만 사실). 오래된 순서 모드에서는 기존 요일(목)을 유지하되 **캐시가 유효한 경쟁사만** 처리(`cache_still_valid`).
- **드라이런(서버 실데이터, 네이버 접속 없음)**: 후보 사업장 2곳(둘 다 0.9일 전 동기화) → 오늘 밤 선택 0건, 다음 동기화는 두 방식 모두 11-03경. 켜도 오늘 밤 동작 동일.

### ② 속도 제한 — 정기 잡이 윈도우를 채워 사용자 요청이 거절되던 구조를 수정
- 기존: 배치·사용자 요청이 같은 윈도우(1분12·10분30·1시간120)를 똑같이 쓰고 `batch`는 대기 한도만 달랐다. 배치가 윈도우를 채우면 사용자 요청은 15초 대기 한도를 넘겨 `naver_rate_limited`로 거절.
- 변경: 배치 호출은 각 윈도우의 **0.7배만** 사용(`batch_rate_ratio`, 기본은 일일 배치 몫 비율과 동일, `NAVER_BATCH_RATE_RATIO`로 조정). 사용량 집계는 배치·사용자·외부 기록 전체. 사용자 요청은 남은 30% 몫에서 즉시 처리. `/admin/naver-access`의 `rate.windows[].batch_max`로 확인.
- 값 0.7은 **근거 없는 제안값**. 기존 테스트 2개(`batch=True` 기본에서 전체 한도 가정)는 의도된 동작 변경이라 비율 1.0으로 고정해 의미를 유지하고, 기본 동작은 새 테스트로 검증.

**구매 판단 기준(시험이 아니라 사건 기록):** 7일 카나리 시험은 구조상 불가능하다 — 프록시 설정이 전역이고, 카나리(`rank_canary_job`)는 순위 건강 점검이며 순위 모듈은 프록시를 쓰지 않고, 지금까지 차단이 1건뿐이라 효과를 입증할 기준선이 없고, 프록시 실패 시 직접 접속으로 조용히 폴백(`__init__.py` 회로)해 결과가 섞인다. 그래서 `naver_block_events`에서 ① 속도 기준 아래(시간당 120페이지 미만)에서 차단 ② 같은 주 2회 이상 ③ 24시간 이상 지속 중 하나가 나오면 구매한다. 저장된 네이버 AI 브리핑 스캔 338건(4~10월)에는 CAPTCHA 감지가 0건(프록시 유무 무관)이고 10-27 차단은 플레이스 페이지(직접 접속, 속도 급증)였다.

**어느 업체:** Decodo(한국 주거용) — 2026-08-05에 우리 환경에서 연결·측정 성공(`captcha_detected=false`, 차단 방지의 증명은 아님), 서버에서 `gate.decodo.com:7000` TCP 연결 성공(2026-10-28, iwinv 방화벽 등록 유지 확인; 10001은 막힘). Webshare는 무료 플랜에 한국 프록시가 없었고(407 장기 실패) 한국 주거용 제품·가격은 미확인이며 새 포트 등록이 필요하다. 가격은 8월 기록(3GB $11.25/월)뿐이라 **결제 페이지에서 재확인**(광고가와 실제가가 두 번 달랐음). 트라이얼은 연결 권한이 없었고 결제 후에도 트라이얼·유료가 병기돼 트래픽 라우팅을 따로 확인해야 했다.

**적용 순서(구매 후):** ① 대시보드에서 유료 플랜 활성 확인 → ② `backend/.env`(루트 `.env`는 백엔드가 안 읽음)에 `NAVER_PROXY_LIST=gate.decodo.com:7000:user-<이름>-country-kr:<비밀번호>`와 **`NAVER_PROXY_SCOPE=place`**(10-27 차단이 난 플레이스 쪽만 먼저) → ③ `pm2 restart aeolab-backend --update-env` → ④ `/admin/naver-access`의 `proxy`에서 `configured:true`, `usage.place.proxy` 증가, `usage.*.reasons`의 `circuit_open`(직접 폴백) 여부 확인 → ⑤ 문제가 있으면 `NAVER_PROXY_LIST`를 비우거나 SCOPE를 바꾸고 재시작(되돌리기 한 줄). 쿨다운(회로 차단) 중에는 프록시로도 접속하지 않는 원칙 유지.

**한계:** 키워드 순위 측정은 항상 서버 IP 직접 접속(미연결) — 순위 쪽 차단이 문제가 되면 `naver_keyword_rank.py`의 `chromium.launch`에 프록시 인자를 붙이는 별도 작업이 필요하다. 사용 기록은 프로세스 시작 이후 기준(재시작하면 0)이며 "회선 선택 횟수"이지 실제 전송량이 아니다(전송량은 기존 `bandwidth_tracker`).

## 4. 검증 수준 (정직한 표기)
- **확인한 것(코드·실행)**: 위 5개 커밋의 테스트(전체 pytest 348 통과, 변이 검증으로 테스트가 결함을 실제로 잡음), 서버 md5 일치 후 배포, 서버 테스트 통과, health 정상·에러 없음, 체험 가게 찾기 라이브 화면.

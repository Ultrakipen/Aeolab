현재 NHN Cloud에 승인된 템플릿은 **6개**(공식 5종 + v3.1 공지 1개)이며, 다음 3개 카테고리로 정리됩니다.

| 구분 | 개수 | 조치 |
|------|------|------|
| **제외(사용 중지)** | 1개 | AEOLAB_SCORE_MODEL_01(추정 코드명 — §5-C 참조) — 목적 달성, 재사용 불가 |
| **재신청(문안 교체)** | 4개 | AEOLAB_SCORE_01·CITE_01·COMP_01(변수 누락, §2/§5-A), NEWS_01(코드와 변수 불일치) |
| **신규 추가 필요** | 최소 8개 | 코드는 이미 구현됐으나 승인 목록에 없는 발송 경로 |

**⚠️ 확인 필요(사용자 직접 확인 요망, §5-B에서 톤 하향):** 코드에서 `AEOLAB_NOTICE_01`이라는 템플릿 코드로 구독 만료·결제 실패·서비스 정지·해지 완료·가격 인상 사전고지·리뷰 인박스 알림 등 **최소 14개 발송 경로**(§3-A + §5-B에서 재확인한 `send_text()` 6곳 포함)가 서로 다른 자유 텍스트를 보내는 중인데, 이 템플릿은 제공해주신 승인 목록 6개 안에 없습니다. 다만 이 발송 경로들은 모두 `_send_raw()`를 거치며 `resendType=SMS`(카카오톡 실패 시 문자 자동 대체발송) 옵션이 걸려 있어, 설령 알림톡 자체가 거부되더라도 **문자로는 도달했을 가능성**이 있습니다 — "조용히 실패"보다는 "의도와 다른 채널(SMS)로 새고 있을 가능성"이 더 정확한 표현입니다. 두 경우 모두 NHN Cloud 콘솔에서 `AEOLAB_NOTICE_01` 발송 채널별(알림톡/SMS) 이력을 확인해야 확정됩니다.

**제외 근거:**
- 문안이 "v3.1 업그레이드" 사실 하나에 고정돼 있어 다른 목적으로 재사용 불가 (일회성 공지 템플릿)

- 코드 내부 문안(`KAKAO_TEMPLATE_BODY`, `score_model_migration_notice.py:41`)도 승인된 실제 문안과 문구가 다름 — 어차피 재사용하려면 다시 심사받아야 함

**조치:** 비즈센터에서 "사용 중지"(카카오 정책상 완전 삭제가 아닌 비활성화만 가능한 경우가 많음) 처리하고, 관련 코드(`score_model_migration_notice.py`)는 향후 유사한 "모델 버전 전환 공지"가 또 필요할 때 참고용으로만 남겨두는 것을 권장합니다. 급하지 않으면 코드 삭제 없이 문서화만 해도 무방합니다.

## 3. 신규 추가 필요 — 코드는 있는데 승인 목록에 없는 것들

### 3-A. 최우선 확인 — 다목적 "AEOLAB_NOTICE_01" 재설계

`kakao_notify.py`에서 `template_code="AEOLAB_NOTICE_01"`로 **9곳**이 서로 다른 자유 텍스트를 보내고 있습니다:

| 메서드 | 발송 시점 |
|--------|----------|
| `send_expire_warning()` | 구독 만료 D-7 |
| `send_payment_failed()` | 자동결제 실패 |
| `send_suspended()` | 서비스 정지 |
| `send_payment_recovered()` | 유예 중 결제 재성공 |
| `send_notice()` | 관리자 임의 공지 |
| `send_price_increase_notice()` | 첫 달 할인 종료 D-3 사전고지 (전자상거래법 대응) |
| `send_subscription_cancelled()` | 해지 완료(환불 여부 2분기) |
| `send_gap_card_url()` | 주간 갭 카드 공유 |
| `send_v31_migration()` | (§1에서 폐기 대상과 중복 — 정리 시 제거) |

알림톡은 **승인된 고정 문안**을 기반으로만 발송되므로, 이렇게 매번 다른 텍스트를 하나의 템플릿 코드로 보내는 방식은 정상적으로는 성립하지 않습니다. 아래 두 가지 중 하나로 정리가 필요합니다.

**옵션 A(권장) — 목적별 전용 알림톡으로 분리 신청:**

## 5. 자체 재검증(오판·누락 점검, 2026-07-20)

사용자 요청으로 1차 보고 내용을 다시 코드와 대조하며 반증을 시도한 결과:

### 5-A. 누락 발견 — CITE_01·COMP_01 `#{확인일시}` (§2-C, §2-D로 반영)

1차 분석 단계에서 이미 이 두 템플릿의 변수 불일치를 확인했었는데, 최종 보고서 작성 시 SCORE_01·NEWS_01만 적고 CITE_01·COMP_01은 빠뜨렸습니다. 재검증 과정에서 코드(`kakao_notify.py:205`, `:219`)를 다시 grep해 확인하고 §2-C/§2-D로 추가했습니다. 이 둘은 `_send()`(SMS 대체발송 없음)를 쓰기 때문에 §3-A의 NOTICE_01 계열보다 오히려 실패 시 영향이 더 직접적입니다 — 결과적으로 원래 "결제/구독 쪽이 더 급하다"고 판단했던 우선순위가 부정확했을 수 있습니다. **AI 인용·경쟁사 알림도 결제 알림만큼 시급하게 확인이 필요합니다.**

### 5-B. 과장(오판 가능성) 발견 — NOTICE_01 "조용히 실패" 단정

1차 보고서는 `AEOLAB_NOTICE_01`이 승인 목록에 없다는 근거로 "결제 실패·구독 정지 알림이 조용히 실패 중일 가능성이 있다"고 썼습니다. 재검증 중 `_send_raw()`(`kakao_notify.py:645`) 코드를 다시 보니 `resendType: "SMS"`가 명시돼 있어, 카카오톡 알림톡 전달이 거부되더라도 NHN이 SMS로 자동 대체발송할 가능성을 검토하지 않았습니다. 이 가능성을 빠뜨린 채 "실패"라고만 표현한 것은 근거가 불완전한 상태에서 더 나쁜 시나리오 쪽으로 단정한 것 — 실제로는 "카카오톡 대신 문자로 새고 있을 가능성"이 더 정확한 설명입니다(§0에 반영). 다만 이것도 추정입니다 — `resendType=SMS`가 "템플릿 자체가 없음/미승인" 상황에서도 동작하는지, 아니면 "정상 승인된 템플릿인데 수신자가 카톡 미가입자인 경우"에만 동작하는지는 NHN 공식 문서로 확인하지 못했습니다. **여전히 콘솔에서 실측 확인이 필요하다는 결론 자체는 유지됩니다.**

추가로, `send_text()`(`kakao_notify.py:593`)가 `jobs.py`에서 **6곳**(리뷰 인박스 신규 알림 포함)에서 별도로 호출되는데 1차 보고서의 "9곳" 집계에서 완전히 빠졌습니다 — NOTICE_01 의존 범위는 최소 14~15곳으로, 1차 보고서보다 더 넓습니다(§0에 반영).

### 5-C. 확인 안 된 가정 — "AEOLAB_SCORE_MODEL_01" 코드명

§1에서 제외 대상으로 지목한 6번째 템플릿("이용 서비스 업데이트 안내")의 실제 승인 코드명은 사용자가 주신 파일에 표시되어 있지 않습니다(`AEOLAB_ACTION_01`만 명시적으로 라벨이 있었음). `AEOLAB_SCORE_MODEL_01`이라는 이름은 `score_model_migration_notice.py`의 계획 코드에서 가져온 추정치이며, 그 파일의 실제 문안 초안조차 승인된 문안과 문구가 다릅니다. **"제외해야 한다"는 결론(목적 달성·재사용 불가)은 문안 내용만으로 판단 가능해 유효하지만, 코드명 라벨은 비즈센터에서 직접 확인 후 정정이 필요합니다.**

### 5-D. 검토했지만 문제 없음으로 확인된 것

- `AEOLAB_ACTION_01`: 승인 문안(`#{사업장명}`, `#{할일목록}`)과 `send_action_items()`가 정확히 일치 — 재신청 불필요

최초 점검 시 `send_growth_stage_upgrade()`가 `#{현재순위}`에 `track1_score` 원점수를 그대로 넣는 설계 결함으로 판단했으나, 실제 호출부(`jobs.py:918-922`)를 대조한 결과 더 근본적인 문제를 발견:

- 함수 시그니처: `send_growth_stage_upgrade(self, phone, biz_name, prev_stage, curr_stage, track1_score: float)`
- 실제 호출: 5번째 인자로 `current_stage.this_week_action`(`gap_analyzer.py:294` 등에서 정의된 **문자열**, 예 "스마트플레이스에서 사진 5장·영업시간·전화번호 완성하기")을 전달
- 함수 내부는 `str(int(track1_score))`를 실행 → 문자열에 `int()`를 적용해 매 호출마다 `ValueError` 발생
- 호출부의 `try/except`(`jobs.py:923`)가 예외를 삼키고 `logger.warning`만 남김

**결론:** GrowthStage 업그레이드 알림톡은 지금까지 정상 발송된 적이 없을 가능성이 높습니다. SCORE_01은 승인된 살아있는 템플릿이라 이 경로가 유일하게 "즉시 발송 가능했던" 것이었는데, 애초에 예외로 막혀 있었습니다. §3-B의 기존 서술("전용 문안 필요")은 방향은 맞았으나 원인 진단이 부정확했으므로 이 절로 대체합니다.

### 6-C. 확인 완료 — 문제 없음

`send_score_change()`(SCORE_01 본연), `send_scan_complete()`(SCAN_01), `send_weekly_score_report()`, `send_competitor_change()`(COMP_01)는 등급/순위 텍스트만 사용 — 원점수 노출 없음. `send_ai_citation()`·`send_action_items()`·`send_market_news()`는 애초에 점수 데이터를 다루지 않음.

## §1. 점검 원칙 (먼저 읽을 것)

1. **루브릭 고정 + 페이지별 분할** — 6페이지 × 5축을 한 번에 "다 봐줘"로 묻지 말 것. §3 5축 0~10점으로 채점하고 ❌만 수정.
2. **근거 + 반증 동시 제시** — "P0/P1이다" 보고 직전, **단정 근거 file:line 1줄 + 반증 시도 1줄**을 본 적이 있어야 함 (CLAUDE.md §"문제 분류 검증 의무").
3. **실증 우선** — 더미숫자·`text-xs`는 grep 카운트로, 레이아웃은 라이브 `https://aeolab.co.kr` PC+모바일 스크린샷으로 실증. 추측 보고 금지.
4. **종료 기준** — 5축 전부 ✅면 즉시 중단. 취향 제안 금지. 제안은 반드시 ❌항목에 매핑 (CLAUDE.md `feedback_dashboard_inspection_standard`).
5. **서버 우선 배포** — 수정 시 `md5 선확인 → scp → npm run build → pm2 restart aeolab-frontend → 라이브 검증 → git 커밋` 순서 준수.
6. **솔직함(정직 보고) — 필수** — 점검·수정·배포·테스트 전 과정에서 **있는 그대로 보고**한다. 사용자가 듣기 좋은 결론으로 포장하거나 자화자찬하지 말 것.
   - **거짓 "완료" 금지** — 실제로 안 한 것을 했다고, 실패를 성공이라고 보고 금지 (CLAUDE.md §"에이전트 보고 검증 의무")
   - **개선사항·문제는 불편해도 먼저 알린다** — 발견한 결함·한계·미흡·확신 없는 부분을 숨기지 말고 명시. "잘 됩니다" 대신 "A는 됨, B는 미확인, C는 결함"으로 구분
   - **모르면 모른다고** — 확인 못 한 항목은 "미확인"으로 표기, 추측을 사실처럼 쓰지 않음
   - **자기 작업도 비판적으로** — 내가 만든 문서·코드·수정도 결함을 적극적으로 찾아 보고(이 문서 §"완성도 자체점검"이 그 예)
   - **테스트 실패·회귀는 즉시 그대로 보고** — 통과한 것처럼 넘기지 않음

## §3. 5축 점검 루브릭 (각 페이지를 0~10점 채점, 만점 50)

### 축 A — 사실적·실질적 구현
- 표시 데이터가 **실측**인가? 더미/임의 추정 숫자 노출 **0건**인가?
- **[회귀 점검] 점수 수치 → 텍스트 레이블 개선이 이미 적용됨** (2026-06 완료). 숫자(`72점`·`track1Score:68`)가 다시 노출되지 않는지 확인. 허용: `양호`·`보통`·`주의 필요`·`업종 상위권` 등 의미 레이블, 진행률 바(숫자 레이블 없이). (CLAUDE.md §"점수 표시 원칙", `feedback_score_display_text_only`)
- API 실패 시 `0`/`N·A`로 폴백하는가, 허위 수치를 만들지 않는가?
- 버튼·생성기(소개글/태그/리뷰답변/FAQ)·필터가 실제 백엔드 엔드포인트에 연결돼 동작하는가?
- 빈 상태에서 "아직 데이터 없음 — 첫 스캔 후 표시" 안내가 뜨는가?
- 업종 라벨 영문 폴백(restaurant→음식점 누락) 없는가? (`reference_category_label_leaf_fix`)

### 축 B — PC/모바일 텍스트 크기·구조
- 본문 `text-xs` 잔존 grep 카운트 (권장 `text-sm` 이상)
- PC/모바일이 **별도 레이아웃**으로 알맞게 분기되는가 (한 화면 강제축소 아님)
- 모바일 가로 스크롤·텍스트 잘림·버튼 겹침 0건
- 페이지 패딩 반응형(`p-4 md:p-8`)인가

### 축 C — 이해도·업종별 적합성
- 비전문가(소상공인)가 용어 설명 없이 이해 가능한가
- **ACTIVE/LIKELY/INACTIVE 업종별 분기**가 알맞은가
  - INACTIVE 업종에 네이버 AI 브리핑 **단정 노출 금지** (글로벌 AI 중심 안내)
  - 프랜차이즈 제외 처리 정상인가 (`getBriefingEligibility(category, is_franchise)`)
- AI 정보탭 가이드: AI탭 vs AI 브리핑 **용어 혼동 없는가** (`docs/ai_briefing_vs_ai_tab_clarification_v1.0.md`)

### 축 D — 스크롤·정보 구조
- 위→아래 우선순위(중요 정보 먼저)가 자연스러운가
- 섹션 앵커/아코디언/탭 점프가 끊김 없이 동작하는가 (예: `naver-intro-anchor`)
- 첫 화면(above the fold)이 부정 평결·빈 상태로 시작하지 않는가

### 축 E — 상업 서비스 적합성 (출시 게이트)
- **플랜 게이트** — Basic/Pro/Biz 등 요금제별 노출/잠금이 의도대로인가 (`PlanGate.tsx`). 무료가 유료 기능을 보거나, 유료가 막히는 오작동 없는가
- **결제·전환 동선** — 잠금 → 업그레이드 CTA가 실제 결제/플랜 페이지로 연결되는가
- **면책 문구** — 변동 데이터(키워드 순위·AI 인용·점수)에 "측정 시점·기기·로그인 상태에 따라 달라질 수 있음" 일관 적용. ChatGPT 측정 면책 문구 노출
- **법적·정책 표현** — 과장/허위 보장 없는가 ("반드시 노출"·"100% 보장" 금지). 네이버/ChatGPT 정책 위반 표현 없는가
- **신뢰성** — 베타 후기 placeholder가 실데이터로 교체됐는가, 미검증 기능을 "완료"로 노출하지 않는가

## §5. 보고 형식

각 페이지마다:
```
[페이지명] 종합 X/50
- 축 A 실측구현: N/10 — 근거 file:line / 반증 file:line
- 축 B PC·모바일: N/10 — text-xs 카운트, 스크린샷 첨부
- 축 C 이해도·업종: N/10
- 축 D 스크롤·구조: N/10
- 축 E 상업성: N/10 — 플랜게이트·면책·법적표현 (P0 1건이라도 = 상업 부적합)
발견: P0 n건 / P1 n건 / P2 n건  (각 file:line + 1줄 설명)
미확인: (확인 못 한 항목을 솔직히 명시 — 추측으로 채점 금지, §1.6)
```

전 페이지 ❌ 0건 + 축 E P0 0건이면 "출시 점검 통과" 선언 후 중단. ❌ 있으면 P0→P1→P2 순으로 **§9 배포 절차**(+ §10 최적성·§11 백업·§12 테스트)로 수정.

## §6. 심층 점검 + 오판 최소화 + 재점검 (필수)

> 2026-05-18·06-12 오판 사고(옛 주석·부분 grep만으로 단정) 재발 방지. **모든 발견은 2-pass(발견 → 반증 재점검)를 통과해야 보고 가능.**

### 6.1 심층 점검 — 표면 점검 금지

각 발견 항목은 **코드 → 호출처 → 라이브** 3계층을 직접 본 뒤에만 확정한다.
- **코드 계층** — 대상 `file:line`을 `Read`로 직접 확인 (grep 1줄 결과만으로 단정 금지)
- **호출처 계층** — `grep -rn "<함수/컴포넌트명>"`로 실제 사용처·데이터 흐름 추적 (선언만 보고 "미사용/누락" 단정 금지)
- **라이브 계층** — `https://aeolab.co.kr` PC+모바일 실화면으로 코드 추정과 실제 렌더 일치 확인

### 6.2 오판 최소화 — 단정 직전 반증 1회 의무

"이 항목은 P0/P1 문제다"라고 쓰기 직전, 아래 반증 시도 중 **최소 1개**를 실행하고 결과를 기록한다.

| 단정 유형 | 흔한 오판 원인 | 필수 반증 시도 |
|----------|--------------|---------------|
| "기능 미연결/미동작" | 다른 파일에서 import·호출됨 | 호출처 `grep -rn` 전체 카운트 |
| "더미/허위 수치 노출" | 실측값을 더미로 오인 | 데이터 출처 prop·API 응답 Read로 역추적 |
| "텍스트 너무 작음" | 모바일 전용 분기를 PC로 오인 | 반응형 클래스(`md:`)·별도 모바일 컴포넌트 확인 |
| "업종 분기 오류" | 단일 소스를 안 봄 | `score_engine.py:30` / `userGroup.ts` 실제 값 대조 |
| "점수 숫자 노출(회귀)" | 진행률 바·레이블을 숫자로 오인 | 렌더 문자열이 숫자인지 `scoreLabels` 경유인지 Read |
| "문구 과장/허위" | 사실 문구를 과장으로 오인 | 계층 구분 — 봇차단(사실) vs 콘텐츠영향(별개), `reference_naver_bot_block_vs_content_effect` |

**보고 형식 강제:** `P1 — [근거 file:line] + [반증 file:line, 결과] 문제 확인` (반증 라인 없으면 보고 무효).

### 6.3 재점검 — 수정 후 2차 패스

수정/배포 후 다음을 **다시** 수행해 "고쳤다는 보고"가 사실인지 메인 세션이 직접 검증한다.
1. **재현 재점검** — 1차에서 ❌였던 항목을 동일 절차로 재측정, ✅ 전환 확인 (grep 카운트 0 / 스크린샷 정상)
2. **부작용 재점검** — 수정이 같은 페이지 다른 섹션·다른 5개 페이지에 회귀를 일으키지 않았는지 인접 영역 1회 재확인
3. **서버 반영 재점검** — `ssh ... "grep -n '<핵심패턴>' /var/www/aeolab/<경로>"`로 서버 파일 실반영 1줄 + 빌드 성공 로그 + `pm2 logs --lines 30 --nostream` 에러 0건
4. **드리프트 재점검** — scp 후 `git add/commit` 누락 없는지, 로컬==서버 md5 일치 확인

### 6.4 종료 게이트 (2-pass 통과 시에만 종료)

- 1차 점검 리포트의 모든 P0/P1이 **6.2 반증 라인을 포함**하는가? (없으면 재작성)
- 수정 항목이 **6.3 재점검 4단계를 모두 통과**했는가?
- 둘 다 ✅면 "출시 점검 통과(2-pass 검증 완료)" 선언. 하나라도 ❌면 해당 항목만 루프, 신규 취향 항목 추가 금지.

## §7. 분야별 전문가 패널 점검 + 교차검증 (오판 없는 상업성 판정)

> 제너럴리스트 1명이 4축을 훑으면 전문 깊이가 얕고 자기검증이 안 된다. **각 축을 담당 전문가가 깊게 보고, 다른 전문가가 그 발견을 반증**해야 오판이 걸러진다.

### 7.1 전문가 ↔ 축 ↔ 담당 에이전트 배정

| 전문가 관점 | 담당 축 | 담당 에이전트 | 핵심 권한·기준 |
|------------|--------|--------------|---------------|

### 7.2 교차검증 프로토콜 (오판 차단 핵심)

1. **1차(발견)** — 각 전문가가 담당 축을 §3 루브릭으로 채점하고 발견을 `근거 file:line`과 함께 제출

## §10. 개선 사항 최적성 판단 (5-게이트)

> "최적"은 모호하므로 3가지로 분리해 판단한다. ① 점검 완전성(5축×6페이지=30칸 전부 채점, 스킵 0) ② 발견 정확성(§6 반증+§7 교차검증) ③ **개선 타당성(아래 5게이트)**.
> **핵심 원칙: 최적 = 완벽이 아니라 "상업 적합"**. "더 좋게 만들 수 있는데"는 무한 루프 — 출시 게이트와 분리.

### 10.1 개선 5-게이트 (전부 ✅여야 "최적 수정")

| 게이트 | 판단 질문 | ❌일 때 |
|--------|----------|---------|
| 1. 필요성 | ❌난 루브릭 항목에 **매핑**되나? | 매핑 안 되면 취향 → **버림** |
| 2. 최소성 | 그 항목 고치는 데 **필요한 라인만** 건드리나? | 불필요 리팩터링 동반 → 범위 축소 |
| 3. 비교우위 | 같은 효과의 **더 단순/안전한 대안**이 있나? | 대안 1~2개 비교 후 저비용·저리스크 채택 |
| 4. 무부작용 | 같은 페이지 다른 섹션·나머지 5페이지에 **회귀** 없나? | 인접 영역 재점검(§6.3) |
| 5. 가치보존 | 독점 데이터·교육·모바일 UX 가치를 **제거 안 하나**? | 중복처럼 보여도 가치 있으면 유지 |

### 10.2 최적성 보고 형식

```
[수정 X] ❌루브릭: 축 B "review-inbox 모바일 버튼 겹침 P1"
  G1 필요성✅(P1매핑) G2 최소성✅(div 1곳) G3 비교우위✅(flex-wrap vs 별도컴포넌트→flex-wrap)
  G4 무부작용✅(PC 동일) G5 가치보존✅
  검증: 수정 후 모바일 스크린샷 겹침 0 (before/after) → 항목 ✅ 전환
```

### 10.3 종료 기준 (최적 도달 선언)

- **축 E(상업성) P0 = 0 + 나머지 축 ❌ = 0** → "최적 도달, 상업 적합"으로 **중단**
- 그 이상의 "더 좋게"는 **개선 백로그로 분리** — 출시 게이트에 섞지 않음

## §11. 파일 수정 전 백업 의무 (필수 — 건너뛰기 금지)

> 어떤 파일이든 **편집/덮어쓰기 전에 반드시 백업**한다. 구버전 덮어쓰기·잘못된 수정 시 즉시 복원하기 위함.

### 11.1 백업 순서 (편집 직전)

```
1. md5 선확인(§9.1-0)으로 로컬==서버 일치 먼저 확인. 다르면 서버가 진실 → scp 서버→로컬 받은 뒤 백업
2. 로컬 백업    cp <파일> <파일>.bak_<YYYYMMDD_HHMM>   (또는 docs/_backups/ 등 백업 폴더로)
3. 서버 백업    ssh root@115.68.231.57 "cp /var/www/aeolab/<경로> /var/www/aeolab_predeploy_backups/<파일명>.bak_<ts>"
4. 백업 생성 확인(ls)한 뒤에만 편집·scp 진행
```

### 11.2 규칙

- **로컬·서버 양쪽 모두 백업** (한쪽만 하면 다른 쪽 사고 시 복원 불가)
- 타임스탬프 포함 파일명으로 덮어쓰기 방지 (날짜·시각 값은 명령 실행 시점으로)
- 백업 위치: 서버는 기존 `/var/www/aeolab_predeploy_backups/` 활용, 로컬은 동일 폴더 `.bak_<ts>` 또는 별도 백업 폴더
- 수정·배포·검증 완료 + §6.3 재점검 통과 후, 불필요해진 임시 `.bak` 정리(최근 것만 보존)
- ⚠️ deploy.yml의 predeploy tar 가드는 **git reset 배포 경로**용 — **scp 직접 배포는 자동 백업 안 됨** → 이 §11 수동 백업이 유일한 안전망

### 11.3 복원(롤백) 절차 — 테스트 실패·회귀 발생 시

```
1. 로컬 복원   cp <파일>.bak_<ts> <파일>   (또는 git: git checkout -- <파일> / git restore <파일>)
2. 서버 복원   ssh root@115.68.231.57 "cp /var/www/aeolab_predeploy_backups/<파일명>.bak_<ts> /var/www/aeolab/<경로>"
3. 프론트 재빌드+재시작  ssh ... "cd /var/www/aeolab/frontend && npm run build" → pm2 restart aeolab-frontend
4. 라이브 재확인(§8 브라우저)으로 정상 화면 복귀 확인 → 원인 분석 후 §10 재판단
```
- §12 테스트에서 **회귀가 잡히면 무리하게 추가 수정하지 말고 먼저 롤백**해 라이브를 정상화한 뒤 원인 분석 (라이브 안정 최우선)

## 1. 설계 원칙: 기존 기능을 "보완"하는가, "독자"인가

사용자 지시: 기존 구현을 참고해 **보완 기능인지 독자 기능인지 구분**해 설계.

| 구분 | 의미 | 규칙 |
|---|---|---|
| **보완** | 기존 화면·데이터·함수를 재사용하고 빈 곳만 채움 | 기존 테이블/컴포넌트를 먼저 확장. 새 구조를 만들지 않는다. |
| **독자** | 기존에 없는 측정/입력 경로 | 기존 점수·알림·플랜 로직과 **분리**한다(§4-3: 점수에 넣지 않음). |

## 2. 외부 조사 요약 (AI 검색 노출 진단 업계 표준과 AEOlab 위치)

출처 신뢰 등급: 대부분 벤더·SEO 블로그(2차). **방향성 참고용이며 수치는 단정하지 않는다.**

### 2-1. 업계 표준 방법론
- 고정 프롬프트 세트를 여러 엔진에 반복 실행하고 언급·인용·감정·점유율(SOV)을 기록(HubSpot, position.digital, Foglift 등). 반복 3~5회/프롬프트가 흔한 권장.
- 변동 원인은 반복 샘플링 외에 **프롬프트 표현, 모델, 질의 언어** (arXiv 2607.13304, 프리프린트 — 동료심사 여부 [미확인]).
- 비율은 이항 비율이므로 **Wilson 구간** 권장(Wald는 작은 n에서 부정확, 해당 문장은 검색 결과가 아니라 일반 통계 지식).
- 모델 버전·프롬프트 세트·언어·날짜를 매 실행에 기록.
- **AEOlab 현황 [확인]**: 50/100회 표본, 질의 변형 균등 분배, Wilson 구간(`chatgpt_scanner.py:130`), 비유도형 추천 프로브(`:247`), 실패 표본은 분모 제외. **측정 방법론은 업계 일반 수준 이상.** 부족한 건 측정이 아니라 "측정 결과로 사장님이 할 수 있는 일".

### 2-2. 로컬 사업장 정보 정확도 (이 설계의 근거)
- SOCi 2026 연구를 인용한 Search Engine Land 요약: 사업 정보 정확도 ChatGPT·Perplexity ≈ 68%, Gemini ≈ 100%(Google 지도 사용). **원 보고서는 찾지 못함 [미확인]**, 벤더 간 수치도 상충(93% vs 56% 등) → **방향성만**.
- 가장 흔한 오류는 전화번호, 그다음 웹사이트·이름(Insites). 약 1/60은 다른 가게/경쟁사를 설명(같은 출처).
- 출처 경로(벤더 주장, 방향성): Google AI Mode는 비즈니스 프로필, AI Overviews는 웹사이트·스키마, ChatGPT는 서드파티 리스팅·일관성. ChatGPT 로컬 정보에 Foursquare 비중이 크다는 주장(60~70%)은 **독립 측정이 아님**. Yelp는 한국과 거의 무관 → **한국 소상공인에게 그대로 적용 불가**, 한국 상황 검증은 **[미확인]**.
- 실무 권고(여러 출처 일치): ChatGPT를 직접 고칠 수 없고, **출처가 되는 곳의 정보를 고치고 채널 간 정보를 일치**시킨다.

### 2-3. 비용 관련 [외부, 2차]
- Gemini 검색 접지(Grounding with Google Search): 2.5 계열 $35/1,000 프롬프트, 무료 1,500건/일(경쟁 벤더 글 — 공식 가격 페이지 미확인). → Phase 3 전에 공식 확인.
- Google Places API(신): Essentials $5·Pro $17·Enterprise $20 / 1,000건, 무료 월 한도 있음. **영업시간·전화가 어느 등급인지 출처 간 상충 → [미확인]**. 그래서 구글 쪽은 지금처럼 Serper(체험 전용 구현 있음)를 우선 검토.
- Google Business Profile Performance API: 소유자 OAuth + Google 승인 전 쿼터 0(비공식 가이드). 한국 소상공인의 GBP 사용률 [미확인] → **보류**.

### 2-4. 네이버 쪽 [외부]
- 스마트플레이스 통계 엑셀 내보내기 기능 유무는 검색으로 **확인하지 못함 [미확인]**. 그래서 E(스크린샷)는 "공식 내보내기가 있으면 그쪽이 우선"으로 설계.
- 경쟁사 중 이 기능(AI 답변의 사실 오류 점검)을 이미 제공하는 곳이 한국에 있는지는 **확인하지 못함 [미확인]**. 해외는 별도 소형 도구(Apify의 AI Fact-Check 등)가 존재 — 즉 "대형 가시성 도구의 핵심 기능"은 아니며 틈새다.

## 3. 현재 코드에서 확인한 제약 (설계에 직접 영향)

1. **[확인] 정답지가 없다.** `businesses`에는 주소·전화·웹사이트만 있고 영업시간·메뉴·가격대 컬럼이 없다(스키마 grep). 영업시간은 JSON-LD·소개글 생성 때 요청 인자로만 받고 저장하지 않는다. → A가 B의 선행 조건.
2. **[확인] 기존 ChatGPT 프로브는 가게 이름 목록만 반환**(`_recommend_once`, `chatgpt_scanner.py:205-245`)해 설명 텍스트가 없다. 사실 점검에는 **가게를 지목하는 새 프로브**가 필요하다.
3. **[확인] 지목형 질문은 노출 점수에 쓰면 안 된다.** 유도형은 실사업장에서 43~95/100으로 부풀고 환각 인용문이 확인됐다(CLAUDE.md 스캐너 표, 메모리 2026-09-28). → B는 점수·성장 단계·알림에서 **완전 분리**.
4. **[확인] API 호출은 웹 검색 없이 학습 지식으로 답한다.** Gemini 접지는 서버에서 꺼져 있다(`/var/www/aeolab/.env:12 GEMINI_GROUNDING_ENABLED=false`, 주석에 "backend/.env로 옮겨야 켜짐"). ChatGPT도 검색 도구 없이 호출(`chatgpt_scanner.py:48-55`). 학습 컷오프는 2024-06(CLAUDE.md). → **실제 소비자가 검색을 켜고 보는 화면과 다르다.** 면책 필수(기존 ChatGPT 면책 문구 재사용).
5. **[확인] Gemini 표본 4~10/100 실패 이력**(무료 티어 한도, 핸드오프 §7·CLAUDE.md). → 실패는 "AI가 모름"이 아니라 **측정 불가**로 분리(error ≠ false, 지침 8).
6. **[확인] 네이버 접속 0.** B는 OpenAI/Gemini API만 쓴다 → `@naver_batch_job`·`naver_load_model.py` 대상 아님. 네이버가 차단돼도 동작.

## 4. 기능 B 상세 — AI 답변 정확도 점검 (독자)

### 4-1. 사용자에게 주는 가치 (한 문장)
"ChatGPT·Gemini에게 우리 가게를 물으면 무엇이라 답하는지, 내가 입력한 실제 정보와 비교해 **틀린 항목**과 **고칠 곳**을 알려준다."

### 4-2. 위험 3개와 설계 대응 (오판 방지의 핵심)

| 위험 | 시나리오 | 대응 |
|---|---|---|
| **R1 환각을 "AI가 틀렸다"로 보고** | 무명 가게를 물으면 모델이 그럴듯한 전화번호를 지어냄. 이를 "ChatGPT가 틀린 번호를 안내"라고 알리면 실제 소비자(검색 켬)와 다른 경고가 됨 | ① 프롬프트에 "모르면 `known:false`, 확실하지 않은 항목은 null" 명시 ② **같은 값이 N회 중 K회 이상**일 때만 "불일치" 확정(K=3/N=5 **[제안]**), 미달이면 "일관되지 않은 답(확정 아님)" ③ 면책: "검색 기능 없이 AI가 기억하는 정보 기준" |
| **R2 인기 가게가 "AI가 모른다"로 저평가** (지침 9) | 하라식당·어니언 성수 같은 곳이 AI에서 `known:false`로 나오면 "미끼 상품" 인상 | "모름"을 **0점/나쁨으로 표현하지 않음**. 문구: "이 AI는 가게 정보를 기억하고 있지 않아요(검색 사용 시 다를 수 있어요)". 점수 비연결. 라이브 대조는 Phase 0에서 인기 가게 필수 |
| **R3 정답지가 틀림/오래됨** | 사장님이 입력한 영업시간이 변경됐는데 AI가 맞았다면 "AI 오류"로 오표시 | 정답지 각 항목에 `updated_at` 표시, 90일 초과 시 "정보 확인 필요" 먼저 노출 **[제안]**. 판정 문구는 "입력하신 값과 다름"(AI가 틀렸다 단정 안 함) |

### 4-3. 프로브 설계
- **입력**: 가게 이름 + 시·군·구만. **주소·전화·시간은 프롬프트에 넣지 않는다**(정답 누설 방지).
- **출력(JSON)**: `{known, address, phone, hours, representative_menu, website, status}` — `status`: 영업 중/휴업/폐업/모름. 미확실은 null.
- **표본**: 엔진당 5회 **[제안]**(업계 3~5회 권장 + 비용). 온도는 기존과 같은 1.0으로 시작하되 파일럿에서 0.0과 비교해 결정 **[제안]**.
- **엔진**: gpt-4.1-mini, Gemini 2.5 Flash (기존 클라이언트). Perplexity 등 추가 안 함.
- **판정은 코드가 한다(LLM 심판 금지)**:
  - 전화: 숫자만 추출·국가코드 정규화 후 완전 일치. 사장님이 `phone_aliases`(추적번호 등) 등록 가능(Insites: 일부 "오류"는 추적번호).
  - 웹사이트: 등록 도메인(eTLD+1) 비교.
  - 주소: 시·군·구 + 도로명/지번 번호 토큰 비교 → 일치/일부 일치/불일치. **구가 다르면 "다른 가게와 혼동" 별도 표식**(`kakao_visibility._district_token` 재사용).
  - 영업시간·대표메뉴: 파싱 성공 시에만 판정, 아니면 **"확인 필요"로 원문 병기**(자동 불일치 판정 안 함).
  - `status=폐업/휴업`: 최고 심각도지만 K회 규칙 동일 적용(한 번 나온 폐업 답변은 확정 아님).
- **정답지에 없는 항목**은 판정하지 않고 "정답지에 없음 — 입력하면 점검돼요"(빈 값을 0/불일치로 만들지 않음).
- **프랜차이즈 — 포함(결정 10-29, 사용자 지적으로 정정)**: 가맹점도 "지역+가게"이며 지점별 주소·전화·플레이스 ID가 있다. `is_franchise`는 네이버 AI 브리핑 자격 판정 전용 플래그이며(`guide.py:717`, `report.py:142`, `business.py:763`) 정보 점검과 무관해 제외 근거가 없었다. 처리 규칙: ① D는 지점별 `naver/kakao/google_place_id`로 지점을 특정 ② B 프로브는 이름+시군구에 **지점 단서(동·역)** 를 더해 같은 구 안의 동일 브랜드 지점 혼동을 줄임 ③ AI가 **본사 대표번호·브랜드 공통 정보**로 답하면 "불일치"가 아니라 "지점 정보가 아님"으로 분류 ④ 같은 구에 동일 브랜드 지점이 여럿이라 특정이 안 되면 "지점 특정 불가"로 표시(오판정 금지).

### 4-4. 결과 상태(엔진·항목별)
`일치` · `입력값과 다름(N회 중 M회)` · `일관되지 않은 답(확정 아님)` · `AI가 답하지 못함` · `정답지에 없음` · `측정하지 못함(오류)`. **점수·등급·숫자 합산 없음**(점수 표시 원칙 준수).

### 4-5. 데이터 모델 [제안]
```
businesses (보완)
  + fact_sheet        JSONB   -- {hours:{value,source:'owner',updated_at}, closed_days, menu_highlights[], price_note, phone_aliases[], ...}
  (기존 address/phone/website_url 유지 — 별도 복제 금지, 단일 소스)

ai_fact_checks (독자, 신규)

  agree_count, verdict, error TEXT
```

- SQL은 Supabase 수동 실행(`scripts/supabase_schema.sql`에 추가).

### 4-6. API·잡 [제안]

## 5. 기능 A·C·D 상세 (보완)

**A. 가게 정보 원본 (§11-1로 개정: 필수 아님·선택 입력, 외부 사용자에게 노출되지 않는 "정답지")** — 새 화면을 만들지 않고 기존 `BusinessQuickEditPanel`/설정에 입력란 추가. 저장된 값을 **소개글·FAQ·JSON-LD 생성이 자동 사용**(현재는 매번 입력). 이점: 지침 7번(AI 생성 콘텐츠의 사실 지어내기 금지)에 대한 **단일 사실 소스**가 생긴다. 사용자 입력은 즉시 반영, 출처는 "입력하신 값"으로 표기(지침 7·9).

**C. 수정 안내** — 불일치 항목마다 "어디를 고치면 되는가"를 기존 가이드 체계에 연결: 네이버 스마트플레이스(`/profile`), 카카오, 구글 비즈니스 프로필, 웹사이트(+ `/schema`). 채널↔AI 매핑 문구는 §2-2의 **벤더 주장**이므로 "AI마다 참고하는 곳이 달라요(예시)" 수준으로만 쓰고 단정 금지.

**D. 채널 일관성 표** — 네이버/카카오/구글에서 **이미 가져오는** 이름·주소·전화를 한 표로 비교(신규 접속 0). 네이버 `telephone`은 빈 값이 올 수 있으므로 비면 "확인 못함"으로 표시(0/불일치 금지).

## 11. 2차 검토 (2026-10-29 후반) — 개정 사항. §1·§4~§7과 충돌하면 이 절이 우선한다

### 11-1. Fact Sheet(A)의 의도 정정
- **외부 검색 사용자에게는 보이지 않는다.** 사장님 입력 화면에서만 쓰이는 **정답지**이며, 용도는 "AI 답변이 입력값과 다른지 비교"뿐이다.
- 사장님은 이미 스마트플레이스에 같은 정보를 넣었으므로 **필수 입력으로 요구하지 않는다.** 주소·전화·웹사이트는 `businesses`에 이미 있다 [확인].
- **Phase 1은 새 입력 0**: 기존 3개 필드로 점검하고 결과 카드에서 "이 정보가 맞나요?"를 1회 확인받는다. 영업시간·메뉴는 **선택 입력**("입력하면 점검 항목이 늘어요")이며, 입력된 값은 소개글·FAQ·JSON-LD 생성이 재사용한다(부수 이득).
- 외부 노출용 가게 정보 페이지는 이 기능이 아니라 **별개의 Phase 3 후보**(효과 미입증)다.
- 외부 자료(카카오·구글)를 정답지로 삼으면 순환이 되므로, 정답은 사장님 본인 입력이어야 한다.

### 11-2. B(AI 답변 정확도 점검) 재검토 — "기능 확정"이 아니라 "가설"
- **약점**: API 호출(검색 미사용)은 *모델의 기억*을 측정한다. 지역 가게 질문은 실제 서비스에서 검색 기반 답이 쓰일 수 있는데(벤더 주장 [외부]) 그 화면은 못 본다. 검색 미사용 모드만으로는 사장님이 고칠 수 있는 근거(출처)도 못 준다.
- **개정**: Phase 0 파일럿은 **두 모드**를 비교한다 — (a) 검색 미사용 (b) 검색 사용(Gemini 접지, OpenAI 웹 검색 도구). (b)는 출처 URL을 돌려줘 C를 구체화할 수 있다.
- **비용 확인 [외부, 공식 페이지 기반]**: Gemini 2.5 Flash 접지는 공식 가격 페이지 기준 일 1,500건 무료(Flash/Flash-Lite 공유) 이후 $35/1,000 프롬프트(표의 무료 티어 열은 500으로 표기되어 충돌), Gemini 3 계열은 쿼리당 $14/1,000 (ai.google.dev/gemini-api/docs/pricing 검색 요약). 파일럿 규모(가게 7곳×2엔진×5회=70콜)는 Gemini 무료 한도 안. **OpenAI 웹 검색 도구 단가는 출처 간 상충($10~$50/1,000, 숨은 하위 검색 과금 사례)이라 [미확인]** — 사용 전 공식 확인.
- **SDK 제약 [확인]**: 서버 Gemini 접지는 `google_search_retrieval`(구 방식, `gemini_scanner.py:31-36`)이며 현재 설정은 꺼짐(`/var/www/aeolab/.env:12`). 신 방식·Gemini 3 지원 여부는 **[미확인]**.
- **게이트(둘 다 필요)**: ① 파일럿에서 실제로 틀린 답이 의미 있게 나온다 ② 사장님이 고칠 수 있는 항목이다. 하나라도 아니면 B는 **접는다**(비용 낭비 방지). 점수·알림·성장 단계 비연결은 유지.

### 11-3. C(수정 안내) 재검토 — 규모 축소
- 독자 가치가 낮다: "영업시간 정확히 입력"·"전화번호 최신 유지"는 **이미 체크리스트에 있다** [확인: `schema_generator.py:76-79`, `SMARTPLACE_CHECKLIST`].
- **새 콘텐츠를 만들지 않고** B·D 결과에서 기존 가이드 항목으로 **딥링크만** 연결한다. 출처 URL이 있는 (b) 모드에서만 "이 페이지 정보가 원인일 수 있어요"로 구체화한다.

### 11-4. D(일관성 표) 재검토 — **우선순위 상향(1순위)**
- 장점: LLM 없는 **결정적 비교**라 환각 위험이 없고, 사장님이 직접 고칠 수 있는 **확정 오류**(예: 카카오맵 전화번호 불일치)를 준다. 신규 접속도 거의 없다.
- **실측 [확인, 2026-10-29 서버, 공식 API 각 1회, "어니언 성수"/서울 성동구]**: 네이버 지역검색 5건 **전부 `phone=''`**(주소는 옴), 카카오는 `070-4353-3238`로 정상. → **네이버 전화는 공식 API로 비교 불가**. 표에는 "확인 못함(공식 검색이 전화번호를 제공하지 않음)"으로 표시하고 Playwright로 보충하지 않는다(차단 대응 지침). 표본은 1개 가게라 다른 가게에서 값이 오는 경우는 **[미확인]**.
- 비교 범위: 입력값 vs **카카오(전화·주소)** vs **네이버(주소만)** vs **구글(Serper, 사업장당 월 1회 이하·호출당 크레딧)**. 이름 표기 혼동은 기존 이름/구 일치 규칙 재사용(위 조회에서 "버터앤어니언"이 함께 나옴 → 엔티티 오매칭 방지 필요).

### 11-8. 이 절의 오판/오탐/누락 재확인
- 네이버 전화 빈 값은 **1회·1개 가게** 관찰이므로 일반화하지 않았다(미확인 명시). 코드가 읽는 필드명(`telephone`)은 `local_search.py:132`에서 확인.
- 가격 정보는 검색 요약이며 OpenAI 쪽은 상충 — 단정하지 않았다.
- G·H·I의 수요는 실사용 데이터가 없어 **미확인**이다. "있으면 좋을 것"이 아니라 소규모 시험 후 판단 대상으로 표기했다.

### 11-9. G(유입 경로)·H(측정 QR) 유용성 재검토 — G 보류, H 철회

**확인한 사실**: 기존 QR 카드는 사장님이 넣은 `naver_review_url`을 그대로 QR로 만든다(`qr_generator.py:42-50`, 호출처 `guide.py:567-605` 한 곳). 스마트플레이스에 네이버 자체 리뷰 QR 기능이 있는지, 리뷰 유도 정책 제약이 무엇인지는 검색으로 **확인하지 못했다 [미확인]**(검색된 QR 기능은 구글 비즈니스 프로필 것이었음).

**H — 철회**
- 스캔 수는 리뷰가 작성됐는지를 말해주지 않는다(스캔≠작성). 사장님이 보는 결과는 어차피 리뷰 수 변화다.
- 인쇄된 카드가 AEOlab 주소를 경유하면 **AEOlab이 내려가거나 주소가 바뀔 때 이미 인쇄된 카드가 먹통**이 된다 — 얻는 것(스캔 수) 대비 운영 책임이 크다.
- 정책 제약이 미확인인 영역에 중간 경유지를 추가하는 것은 위험만 늘린다.
- 네이버 독립(차단 대비)과도 직접 관련이 없다.

**G — 보류 (수요 확인 전 개발 금지)**
- 가치: 사장님이 궁금한 "AI·네이버로 온 손님이 있나"에 직접 답하는 1차 데이터. 네이버 접속 0.
- 약점: ① 손님마다 묻고 누르는 **상시 마찰**(바쁜 매장에서 꾸준히 할지 미확인) ② 하루 몇 건 수준이면 표본이 작아 비율이 흔들림 ③ AI 유입이 실제로 드물면 "0"만 쌓여 동기 저하 ④ AEOlab의 작업과 인과를 연결할 수 없음 ⑤ 사장님은 이미 손님에게 구두로 묻는 경우가 있어 직관이 있을 수 있음(일반론, 미확인).
- 코드 전에 할 일(비용 0): 사장님 1~3명(관리자 소유 사업장 포함)에게 **2주간 종이/메모 집계**를 부탁해 ① 끝까지 하는지 ② 건수 규모 ③ AI·네이버 응답이 실제로 나오는지 확인. 셋 중 하나라도 아니면 만들지 않는다.
- 만든다면: 모바일 1탭, 건수만 표시("입력하신 값"), 점수·알림과 연결하지 않음.

**정리**: 네이버 독립에 직접 기여하는 근거가 확실한 것은 **K(점검)와 D(일관성 표)** 뿐이다. G·H·I는 "있으면 좋을 수 있는" 수준의 가설이며, 앞 절(11-6)에서 보완/독자로 분류한 것이 유용성을 보증하지 않는다.

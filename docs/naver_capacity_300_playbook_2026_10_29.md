# 네이버 접속 용량 — 300곳 대비 단계별 대응표 (2026-10-29)

> 모든 숫자는 **코드 기준 모델(`scripts/naver_load_model.py`)이며 실측이 아니다.** 구독자가 거의 없어 실제 트래픽 데이터가 없다.
> 재현: `python scripts/naver_load_model.py --levers 300` (사업장 수 인자만 바꾸면 100·50곳도 출력).
> 같은 표가 코드(`backend/services/naver_capacity.py` `PLAYBOOK`)에 있고, 용량 알림 메일(70/90/100%)과 `/admin/naver-access`의 `capacity.next_steps`가 읽는다.

## 1. 결론

- **수용량은 서버 사양이 아니라 네이버 차단 위험이 정한다.** 한도(일 600·분/10분/시간 속도 기준)는 2026-10-27 서버 IP 차단 사건 하나에서 나온 **보수적 제안값**이다(`naver_access_guard.py`). 네이버의 실제 기준은 비공개라 미확인.
- 서버를 늘려도 같은 IP의 총량은 그대로다. IP를 나누는 방식(서버·프록시 추가)은 법적 회색지대(`naver_scraping_legal_risk_assessment_v1.0.md`)라 **자문 후 사용자 결정**이 필요하다.
- **현재 설계의 현실적 수용량은 50곳 안팎**(판매 한도 알림 `NAVER_CAPACITY_BUSINESSES=50`). 100곳부터는 약속·플랜 한도가 바뀌는 결정 없이는 정기 잡 몫(420)에 들어오지 않는다.
- 상한을 넘으면 보호 장치가 접속을 건너뛴다(스스로 줄이는 것). 건너뛴 항목은 0점·미노출이 아니라 "확인 전"이어야 한다(지침 8·9번). **이 동작을 대규모로 실행해 본 적은 없다(미확인).**

## 4. 미리 해 둔 것 / 아직 안 한 것

- 해 둔 것(약속 영향 없음): AI탭 질의 수 환경변수(`NAVER_AI_TAB_MAX_QUERIES`, 기본 4), 단계별 대응표를 알림·관리자 API에 연결, 절감책 효과표 스크립트, 가게별 요일 분산(Basic 순위·내 가게 통계·Pro 순위), 슬롯 분산 패턴 균등화(플래그 꺼 둠), 경쟁사 크롤 평활화, 수동 새로고침 3단 보호(경쟁사별 1시간·사용자별 10분 3회/1시간 15회·네이버 쪽 거절은 503).
- 안 한 것: 경쟁사 겹침 캐시 효과 실측, 사전 스캔 재사용, 수동 스캔의 네이버 부분 재사용(최근 결과가 있으면 다시 접속하지 않기 — 모델에서 가장 큰 미지수), 일일 사용량 기준 새로고침 예약분(스캔 몫 보호).
- 사용자 결정 대기: 슬롯 분산 켜기, 플랜 한도·측정 범위 축소, 신규 대기자 전환, 접속 경로 분산.

## 6. 2026-10-29 추가 발견 — 사전 스캔(GitHub 야간 워크플로)

- `.github/workflows/naver_scan.yml`이 매일 01:00 KST에 **GitHub 호스팅 서버(실행마다 다른 IP)**에서 네이버 AI 브리핑을 측정해 `naver_prescan`에 저장하고, 서버 야간 스캔(02:00)은 `skip_naver`로 같은 접속을 생략한다(`jobs.py`). 서버 DB에 매일 4행(활성 사업장 수 근처)이 쌓이고 있음을 확인했다(읽기 전용 조회).
- **수동 스캔(quick·full)은 사전 스캔을 읽어 결과만 덮어쓰고 서버는 같은 접속을 또 보냈다.** 2026-10-29에 같은 판정 함수(`services/naver_prescan.py`)로 서버 접속을 생략하도록 고침. 결과 값은 이전과 같다(어차피 덮어쓰던 값).
- **그러나 대시보드의 "지금 측정" 버튼은 이 경로가 아니다.** `ScanTrigger.tsx`는 `/api/scan/stream`(SSE → `scan_quick_with_progress`)을 쓰고(프론트 호출 확인), `/scan/full`을 호출하는 곳은 `GuideClient.tsx` 하나뿐이다. SSE 경로는 사전 스캔을 읽지 않고 `check_mention_multi`(여러 질의)로 직접 접속한다. **즉 가장 많이 쓰일 수동 경로는 아직 그대로다.** 사전 스캔은 질의 1개 결과라 형태가 달라 그대로 대체하면 점수 입력이 바뀐다 — 형태를 맞추거나 "최근 스캔 결과 재사용(N시간)" 방식으로 따로 설계·검증해야 한다(후속, 미착수).
- 이 구조는 "접속 경로 분산"이 일부 이미 쓰이고 있다는 뜻이다. 워크플로 한도(90분)는 약 60곳 기준이라 사업장이 늘면 나눠 실행해야 하고, **GitHub IP로 네이버에 접속하는 것의 법적 평가는 자문 대상**이다(`naver_scraping_legal_risk_assessment_v1.0.md`와 함께 검토 필요).

## 7. 사용자 요청 접속 계측 (2026-10-29 추가)

- **보는 곳**: `GET /admin/naver-access`의 `usage` — `today`(오늘 사용자 몫 페이지·출처별·수동 스캔 종류별 횟수·서로 다른 사업장 수), `summary`(날짜가 쌓인 뒤의 사용자 몫 %, 하루 수동 스캔 수, **사업장당 하루 수동 스캔 수 vs 모델 가정 0.2**), `history`(일별).
- **"사용자 몫"의 정의**: 정기 잡(`@naver_batch_job`)이 아닌 모든 네이버 접속 = 수동 스캔·새로고침·체험·정기 잡으로 표시되지 않은 백그라운드 작업. 순수한 사용자 클릭만이 아니므로 출처별(`user_by_source`)을 같이 보고 해석할 것(첫 실측에서 `naver_place_resolver` 4페이지가 잡혔다 — 어떤 경로인지는 미확인).
- **수동 스캔으로 세는 곳**: 대시보드 "지금 측정"(`stream`), `/scan/full`(`full`), 가입 후 1회 체험(`basic_trial`), 비로그인 체험(`trial`).
- **판단 기준(제안)**: 하루 이상의 표본이 쌓이기 전에는 `summary` 값이 None이다(0으로 보이지 않게). 구독자가 거의 없을 때의 값은 모델 가정을 바꿀 근거가 못 되고, 사용자 몫이 전체 접속의 큰 비중으로 확인되면 §3의 `/stream` 재사용(②) 설계를 시작한다.
- **같이 고친 결함**: 한도 기록의 일별 이력(`.naver_quota_state_history.jsonl`)이 서버에 한 번도 생기지 않았다. 배포가 잦아(백엔드 재시작 600회 이상) 자정을 넘겨 살아 있는 프로세스가 없었고, 재시작 때 어제 기록은 버려졌다. 이제 재시작 시 어제 기록을 이력에 남긴다(내일 새벽 첫 재시작/요청부터).

## 1. 문제 정의 (왜 신뢰도가 깨지나)

### 1-1. 실제로 겪은 사례
- **어니언 성수**(네이버 플레이스 ID 38561949): 업종·지역 검색에서 1위인 유명 가게인데, 가입 때 플레이스 ID가 자동 확정되지 않아 리뷰·소식·키워드 순위가 수집되지 않았고 **점수 0 → "survival(생존)" 단계**로 저평가됐다. 사장님이 보면 "1위인데 왜 생존?"이다.
- 원인: 네이버 지역검색 API는 플레이스 ID를 주지 않고 `link`는 가게 홈페이지라 ID 없이 등록되는 경로가 있었다.
- 같은 시기 **키워드 순위 측정이 9월부터 전 채널 None으로 저장**되는 사고(`local.json`→`local` 전환 누락)가 있었고, 측정 실패가 "미노출"로 보이는 구조였다.

### 1-2. 신뢰를 깨는 패턴(분류)
| 유형 | 사장님이 느끼는 것 | 구조적 원인 |
|------|---------------------|-------------|
| A. 측정 누락이 낮은 점수로 | "우리가 1위인데 점수가 왜 낮아?" | 미수집·측정 오류가 0점으로 합산 |
| B. 측정 오류가 "미노출"로 | "ChatGPT에 나오는데 안 나온다고?" | 오류(error)와 미노출(false)이 같은 저장값 |
| C. 가게 이름 검색 순위 | "내 이름으로 검색하면 당연히 1위지" | 상호 키워드가 순위·강점에 섞임 |
| D. 범위를 넘는 문구 | "상위 20위"라더니 5곳만 확인? | 측정 범위와 화면 문구 불일치 |
| E. 측정 시점·기기 차이 | "내가 직접 검색하니 다르다" | PC/모바일·로그인·시점 차이를 안내 안 함 |
| F. AI(ChatGPT/Gemini) 한쪽 실패 | "한쪽만 안 돼도 점수가 반토막?" | 한쪽 대량 실패를 0점으로 처리 |

## 2. 이미 구현된 방어선 (확인 후 재사용)

> 모두 서버 반영·커밋 완료(10-25~27). 아래 경로는 작업 전 `grep`으로 존재 확인.

### 2-1. 측정 정확도·누락 방지
- **플레이스 ID 자동 확정**: `backend/services/naver_place_resolver.py` — 이름 일치 1곳일 때만 확정(모호하면 저장 안 함). `GET /api/businesses/resolve-place`(시간당 10회), 온보딩·사업장 추가 연결, `_run_full_scan`·`daily_scan_all`에서 ID 없으면 확정·저장.
- **순위 측정 복구·재구현**: `backend/services/naver_keyword_rank.py` — `local.json`→`local`, PC·모바일을 가게 카드(플레이스 링크) 화면 순서·광고 제외로 계산(`_place_card_rank`), 목록 비었을 때 재확인(일일 상한 80% 이내).
- **측정 실패 ≠ 미노출**: `error` 행을 점수·CSV·카드 배지·평균에서 제외, 변동 알림도 error 행을 이탈로 오인하지 않음.
- **네이버 접속 실패 처리**: 접속 실패는 `error:"page_load_failed"`(→ `score_engine._is_naver_unmeasured`가 미측정 처리).
- **카나리**: `rank_canary_job`(04:50 KST, 서버 `.env` `RANK_CANARY=어니언 성수|38561949`) — 1위 유명 가게로 매일 측정 파이프라인이 살아있는지 확인.
- **대량 실패 알림**: 순위 대량 실패(≥50%) 운영자 알림, 네이버 Playwright 일일 상한(250건) 사용량 70/90% 경고.

### 2-2. 점수가 억울하게 깎이지 않게
- **미측정 항목은 제외 후 재정규화**: `backend/services/score_engine.py` `_renormalized_track1`(약 1441행), v3.1·v3.2. `detail.excluded`에 제외 항목 기록, `ScoreEvidenceCard`가 재정규화 비중 표시. 순위가 미측정이면 0점이 아니라 빼고 나머지로 계산한다.
- **한쪽 AI 실패 시 다른 쪽만으로 평가**: `_ai_measurement_failed`(811행), `_one_ai_rate`(827행) — 성공<10·실패≥10이면 대량 실패로 보고 0점 대신 다른 쪽만 사용.
- **순위는 점수에 연결하지 않음**: 시뮬레이션에서 평균 방식 연결 시 인기 가게도 감점돼 보류(`docs/keyword_rank_measurement_findings_2026_10_26.md` §5~7). 현재 순위는 "점수 미포함·별도 표시".
- **`gap_analyzer`**가 미측정 순위를 격차로 말하지 않게 수정.
- 서버 전 사업장 시뮬레이션(10-26): 점수 +25~60%, 7곳 중 4곳 성장 단계 상승(기존 기록은 다음 스캔부터).

### 2-3. 화면 정직성·설명
- **상호 키워드 분리**: `frontend/lib/keywordBrand.ts`, 파이썬 `strength_signals.is_brand_keyword`(보수적 — 오탐이 더 나쁨).
- **"네이버에서 직접 확인" 링크**(키워드별), 순위 요약 문구, "검색 첫 화면(PC 3~13곳/모바일 5~14곳) 광고 제외 기준" 명시.
- **"측정으로 확인된 점" 카드**: `backend/services/strength_signals.py`, `GET /api/report/strengths/{biz_id}`, `StrengthSignalsCard.tsx`. 사실+측정 시점만, 평가어 금지, 0·NULL·오류는 미표시, 오류는 "확인하지 못한 항목"으로만. 설계 `docs/strength_signals_design_v1.0.md`.
- **점수 계산 방식 변경 안내**: `ScoreMethodChangeNote`, `lib/scoreMethodChange.ts`(변경일 2026-10-26) — 점수가 갑자기 올라간 사장님이 의심하지 않게.
- **공개 페이지 정정**: score-guide·how-it-works의 키워드 순위 25/30/35% 비중 제거 → "점수 미포함·별도 표시" + 나머지 5항목 환산 비중.
- **체험 화면 정정**: 한 줄 진단 범위를 "측정한 네이버 검색어의 상위 5곳"으로, 구글 지도 비슷한 이름 가게 인식, "상위 20위"→"상위 5곳".

## 3. 현재 남은 약점 (오판 방지: 아래는 "의심"이지 확정 아님 — §4에서 실측으로 검증)

1. **로그인 대시보드의 실제 화면을 확인하지 못했다.** 서비스 키로 로그인 토큰을 만드는 것은 권한 분류기가 거부해, "측정으로 확인된 점" 카드·순위 카드가 실제 사용자 화면에서 어떻게 보이는지 미확인. (사용자가 `/permissions`에 좁은 허용 규칙을 두거나 직접 화면을 캡처해 줘야 함)
2. **순위와 점수가 따로 노는 점**: 1위 가게 사장님이 "키워드 1위인데 점수가 낮다"고 느낄 수 있다. 현재는 순위를 점수에 넣지 않고 별도 표시. 연결 산식(예: 상위 N 안 노출 비율)은 실사용자 데이터 없이 정하면 인기 가게가 감점될 수 있어 보류.
3. **강점 신호 임계값은 근거 약한 제안값**: ChatGPT 표본≥30, 측정 30일 이내, 경쟁사≥3곳, 최대 4항목(`strength_signals.py` 상단 상수). 실사용 반응 전엔 맞는지 모름.
4. **유료 스캔 ChatGPT 질문 방식**: 체험은 가게 이름을 넣지 않는 비유도 방식(`sample_recommend`)인데, 유명 가게도 "추천 목록에 안 나온다"로 보일 수 있다. 유명하지만 ChatGPT 학습 데이터에 약한 가게(소상공인 일반)에 대한 문구가 사장님 기대와 어긋날 수 있음.
5. **Gemini 측정 신뢰**: 결제 연결 전 100회 중 92~97회 실패(무료 티어 한도). 사용자가 결제·크레딧 연결 예정(연결로 가정하고 구현함). 연결 후 `scripts/check_ai_providers.py`로 Gemini 9/10 이상 성공 확인 필요. 미달 시 `frontend/lib/featureFlags.ts` `GEMINI_MEASUREMENT_LIVE=false` + 재빌드.
6. **측정 시점·기기·로그인 차이 안내**가 모든 화면에 일관되게 있는지 전수 확인 안 됨(CLAUDE.md 면책 원칙).
7. **저평가 사업장의 "성장 단계" 표현**: survival/stability 같은 단계 이름이 유명 가게에게 모욕적으로 읽힐 수 있다(예: 1위 가게가 "생존 단계"). 단계명·카피 점검 필요.
8. **과거 기록 오표기**: 10-17 이전 네이버 결과 중 접속 실패분은 `error` 표시가 없어 "미노출"로 남아 있을 수 있어 구분 불가(소급 정정 불가).

## 4. 보완 과제 (우선순위)

> 각 과제는 구현 전 **§5 규칙**을 적용한다. 코드 변경이 필요한 항목은 사용자 승인 후.

### P1 — 유명 가게 시나리오 검증 세트 만들기 (가장 먼저)
- 목표: "유명한데 점수가 낮게 나오는" 경우를 재현 가능한 목록으로 확정.
- 방법: 서버 `businesses`·`scan_results`에서 실제 가게 중 유명 가게(예: 어니언 성수)로 스캔 결과 화면의 모든 숫자·문구를 한 줄씩 대조. 카나리 가게로 PC/모바일 순위가 네이버 직접 검색과 일치하는지.
- 산출물: `docs/popular_shop_trust_cases_2026_xx.md`(가게·화면·기대 vs 실제·원인 분류 A~F).

### P1 — 성장 단계 이름·결과 문구 점검 (§3-7)
- 단계명(survival 등)과 "저평가·이탈 위험" 문구가 이미 잘 되는 가게에도 그대로 보이는지.
- 방향 후보(결정 필요): 측정으로 확인된 강점이 있으면 단계명 대신 "확인된 강점 + 아직 측정하지 못한 항목"으로 요약.

### P2 — 순위의 점수 연결 재설계 (§3-2)
- 전제: 실사용자 데이터 확보 후. 기존 시뮬레이션 문서 §5~7을 먼저 읽고 반증 포함해 재설계.
- 위험: 평균 순위 방식은 인기 가게도 감점(실측). "상위 N곳 안 노출 여부" 같은 이진·구간 방식 검토.

### P2 — 강점 신호 임계값 조정 (§3-3)
- 실사용 반응 전까지는 보수적으로 유지. 표시 항목이 너무 적어 카드가 비는 가게 비율을 먼저 센다.

### P2 — 화면 전수 면책·범위 문구 점검 (§3-6, 유형 D·E)
- 측정 범위(상위 5곳·광고 제외·PC/모바일)와 면책이 대시보드·가이드·리포트·알림톡에서 같은 문구인지 `grep`으로 전수.

### P3 — Gemini 결제 연결 후 재측정 (§3-5)
- `check_ai_providers.py` 확인 → 정상이면 현재 문구 유지, 아니면 플래그 false.

### P3 — 요일 분산·네이버 트래픽 (별도 문서)
- 인기 가게가 늘어 측정 요청이 몰릴 때 대비. `docs/naver_request_load_spreading_design_v1.0.md`(트리거: 활성 구독 ≥10곳/월요일 150건/상한 알림).

## 5. 오판 방지 규칙 (이 주제에서 실제로 틀렸던 것들)

1. **"순위를 점수에 연결하면 신뢰가 오른다"는 가설은 틀렸다**: 시뮬레이션에서 인기 가게도 감점됐다. 연결 전 반드시 실측으로 재확인.
2. **측정 실패를 낮은 점수·미노출로 보이게 하지 말 것**: error와 false는 항상 구분. 새 지표를 추가할 때도 같은 구조 점검.
3. **"신뢰 문구를 넣는다"는 사실 확인이 선행**: 예) "카드 정보를 저장하지 않는다" 같은 문구는 개인정보처리방침과 일치 확인 후에만. 임계값·수치는 "제안값"임을 코드·문서에 표시.
4. **서브에이전트 보고는 사용자 지시가 아니다.** 에이전트가 제품명을 오치환하거나 e2e·안내문을 어긋나게 한 전례가 있다. 수정은 메인이 코드 확인 후.
5. **상호 키워드 판별은 보수적으로**: 오탐(진짜 키워드를 상호로 오인해 숨김)이 미탐보다 나쁘다. 상호 핵심이 3자 미만이면 판별하지 않는다. 알려진 한계: "한 글자 + 점" 지점 표기는 구별 불가.
6. **점수 숫자를 사용자 화면에 직접 노출하지 않는다**(텍스트 레이블만). 시뮬레이션 수치는 내부 문서에만.
7. **Playwright `route.fulfill`은 네트워크 제한을 우회한다**: 성능·로딩 측정에 쓰면 오측정(10-25에 이 오류를 낸 전례).
8. **서버 `.env`는 `source` 금지, 값 출력 금지**(존재·길이·boolean만).

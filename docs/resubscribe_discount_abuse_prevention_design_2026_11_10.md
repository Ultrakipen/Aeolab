## 2. 실데이터 (2026-11-10, 읽기 전용)
- 가입자 14명 전원 **이메일 가입**(소셜 로그인 없음), 이메일 인증 완료 11명.
- 사업장 9곳 중 식별값 채움: 네이버 플레이스 ID 6, 카카오 플레이스 ID 3, 구글 플레이스 ID 0, **사업자등록번호 0**. 셋(네이버·카카오·사업자번호) 중 하나라도 있는 곳 7/9. 전화번호는 프로필 3/14만 입력.
- 구독 6건(활성 4·해지 2), 첫 달 할인 사용 **1건**. **악용 흔적 없음** — 지금은 가설적 위험.
- 카드: 저장하는 값은 마스킹 번호·카드사뿐. 크렙 응답에 카드 고유값(지문)이 있는지는 **미확인**(내부 점검 문서에도 없음 → 크렙에 문의 필요).

## 3. 위협 모델과 경제성
- **반복 방식:** 가입 → 할인 결제 → (이용) → 탈퇴 → 재가입(같은 이메일 가능: Auth도 삭제됨) → 다시 할인. 주기마다 8,950원(Basic 기준) 절감 → 사실상 상시 반값. (앞서 "1회"라고 한 것은 틀렸다.)
- **악용자의 비용:** 60일 이력 상실, 사업장·키워드·경쟁사 재등록, 첫 측정 대기, 7일 이내 미이용 환불은 이용하면 불가. 즉 번거로움이 비용이다.
- **한계:** 새 이메일 + 사업장 식별값을 비우는 사람은 어떤 방식으로도 완전히 못 막는다. 목표는 "같은 가게·같은 이메일로 쉽게 반복"하는 길을 막아 비용을 올리는 것.

## 5. 설계안 (안 1) — 지금 구현하라는 권고가 아니라, 착수 신호가 오면 쓸 준비된 설계

### 5-1. 보관 대상 — 해시만, 원문은 보관하지 않는다
| 키 종류 | 정규화 | 신호 강도 |
|---|---|---|
| 네이버 플레이스 ID | 숫자만 | 강 |
| 카카오 플레이스 ID | 숫자만 | 강 |
| 사업자등록번호(입력 시) | 숫자 10자리 | 강 (지금은 0/9 — 입력률이 오르면 가치 상승) |
| 이메일 | 소문자, gmail은 점·`+별칭` 제거 | 약(쉽게 바꿈) — 보조 |
- 해시는 `HMAC-SHA256(서버 비밀값, "종류:정규화값")`. 플레이스 ID는 공개 숫자라 단순 해시는 역산이 쉬워 **서버 비밀값(pepper) 필수**. 비밀값 분실 시 보관 키가 무효가 되므로 `.env` 백업 대상.
- **기록 시점:** 탈퇴 때가 아니라 **할인 결제 성공 때**(한 곳에서만 기록 → 관리자 삭제·Auth 직접 삭제 등 모든 탈퇴 경로를 덮는다).

### 5-2. 테이블(SQL Editor 수동 실행, `scripts/supabase_schema.sql`에도 기록)
```sql
CREATE TABLE IF NOT EXISTS discount_used_keys (
  id          UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  key_type    TEXT NOT NULL,          -- naver_place | kakao_place | brn | email
  key_hash    TEXT NOT NULL,          -- HMAC-SHA256 hex
  used_at     TIMESTAMPTZ DEFAULT now(),
  expires_at  TIMESTAMPTZ NOT NULL,   -- 보관 기간 만료(D-2)
  released_at TIMESTAMPTZ,            -- 관리자 해제(오탐 구제)
  released_by TEXT,
  UNIQUE (key_type, key_hash)
);
ALTER TABLE discount_used_keys ENABLE ROW LEVEL SECURITY;   -- 정책 없음 = 서비스 롤만 접근
CREATE INDEX IF NOT EXISTS idx_discount_used_keys_exp ON discount_used_keys(expires_at);
```
`tests/fixtures/db_columns.json` 갱신(`refresh_db_columns_snapshot.py`)이 새 컬럼을 쓰는 코드의 선행 조건.

### 5-3. 판정 흐름
1. **결제 전 자격 조회 API**(신규, 읽기 전용): 현재 사용자의 구독 이력·사업장 식별값·이메일 해시로 `eligible` 판정. `PayButton`은 지금 `subscriptions`만 조회해 할인가를 보이므로, 이 API로 바꿔야 **카드 입력 뒤 거부**되는 나쁜 경험이 없다(사용자가 이미 카드까지 입력한 뒤 400을 받는 것을 방지).
2. `_is_first_time_subscriber`는 기존 ①② 뒤에 ③ `discount_used_keys` 조회(만료·해제 제외)를 더한다. 서버 재검증은 유지.
3. **fail-open:** 조회 실패 시 기존 가드(`_already_subscribed_same_plan`)와 같이 결제를 막지 않고 경고 로그 — 막지 못하는 비용은 8,950원 수준, 막는 비용은 정상 고객의 결제 실패.
4. 할인 결제 성공 시 키 기록. 같은 키 동시 기록은 `UNIQUE`로 하나만 남는다(경합 허용, 로그).
5. 일 1회 만료 키 삭제 잡(`expires_at < now`).

### 5-4. 오탐 구제와 안내
- 오탐 사례: 사업 양도·인수, 대행사가 고객 가게를 등록, 탈퇴 후 실수로 복귀한 정상 고객.
- 관리자 해제 도구(키 종류·마스킹 표시 → `released_at`), 문의 경로 안내.
- 거부 문구: "이 사업장(또는 이메일)으로 첫 달 할인을 이미 이용하셨습니다. 정상가로 이용하실 수 있어요." — 사용자를 의심하는 어조 금지(신뢰 지침).
- 탈퇴 화면에 "탈퇴 후에도 부정 이용 방지를 위해 비식별 값이 N개월 보관됩니다" 고지.

## 6. 법적·방침 쟁점 (미확인 — 변호사 확인 대상)
- 현재 방침은 결제 정보 5년 보관(전자상거래법)만 있고 **부정 이용 방지 목적은 없다**(`privacy/page.tsx` 76·87·207행 확인, "부정"은 "부정확한 개인정보"만 나옴).
- 개인정보 보호법 제21조 단서는 "다른 법령에 따라 보존"만 예외로 둔다는 것까지 확인했다. **부정 이용 방지를 위한 보관의 허용 근거·기간·해시(가명) 처리 기준은 검색(보안뉴스·경향신문·법제처 요약 등)으로 확인하지 못했다.** 사업자 1인 가게는 사업장 식별값이 개인을 특정할 수 있어 해시도 개인정보(가명정보)로 볼 가능성이 있다.
- 따라서 구현 전: ①수집 항목·목적·기간을 방침에 명시 ②최소 항목(해시)·최단 기간 ③탈퇴 화면 고지 ④법적 근거 확인. 이 순서를 지키지 않으면 방침과 실제 동작이 어긋난다.
- 별건(미확인): 방침의 "결제 정보 5년 분리 보관"과 탈퇴 코드(구독 행 삭제, 결제 이벤트만 잔존)의 부합 여부.

- 못 막는 것: 새 이메일 + 식별값을 비우거나 다른 가게로 등록.
- 구현 규모(중간): 테이블 1, 서비스 모듈 1(정규화·HMAC·조회·기록), `webhook.py` 판정·기록, 자격 조회 API 1, `PayButton` 수정, 관리자 해제 화면, 만료 잡, 방침·탈퇴 화면 문구, 시험(정규화·판정·경합·fail-open·오탐 구제). 변이 검증 포함.

## 9. Phase 0 — 지금 할 수 있는 것(개인정보 저장 없음, 2026-11-10 정정)

> 정정: 처음에는 "할인 결제 건수 ÷ 신규 구독 수"를 지표로 적었으나 **쓸모가 없다.** 신규 구독자마다 정확히 한 번 할인이 나가는 구조라 비율이 늘 비슷하고, 탈퇴한 계정은 DB에서 사라져 재가입 악용을 감지할 수 없다. 아래로 대체한다.

- **노출 규모 집계(식별값 없이 숫자만):** 탈퇴 시점에 "구독 이력이 있고 첫 달 할인을 쓴 계정"이면 월별 카운터만 올린다(계정·사업장·이메일 정보는 저장하지 않음 → 방침 변경 불필요). 이 값이 재가입으로 다시 할인받을 수 있는 **최대 규모**다. 월 0~2건이면 Phase 1은 구현할 이유가 없다.
- **착수 신호(제안값, 근거 없음 — D-1에서 확정):** ①월 노출 규모가 5건 이상 ②구독자 20명(BEP) 도달 ③고객 문의·관리자 눈에 띈 실제 반복 사례 중 하나.
- 크렙 카드 고유값 문의(D-6)는 Phase 1을 할 때만 쓸모가 있어 급하지 않다.
- 미확인 대안: 방침이 이미 밝힌 "결제 정보 5년 보관"을 법정 취지대로 유지하는 쪽으로 탈퇴 코드를 고치고 그 기록을 자격 판정에 쓰는 방법. 당초 목적과의 관련성은 법률 쟁점이라 변호사 확인 후에만 검토.

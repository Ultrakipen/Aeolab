## 0. 왜 필요한가

시스템(`delivery.py`)은 주문 상태 추적·결제·메시지·완료보고서 저장까지는 되어 있지만, **"실제로 무엇을 어떻게 작업하는지"는 코드 어디에도 없다** — 전부 운영자 머릿속에 있던 절차다. 관리자 완료 화면(`AdminDeliveryDetailClient.tsx:35-40`)의 체크리스트도 패키지 구분 없이 고정 4항목이라 패키지 01(등록 대행)에는 맞지 않는다(§5 참조). 실주문이 아직 0건이라 지금 만드는 이 문서는 "시범 없이 쓰는 최초 체크리스트"이며, 첫 실제 건을 마친 뒤 반드시 §9를 채워 정식 SOP로 갱신한다.

## 2. 전체 처리 흐름 (상태 머신, `VALID_STATUSES`)

```
received(접수) → paid(결제완료) → in_progress(진행중) → completed(완료)
                                    ↳ rework(재작업, 최대 2회 권장)
결제 전: received → cancelled(취소, 결제 전만 가능)
결제 후: paid/in_progress/rework → refunded(환불, owner 전용, 토스 실환불 발생)
```

- 관리자 화면: `/admin/delivery`(목록) → `/admin/delivery/{id}`(상세, 메시지·상태변경·완료처리·납품파일)
- 카카오 알림톡 자동 발송 시점: `in_progress` 전환 시, `completed` 처리 시 (그 외 상태는 알림 없음)
- **"취소"와 "환불" 버튼을 혼동하지 말 것** — 결제 전 주문은 취소만 가능(환불 API 호출 안 됨), 결제 후 주문은 반드시 환불 처리(취소 버튼은 400 에러로 막힘, `delivery.py:807-812`)

## 3. 접수 ~ 착수 단계 체크리스트 (공통, 전 패키지)

1. `/admin/delivery`에서 신규 의뢰 확인 — `request_title`·`request_body`·첨부 자료 확인
2. 결제 완료(`paid`) 확인 후 "진행 시작" 클릭 → `in_progress` 전환 (카카오 알림 자동 발송)
3. **부운영자 위임 안내 발송** — ⚠️ 프론트 배너(`delivery/page.tsx:238-241`)가 "결제 완료 후 안내해 드립니다"라고 고객에게 약속하지만, **이 안내를 실제로 보내는 자동 기능은 코드에 없다.** 운영자가 카카오톡/메시지 기능(`/admin/delivery/{id}/messages`)으로 직접 안내를 보내야 함.
   - ⚠️ **"위임" 표현 자체를 재확인할 것** — WebSearch로 찾은 절차([스마트플레이스 소유자 변경 권한 위임 방법](https://sfm3.surfingmoon.co.kr/entry/%EC%8A%A4%EB%A7%88%ED%8A%B8%ED%94%8C%EB%A0%88%EC%9D%B4%EC%8A%A4-%EC%86%8C%EC%9C%A0%EC%9E%90-%EB%B3%80%EA%B2%BD-%EA%B6%8C%ED%95%9C-%EC%9C%84%EC%9E%84-%EB%B0%A9%EB%B2%95))에 따르면 스마트플레이스에 "부운영자"라는 제한된 권한 등급이 별도로 없고, **찾은 유일한 메커니즘은 "주인 권한 위임"(가게 우측 점3개/닉네임 → 권한 관리 → 위임받을 아이디 입력 → 신청) — 이는 상대방 동의 절차 없이 즉시 처리되는 "소유자 자체 이전"**이라고 서술돼 있음. 이 서술이 맞다면 지금 매뉴얼의 "부운영자 위임/해제"라는 표현은 실제보다 가볍게 들려 위험하다 — **③(§9) 확인 전까지는 고객에게 "완료 후 스마트플레이스 소유자 권한을 즉시 원상복구해 드립니다"처럼 되돌림을 명확히 약속하는 문구로만 안내하고, 절대 "일부 권한만 잠깐 빌린다"는 뉘앙스로 안내하지 말 것.** 출처가 비공식 블로그라 신뢰도 낮음 — §9에서 최우선 검증 필요.
4. 업종·주소·전화번호 등 기본 정보는 `businesses` 테이블에 이미 있는 값 재사용 (고객에게 중복 질문 금지)
5. **[2026-09-03 재확인] 위임 동의는 이미 결제 전에 받고 있음** — `delivery/new/page.tsx`(4단계 "위임 동의")에 `consentAgreed` 체크박스가 이미 구현돼 있고, "네이버 스마트플레이스 부운영자 권한을 AEOlab에 위임하는 데 동의합니다" 문구로 결제 자체를 막는 필수 동의를 받는다(`consent_agreed: true`로 서버 전송). **다만 이 동의 문구도 "부운영자 권한"이라는 표현을 쓰고 있어서, 위 3번 항목의 미확인 리스크(실제로는 소유자 이전일 가능성)가 사실이라면 이 동의 문구 자체가 고객에게 실제보다 가볍게 전달되고 있는 것** — "동의 절차가 있는지"는 이미 해결된 문제이고, 남은 건 "그 동의 문구가 실제 메커니즘을 정확히 설명하는지"임을 §9에서 구분해서 확인할 것.
5. 사업장이 **프랜차이즈**인 경우 AI 브리핑 관련 안내 문구는 제외 대상임을 인지(`score_engine.py` 프랜차이즈 제외 규칙, 등록 대행 자체는 무관)

## 5. 완료 처리 단계

⚠️ **알려진 불일치**: `/admin/delivery/{id}` 완료 처리 모달의 `COMPLETION_CHECKLIST`(`AdminDeliveryDetailClient.tsx:35-40`)는 패키지 구분 없이 고정 4항목("소개글 등록 완료" / "키워드 최적화 완료" / "톡톡 채팅방 메뉴 등록 완료" / "후기 답글 템플릿 제공")이다. 이 항목들은 사실상 **02 패키지 기준**이라, **01 주문 완료 처리 시 화면 체크박스를 그대로 믿지 말고 §4.1 체크리스트로 실제 완료 여부를 판단**할 것. (코드 자체를 패키지별 분기로 고칠지는 별도 결정 사항 — 필요하면 이어서 처리 가능)

- `completion_report.summary`에 특이사항·다음 단계 안내 기록 (자유 텍스트, 시스템이 강제하는 구조 없음)
- 스크린샷 등 납품 자료는 `/admin/delivery/{id}` → 파일 URL 등록(Supabase Storage 서명 URL 권장, `materials_url` JSONB 배열에 누적)
- "완료 처리" 버튼은 `completion_report` 등록과 `status=completed` 전환이 한 번에 일어남 — 되돌릴 수 없으므로 자료 등록 후 마지막에 클릭

## 6. 완료 후 처리

- [ ] **위임받은 권한 원상복구 요청** — ⚠️ 자동 해제 기능 없음(코드 전체 확인 완료, `delivery.py`·`jobs.py` 어디에도 해제 로직 없음). 완료 메시지에 권한을 되돌려 달라는 안내를 **매번 수동으로** 포함할 것. 잊으면 고객 스마트플레이스에 AEOlab 쪽 접근 권한(§3의 검증 결과에 따라 최악의 경우 "소유자 권한" 자체)이 무기한 남는 보안·신뢰 리스크 — §3의 미검증 상태(WebSearch 근거로는 "부운영자"라는 제한된 등급이 아니라 즉시 처리되는 소유자 이전일 가능성) 때문에 이 항목은 일반적인 "권한 회수"보다 훨씬 무거운 리스크일 수 있음. §9 검증 전까지 완료 처리 직후 **가장 먼저** 챙길 것.
- [ ] 후기 요청 — 고객이 `POST /orders/{id}/testimonial` 제출 시 운영자에게 이메일 알림 자동 발송("코칭 쿠폰 발송 필요"). **카카오톡 쿠폰 발송은 여전히 수동** — 알림 받으면 바로 처리
- [ ] 30일 재진단(패키지 03만) — `work_completed_at + 30일` 조건으로 `delivery_30day_rescan_job`이 자동 실행. 운영자 개입 불필요, 결과만 사후 확인

## 7. 재작업(rework) / 환불 원칙

- `rework_count` 최대 2회 권장 표시(강제 차단 아님) — 3회 이상 요청 시 별도 상담 권장
- 환불은 **owner 전용**(`require_owner`), 결제완료 상태(`paid`/`in_progress`/`rework`)에서만 가능, 토스 실제 결제취소 API 호출 → 이중 클릭해도 락으로 중복 환불 방지됨(2026-07-11 수정 완료)
- 결제 전 주문은 "취소"만 가능(금전 이동 없음)
- ⚠️ **자동환불 안전망은 `paid` 상태만 감시** — `delivery_auto_refund_job`(매일 11:30)은 `status='paid'`(결제완료·미착수)만 대상이라, "진행 시작" 클릭해 `in_progress`로 전환한 뒤 납품물을 계속 안 올리면 이 안전망 밖으로 벗어난다. 보완책으로 `delivery_stalled_in_progress_alert_job`(매일 12:30, 2026-07-21 신설)이 운영자에게 알림만 보낸다(자동환불 아님, 운영자가 직접 확인·처리해야 함) — 알림 오면 방치하지 말 것. **정확한 기준(2026-09-03 코드 재확인, `jobs.py:5766` docstring+실제 쿼리)**: "in_progress 전환 후 14일"이 아니라 **`paid_at`(결제완료 시점) 기준 정확히 14일 경과 시점 + status가 `in_progress`/`rework` + `materials_url` 없음** — 진행 시작을 늦게 눌러도 결제일 기준으로 카운트된다는 점에 유의.

## 8. 활용 가능 사내 도구 (AI 호출 0, 무료)

⚠️ **API로 직접 호출하지 말 것** — 아래 두 엔드포인트는 프론트엔드에 연결된 화면이 없고(코드 전수 확인, 사용처 0건), `X-Admin-Key`가 아니라 **Basic+ 유료 사용자 로그인 토큰**이 있어야만 호출됨(`tools.py:27-41 _require_basic_plus`). 운영자가 실제로 API를 부를 방법이 없다 — **파일을 직접 열어 복사해 쓸 것**.

| 항목 | 실무 사용법 |
|------|-----------|
| 메뉴 일괄 등록 엑셀 | `GET /api/tools/menu-template.xlsx` — 이건 유일하게 프론트(`GuideClient.tsx`)에 붙어 있어 **고객 계정으로 로그인해 실제로 다운로드 가능**. |

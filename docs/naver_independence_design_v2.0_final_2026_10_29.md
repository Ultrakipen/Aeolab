## 1. 결론 (먼저 읽을 것)
1. 지금까지의 설계는 **"AI 노출을 올리는 기능"이 아니라 측정·정확도 점검·서비스 연속성** 기능이다. 노출을 움직이는 레버(리뷰 수, 기존 지도 검색 순위, 구글 비즈니스 프로필)는 미국 중심 외부 연구에서만 확인되며 **한국 환경 검증은 없다** → 한국 실데이터로 레버를 확인하는 기능(N2)을 후보로 검토했으나 **현재 데이터로는 통계가 불가해 보류**한다(§6-1).
2. 근거가 확실한 즉시 후보는 **K(점검), D(채널 정보 일관성 표), S-safe(구글 직접 접속 방지)** 3개다.
3. 재검토에서 **D의 구글 쪽이 현재 데이터로는 대상 0곳**임을 발견했다(`google_place_id` 입력 0/9). 자동 찾기(Text Search IDs Only, 공식 가격표상 무제한 무료)와 사장님 확인 단계가 D의 필수 요소가 됐다.
4. 구글 검색 접지(Gemini grounding)와 그 결과를 저장·분석하는 기능은 **만들지 않는다**(약관 문의 안 함 결정).
5. **가장 큰 한계(재검토 발견)**: 새 비유도 프로브(`recommend_v1`) 기준 유료 스캔 36행(사업장 5곳) 중 ChatGPT 노출이 있는 가게는 **1곳(약 50%)**, 나머지 4곳은 0이다(서버 조회, 대표성 약함). 즉 대부분 가게의 문제는 "노출이 틀리게 보이는 것"이 아니라 **노출이 0인 것**이다. "노출이 있는 가게"를 전제로 하는 기능(B, N1)은 적용 대상이 소수이고, 0→양수로 바꾸는 레버는 아직 한국 데이터로 확인되지 않았다.

## 5. 기능 설계
### 5-1. K — 네이버 "확인 전" 상태의 점수·화면 점검 (코드 변경 없음)
- 목적: 네이버 항목(브리핑·순위·플레이스 통계)이 대부분 측정 불가일 때 재정규화 점수와 문구가 사용자에게 의미 있는지 확인(`naver_dependency_table` §4 [미확인]).
- 방법: 저장된 스캔으로 읽기 전용 재계산, 인기 가게(어니언 성수·하라식당 등) 화면 대조(지침 9). 네이버 접속 없음.
- 산출: 결과 보고 + 필요 시 문구·표시 수정 제안(별도 승인).

### 5-2. D — 채널 정보 일관성 표 (구글 지도 상태 G1 포함) — 보완
**무엇**: 입력값(이름·주소·전화·웹사이트)이 카카오·네이버·구글 지도에서 같은지 비교해 대시보드에 `일치 / 다름 / 확인 못함`으로 표시.
**데이터 소스**
| 채널 | 방법 | 비교 항목 |
|---|---|---|
| 입력값 | `businesses`(기존) | 기준 |
| 카카오 | 로컬 API(기존 `kakao_visibility`·`local_search`) | 이름·주소·전화 |
| 네이버 | 지역검색 공식 API(기존 `search_naver`) | 이름·주소 (**전화는 제공되지 않아 "확인 못함"**, Playwright로 보충하지 않음) |
| 구글 | **Places API (New)** Place Details(신규) | 이름·주소·전화·웹사이트·영업 상태 + **평점·리뷰 수(요청 시점 표시만, 저장 안 함 — 구 N5 흡수)** |

**구글 지도 ID 확보** (재검토 결과 필수): 현재 0/9.
- 방식: Text Search **IDs Only**(무제한 무료)로 이름+주소 후보를 찾아 **사장님에게 후보를 보여주고 확인받아** 저장(`businesses.google_place_id`, 기존 컬럼). 자동 확정은 하지 않는다(프랜차이즈 지점·동명 오매칭 방지). 후보 판정은 기존 `names_match`+시군구 규칙 재사용.
- 후보 확인용 이름·주소 표시는 Place Details 호출이 필요할 수 있어 Essentials 필드만 쓴다 [단계 미확인, 파일럿에서 실청구 확인].
**Places 호출 규칙** (공식 정책 반영)
- FieldMask 필수. `reviews` 계열 필드는 더 높은 단계라 요청하지 않는다. 전화·평점·리뷰 수·영업시간·웹사이트 요청 시 요청 전체가 Enterprise로 과금(요금 $20/1,000, 월 1,000건 무료 → 약 28원/건).
- **저장은 `place_id`만.** 응답값은 화면 표시와 비교에만 쓰고 DB에 쌓지 않는다. 일치/다름 결과 상태의 저장 가능 여부는 **[미확인]** → 파일럿 전까지는 저장하지 않고 요청 시점에 재계산.
- **표시 시 구글 출처 표기**: 구글 로고(공간이 좁으면 "Google Maps" 텍스트)와 장소 상세 출처를 카드에 함께 표시.
- 화면 로드마다 호출 금지(캐시가 금지라 매번 유료). **"지금 점검" 버튼 방식 + 사용자당 일 한도**. 한도 수치는 [제안]: Basic 이상 일 2회.
**판정 규칙(결정적 비교, LLM 없음)**
- 전화: 숫자만 추출·국가번호 정규화 후 완전 일치. 추적번호 등 대체 번호를 `phone_aliases`로 허용.
- 웹사이트: 등록 도메인 비교. 주소: 시·군·구 + 도로명/지번 번호 토큰 비교(일치/일부 일치/불일치).
- 조회 실패·미제공·429는 `확인 못함`(불일치·0점으로 만들지 않음).
- **프랜차이즈**: 지점별 `naver/kakao/google_place_id`로 지점을 특정. ID가 없고 같은 구에 동일 브랜드가 여럿이면 `지점 특정 불가`로 표시. 본사 대표번호는 지점 번호와 비교하지 않고 "본사 번호"로 분류.
**API(제안)**: 신규 라우터 `routers/place_consistency.py` — `POST /api/report/consistency/{biz_id}/check`(인증·소유권 검증·플랜 게이트·일 한도), `GET .../consistency/{biz_id}`(마지막 결과 요약은 저장 불가 항목 제외). 백엔드는 `res.data` 확인 패턴·소유권 검증 필수.
**UI**: PC·모바일 별도 레이아웃, 본문 `text-sm` 이상, 상태는 아이콘+텍스트(색에만 의존 금지), 점수·숫자 등급 없음, 면책 "측정 시점·가게 정보 수정 반영 시차에 따라 달라질 수 있음", 구글 출처 표기. 카드 위치는 구현 설계 때 `dashboard_top_redesign_handoff_v1.0.md`를 읽고 결정 [미열람].
**비용**: Places 호출 1건/점검(무료 월 1,000건 → 사업장 수십 곳 규모까지 사실상 무료), 카카오·네이버 공식 API는 기존 사용량 내.
**수용 기준**: ① 구글 ID 없는 사업장에서 후보 제시→확인 흐름이 동작 ② 불일치 시연 데이터로 `다름` 표시 ③ 네이버 전화는 항상 `확인 못함` ④ 응답 값이 DB에 남지 않음(테스트) ⑤ 변이 테스트(비교 함수를 깨면 실패).

### 5-3. S-safe — 구글 직접 접속 방지 (소규모 코드 수정)
- 문제: `GOOGLE_SCANNER_BACKEND` 기본값이 `playwright`(`google_scanner.py:11`)라 환경변수 누락 시 서버가 `google.com`에 직접 접속→CAPTCHA/IP 차단 위험. 현재 서버는 `.env` 두 곳 모두 `serper` [확인].
- 수정: 기본값을 "측정 안 함"으로 하고 `{"error": "backend_not_configured", ...}`를 반환(→ `_is_google_unmeasured`가 제외 처리). 사용처 한 파일뿐이라 영향 범위 작음 [확인].
- 별개로 `screenshot.py:278`(구글 검색 직접 접속 스크린샷)은 이미 CAPTCHA 상태 — 호출 빈도 미확인, 이 설계 범위 밖.
- Serper 단일 벤더 의존 위험은 유지: 서버에 DataForSEO 자격증명이 있으나 **자동 전환은 확인되지 않음**(분기가 환경변수 기준, `:245-248`).

### 5-4. A-lite + B — 정답지와 AI 답변 정확도 점검 (조건부, Phase 0 게이트)
**A-lite**: 새 입력 요구 없음. 기존 `address/phone/website_url`을 정답지로 사용하고 결과 카드에서 "이 정보가 맞나요?"를 1회 확인. 영업시간·메뉴·가격대·`phone_aliases`는 **선택 입력**(`businesses.fact_sheet` JSONB, 항목별 `updated_at`). 외부 사용자에게 노출되지 않는 내부 비교 기준이며, 입력값은 소개글·FAQ·JSON-LD 생성이 재사용(현재는 호출마다 인자로 받음: `guide_generator.py:1218`, `schemas.py:152`).
**B**: ChatGPT(gpt-4.1-mini)에게 가게(이름+시군구+지점 단서)를 지목해 묻고 응답을 정답지와 코드로 비교.
- **엔진: ChatGPT만**(Gemini는 결제 연결 전까지 제외 — §4 실측 93% 실패, 같은 무료 한도를 기존 스캔·체험과 공유해 오히려 방해). 검색 접지 모드 없음.
- 프롬프트: 정답 누설 금지(주소·전화·시간 미포함), "모르면 `known:false`, 불확실 항목은 null".
- 표본 엔진당 5회 [제안], 같은 값이 3/5 이상일 때만 "입력값과 다름" 확정, 미달은 "일관되지 않은 답(확정 아님)" [제안].
- 판정은 코드: 전화(숫자 일치)·웹(도메인)·주소(시군구+번호)만 Phase 1. 영업시간·메뉴는 파싱 성공 시에만, 실패는 "확인 필요(원문 병기)". 폐업/휴업 답변도 3/5 규칙.
- **프랜차이즈 규칙**: 지점 단서(동·역)를 질문에 추가, 본사 공통 정보 답변은 "지점 정보가 아님"으로 분류(불일치 아님), 특정 불가면 "지점 특정 불가".
- 결과 상태: `일치 / 입력값과 다름(N회 중 M회) / 일관되지 않은 답 / AI가 답하지 못함 / 정답지에 없음 / 측정하지 못함(오류)`. **점수·등급·성장 단계·알림과 연결하지 않는다.**
- **저평가 방지(지침 9)**: "AI가 모름"은 나쁨이 아니라 "이 AI는 가게 정보를 기억하고 있지 않아요(검색 사용 시 다를 수 있어요)". 면책: "검색 기능 없이 AI가 기억하는 정보 기준, 실제 검색 결과와 다를 수 있음" + 기존 ChatGPT 면책 재사용.
- 데이터: `ai_fact_checks`(신규: business_id, run_id, platform, model, probe_version, prompt_version, sample_n, success_n, field, expected, answers JSONB[≤200자], agree_count, verdict, error, checked_at), RLS 본인 사업장만(`qual=true` 금지), 보존 기간 [제안 90일]. `ai_citations`는 건드리지 않음. SQL은 Supabase 수동 실행.
- 비용(추정): ChatGPT 점검 1회 5호출 ≈ 3원(호출당 0.5원, 실측 0.16원 + 긴 출력 가정). Gemini 포함 시 약 +7원이지만 현재 사실상 불가. 월 3회(자동 1+수동 2) ≈ 10원 수준. `ai_usage_log` purpose `fact_check`로 실측해 교체.
- **Phase 0 파일럿(코드 배포 없음)**: 인기 2~3곳·중소 2곳·무명 2곳, ChatGPT 5회씩 = 약 35콜. 응답 원문 저장→사람이 대조→테스트 픽스처화(지침 10). **게이트**: ① 무명 가게 환각이 3/5 규칙으로 걸러지는가 ② 인기 가게가 과도하게 "모름"으로 나오지 않는가 ③ 틀린 답이 실제로 의미 있게 나오고 사장님이 고칠 수 있는 항목인가. ④ **적용 가능 비율**: AI가 가게를 아는 가게의 비율(현재 유료 스캔 5곳 중 1곳만 노출>0)이 낮으면 B의 대상이 소수이므로 우선순위를 낮춘다. 하나라도 아니면 B는 접거나 전화·웹·주소 확인형으로 축소.

### 5-5. 노출 레버 실험 (보류, 행동 기록만 지금부터)
- 한계: ChatGPT는 반영 수개월~1년, Gemini는 표본이 작아 신뢰구간이 넓음(결제 차후), 대상 가게 2~3곳이면 통제군이 없어 인과 불가, 관리자 소유 사업장은 야간 스캔 제외(핸드오프 기록, 코드 재확인 안 함).
- 결정: 실험은 보류. `business_action_log`에 리뷰 요청 강화·소개글 동네 표현·구글 프로필 정비 등 행동 기록을 쌓아두면 이후 같은 전후 비교(같은 `sample_recommend` 표본 + Wilson 구간)가 가능하다. 대체 근거 확보는 §6 N2.

## 14. 상호명 직접 질의 파일럿 (2026-10-30, 사용자 질문 계기)
**질문**: "상호명은 고유명사라 GPT가 알고 있을 확률이 높지 않은가? 지금 측정은 상호로 검색했는가?"
**사실**: 현재 측정(`sample_recommend`)은 상호를 질문에 넣지 않고 "지역+업종" 5가지 질의만 쓴다(상호를 넣으면 가짜 가게도 "추천됨"이라 답하는 유도형 환각 — 2026-09-28 실측 `카페 모모` 등). 상호 인지는 별개 지표라 서버(OpenAI만, 약 50호출, 검색 미사용 기억 모드)에서 소규모로 확인했다.
**방법**: `"{지역}의 {업종} "{상호}"을(를) 아나요? 확실히 아는 가게일 때만, 모르면 known=false, JSON으로`, gpt-4.1-mini, 온도 1.0, 가게당 6회. 가짜 상호 2곳을 대조군으로.
| 가게 | 실존 | known(6회) | 비고 |
|---|---|---|---|
| 어니언 성수 | O | **6/6**, 지역(성수) 6/6 | **주소는 8회 중 0회 정확**(등록 아차산로9길 8; 답변은 성수이로7길 14·성수동1가 656-406 등 **7가지로 흩어짐**) |
| 하라식당 본점·대호흑돼지·힐링하우스마사지·홍뮤직스튜디오 | O | **0/6** (모두 "모름") | 상호로 물어도 모른다 |
| (가짜) 쿠쿠루삥뽕·하늘별빛 일본가정식 | X | 0/6 | 대조군 정상 — 모르면 모른다고 답함 |
**해석**
1. 지금 측정이 상호를 안 넣어서 "0"이 나온 것이 아니다 — 실존 가게 5곳 중 **4곳은 상호로 직접 물어도 기억 모드 ChatGPT는 모른다**(노출 0과 일치). 상호 인지는 아주 유명한 가게(어니언 성수 1/5=20%)에서만 높다. B 게이트 ④("AI가 아는 가게 비율")의 실측: 약 20%.
2. 어니언 성수는 "안다"고 답하지만 **세부 정보(주소)는 매번 달라진다** → "알고 있다"만 보고 정확하다고 단정하면 안 되고, B의 규칙(같은 값 3/5 이상일 때만 확정, 아니면 "일관되지 않은 답")이 필요하다는 근거.
3. 상호 직접 질의는 **검색을 켠 모드에서는 달라질 수 있다** → V1(검색 켠 실제 AI vs 기억 모드 수기 비교)이 여전히 선행. "AI가 이 상호를 모른다" 표시는 인기 가게 저평가 인상을 줄 수 있어 V1 전에는 화면에 내지 않는다(지침 9).
**한계**: 가게 7곳·6~8회·단일 프롬프트(모름 허용 문구가 "모른다"를 유도했을 가능성), 지역 일치는 토큰 포함 여부, 검색 미사용. 상호 인지를 점수·알림에 연결하지 않는다.

### 14-1. 원칙 확정과 질의 범위 시험 (2026-10-30, 사용자 지시)
**원칙(사용자)**: 인기 가게를 **상호명이 아니라 관련 검색**으로 물었을 때 사용자의 사업장이 추천으로 나와야 한다. → 노출의 기준 지표는 현재 방식(상호 비포함 비유도형 `sample_recommend`)이고, 상호 질의(§14)는 보조 정보일 뿐 점수·헤드라인에 쓰지 않는다.
**점검**: 현재 질의 5개는 같은 키워드를 말투만 바꾼 것이라, 대표 키워드가 좁으면 0이 나오는 것 아닌지 넓은 검색과 비교(기억 모드, 가게당 30회).
| 가게 | 현재 키워드 묶음 | 넓은 검색 묶음 |
|---|---|---|
| 어니언 성수 | **12/30**(성수 카페) | **1/30**(서울 카페·베이커리·디저트) |
| 하라식당 본점 | 0/30(일본가정식) | 0/30(창원 맛집·일식·덮밥) |
| 대호흑돼지 | 0/30(동태탕) | 0/30(창원 맛집·고기집·흑돼지) |
| 힐링하우스마사지 | 0/30(상남동마사지) | 0/30(창원 마사지·아로마) |
| 홍뮤직스튜디오 | 0/30(편곡) | 0/30(창원 작곡·실용음악·음악 레슨) |
**해석**: ① 넓히면 오히려 떨어진다(어니언 12→1) — **지역이 구체적인 관련 검색이 로컬 가게에 맞는 질의**이고 현재 방식이 타당하다. ② 창원 4곳은 질의를 넓혀도 0이라 "키워드가 좁아서 0"이 아니다. ③ 창원 질의에서 AI가 대신 추천한 이름이 "창원음악학원(10)·창원뮤직스쿨(8)·창원뮤직아카데미(8)"처럼 **지역+업종 일반 명칭**이어서 실제 가게가 아닌 지어낸 이름일 가능성이 있다(실존 여부 미확인). 기억 모드는 큰 도시의 유명 가게 외에는 실제 가게를 추천하지 못할 수 있어, 검색을 켠 실제 AI와의 비교(V1)가 노출 판단의 핵심이다.
**한계**: 묶음당 30회·1회 실행·기억 모드, 추천 이름의 실존 여부 미검증. 후속 후보(미착수): AI 추천 목록이 일반 명칭이면 "이 지역·업종은 AI가 실제 가게를 잘 모른다"를 사실로 표시(V1 이후 판단).

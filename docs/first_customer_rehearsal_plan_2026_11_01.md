# 첫 고객 리허설 계획 (2026-11-01)

## 1. 왜 하는가
지금까지의 점검은 전부 **운영자 계정** 기준이다. 코드·라우트·스키마 점검은 많이 했지만, 낯선 사용자가 가입해서 돈을 내고 가치를 받는 경로를 **제3자 계정으로 끝까지** 본 적이 없다. 상업 서비스의 가장 큰 미검증 위험이다.

기존 `docs/launch_checklist_2026_10_25_v1.0.md`와의 관계: 그 문서의 #3(SMTP)·#4(가입→인증→첫 스캔)·§5-2(실결제 시험)은 이미 일부 확인됐다. 이 리허설은 **그 뒤 구간**(알림 수신 설정, 정기 스캔, 제3자 알림, 가이드·QR, 해지·환불, 정리)을 채운다.

## 2. 이미 확인된 것 / 아직 한 번도 못 본 것
| 확인됨(재확인 불필요) | 한 번도 못 본 것(리허설 대상) |
|---|---|
| 가입·이메일 인증(10-26, 커스텀 SMTP) | **제3자 번호로 알림톡 수신** (운영자 폰에만 확인, 11-01) |
| 실결제 시험: Basic 8,950원 결제→취소(10-27, 빌링키 심사 포함 확인) | **알림 수신 설정 흐름**: 알림 기본값이 `false`이고 가입 화면에 전화번호가 없다 — 설정에서 번호를 넣고 알림을 켜야 한다(코드·스키마 확인) |
| 운영자 계정의 정기 스캔·알림 | 비관리자 사업장의 정기 스캔 전 과정과 결과 화면 |
| 서버 기록 상 알림 `sent` + 운영자 폰 실수신 | 가이드·소개글 생성(Claude 크레딧 필요), QR 카드 다운로드 버튼 클릭 |
| | 해지(CANCEL_01)·7일 내 환불(CANCEL_02는 승인 대기), 해지 후 알림 차단 |
| | 정기 재결제(30일 뒤) — **리허설로는 확인 불가**, 첫 실제 갱신을 감시 |

## 3. 사전 조건 (리허설 전에 끝내야 의미가 있다)
1. Claude 크레딧 충전 — 없으면 가이드·소개글·QR 단계가 실패해 결과가 왜곡된다.
2. 알림 템플릿 상태 기록: `SCORE_02`·`SCAN_02` 승인·전환 여부. 어느 문장이 나가는지 알아야 대조할 수 있다(전환 전이면 옛 SCORE_01·SCAN_01 문장).
3. Gemini 상태 기록(무료/유료) — 표본 수를 해석하는 기준.
4. 참가자 1명 확보: 실제 가게를 가진 지인이 이상적이다(사업장 등록에 실제 가게명이 필요). 참가자에게 **테스트임과 8,950원 소액 결제 후 환불**, 전화번호가 알림 수신에만 쓰임을 사전에 알리고 동의를 받는다.
5. 네이버 접속량 주의(지침 8): 사업장 등록의 장소 찾기와 첫 스캔이 네이버에 접속한다. 참가자 1명 분량이라 한도에는 영향이 없지만, 같은 날 다른 점검을 겹쳐 돌리지 않는다.

## 4. 시나리오와 합격 기준
관찰 도구: `backend/scripts/rehearsal_watch.py <참가자 이메일>`(읽기 전용: 가입·프로필·사업장·구독·스캔·알림 상태를 한 화면에 출력, 번호는 마스킹). 단계마다 이 스크립트와 서버 로그로 제가 확인한다.

| # | 참가자 행동 | 합격 기준 | 제가 서버에서 확인 |
|---|---|---|---|
| 0 | (사전) 기준 시각·서버 상태 기록 | `/health` 정상, 최근 에러 0 | 로그 기준선, 크레딧·Gemini 상태 |
| 1 | 가입 → 인증 메일 → 링크 클릭 → 로그인 | 메일이 수 분 안에 도착, 인증 후 로그인 | `rehearsal_watch`의 가입·인증 시각, 도착까지 걸린 시간 |
| 2 | 온보딩: 실제 가게 등록, 키워드 선택 | 가게를 찾고 키워드 추천이 나온다 | 사업장·플레이스ID·키워드 저장, 네이버 접속 로그 정상 |
| 3 | 첫 측정 결과 화면 보기(PC·모바일) | 결과가 나오고 문구가 단정하지 않다("이번 측정에서는…"), 측정 못 한 항목은 '확인 전' | 스캔 행, AI 표본 수, 네이버 오류 여부. **참가자에게 "이 화면에서 이해 안 되는 곳"을 묻는다**(제품 가치 확인) |
| 4 | Basic 결제(첫 달 8,950원) | 결제 완료, 구독 `active`, 영수증·안내 문구 정상 | `subscriptions` 행(금액·`start_at` 시각), 결제 로그 |
| 5 | 설정에서 전화번호 입력 + 알림 켜기 | 저장 후 다시 열어도 유지, **저장 안 하면 알림이 안 온다는 점이 화면에서 이해되는지** | 프로필 `phone`·`kakao_scan_notify` 값 |
| 6 | 다음 정기 스캔일(Basic은 주 2회) 이후 알림 수신 | 스캔 후 알림톡이 **참가자 폰에 도착**, 문장이 자연스럽다 | 서버 `notifications`의 `sent`, 참가자 캡처를 `render_alimtalk_messages.py` 재현과 대조 |
| 7 | 가이드 생성, 소개글 생성, QR 카드 다운로드 | 모두 생성되고 QR 이미지가 내려받아진다(한글 가게명) | AI 사용 기록·실패 행 없음, `/qr-card` 200 |
| 8 | 해지(7일 내) | 구독 상태가 바뀌고 환불 안내가 정확하다. CANCEL_02 승인 전이면 "발송 안 함"이 기록된다 | 구독 행, `notifications`, 환불 금액·카드사 취소 내역은 **사용자가 크렙 화면에서 직접 확인** |
| 9 | 해지 후 알림 차단 | 해지·만료 계정 번호로 알림이 더 가지 않는다 | `notify_gate`, 이후 `notifications` |
| 10 | 정리: 계정·사업장 삭제 요청 | 계정이 삭제되고 **Storage·DB에 참가자 데이터가 남지 않는다** | 사업장·프로필·구독·Storage 잔여 파일 확인(과거 교훈: DB 삭제 ≠ Storage 삭제) |

## 5. 결과 기록 방식
- 단계별 통과/실패, 걸린 시간, 참가자가 막힌 지점을 표로 남긴다(`docs/first_customer_rehearsal_result_<날짜>.md`).
- 참가자 이메일·번호는 **문서·메모리에 저장하지 않는다**(관찰 스크립트도 마스킹 출력만 한다).
- 실패 항목은 재현·원인·수정으로 이어서 처리하고, 같은 단계를 다시 시험한다.

## 6. 안전장치
- 실결제는 소액(8,950원), 취소·환불은 크렙 가맹점 화면에서 사용자가 직접 확인(라이브 결제는 자동 취소가 없다).
- 운영 DB를 쓰는 점검 도구를 같은 날 함께 돌리지 않는다(`route_smoke_readonly.py` 등은 리허설 중 비활성).
- 참가자 요청으로 중단하면 바로 계정·사업장을 정리한다.

## 7. 리허설로 해소되는 가정 (현재 모두 미확인)
- 제3자 번호로 알림톡이 간다.
- 알림 기본값 `false`와 설정 화면 흐름이 사용자에게 이해된다(이해하지 못하면 알림이 전혀 안 가므로 제품 문제).
- 비관리자 사업장의 정기 스캔 결과·AI 표본·네이버 측정이 정상이다.
- 해지·환불·알림 차단이 설계대로 동작한다.

## 8. 사용자 준비
1. 참가자 1명과 일정(스캔 일정 때문에 최소 3~4일 걸린다), 2. Claude 크레딧 충전, 3. SCORE_02·SCAN_02 승인·전환 상태 알려 주기, 4. 결제 취소 확인(크렙 화면).

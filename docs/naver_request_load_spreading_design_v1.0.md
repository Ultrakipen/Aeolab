# 네이버 요청량 분산 설계 (2026-10-26, 설계만 — 구현은 트리거 도달 시)

## 0. 요약
네이버 Playwright 일일 상한 250건은 **우리가 둔 안전장치**(`NAVER_PLAYWRIGHT_DAILY_CAP`, `ai_scanner/__init__.py:236`)다. 목적은 구독자가 늘어도 네이버로 가는 자동화 트래픽을 완만하게 유지하는 것.
구독자가 늘면 걸리는 구조는 맞고, 병목은 평균이 아니라 **월요일 쏠림**이다. 요일 분산만으로 같은 상한에서 감당 사업장이 2.5배(17→42곳, 키워드 3개 기준)로 늘어난다.

## 1. 검증된 현재 구조 (코드 근거)
- 정기 스캔 `daily_scan_all`(02:00): basic=월·목 풀스캔, startup=월 풀스캔, pro=월·수·금 풀스캔+나머지 경량(`scan_basic`), biz=매일 풀스캔 (`jobs.py:~505-520`, 요일이 고정이라 같은 플랜 전원이 같은 날 몰림).
- 순위 잡: basic 월 04:00 주1회, 그 외 플랜(startup·pro·biz) **매일** 04:30 (`jobs.py:215-222`). 키워드당 PC+모바일 2건, 최대 10키워드=20건.
- GitHub Actions 사전 스캔(`naver_scan.yml`, 매일 01:00 KST)은 **활성 구독 전 사업장**을 플랜 무관 매일 스캔(`scripts/github_naver_scan.py`). 결과는 서버 스캔이 덮어쓰기만 하고 서버는 자체 네이버 스캔을 **그대로 또 실행**한다(`scan_all`에 생략 인자 없음, `multi_scanner.py:126`) → 중복.
- 서버 상한 카운트 대상: 브리핑(`naver_scanner.py:425,501`), AI탭(`naver_ai_tab_scanner.py:173`), 순위(`naver_keyword_rank.py`), 플레이스 ID 확정, 재확인 새로고침. **GitHub 사전 스캔은 카운트되지 않는다** → 상한은 실제 총 네이버 트래픽을 과소 반영.
- 순서 공정성: 순위 잡·스캔 모두 DB 순서대로 순차 처리 → 상한 도달 시 항상 뒤쪽 사업장이 건너뛰어진다(굶는 사업장 고정).
- (발견·수정 완료) 정기 순위 잡이 `region`을 넘기지 않아 수동 측정과 다른(지역 없는) 검색어로 돌았음 → `jobs.py` 수정, 스텁 실행으로 전달 확인.

## 2. 부하 모델 (가정: basic70/startup10/pro15/biz5, 풀스캔=브리핑≤4+AI탭≤4, 경량=1, 순위=2×키워드수)
감당 가능한 사업장 수(상한 250건 / 보호선 200건):
| 키워드수 | 현재 | A 요일 분산 | A+사전스캔 재사용 | A+고급플랜 순위 주3회 |
|---|---|---|---|---|
| 3개 | 17 / 14 | 42 / 33 | 59 / 47 | 67 / 54 |
| 5개 | 13 / 11 | 33 / 26 | 43 / 34 | 49 / 39 |
| 10개 | 8 / 7 | 21 / 17 | 25 / 20 | 28 / 23 |
100곳·키워드 3개 요일별 최대: 현재 월 1,400건 → A 591건 → A+C 369건(여전히 250 초과 — 이 규모에서는 상한 상향 또는 순위 빈도 축소가 필요).
한계: 풀스캔·경량 스캔의 카운트 구성은 코드로 상한을 추정한 값이며 실측 미검증(일별 키워드 순환·사전 스캔 재사용 때문에 실제는 더 적을 수 있음). 플랜 혼합·키워드 수는 가정.

## 3. 설계
### A. 결정적 요일 슬롯 (DB 변경 없음)
- 슬롯 = `int(md5(biz_id)[:8],16) % 7` (사업장 ID 기반, 재시작·재배포에도 동일, 새 구독자도 자동 배정).
- basic: 풀스캔 2회를 이틀 간격 쌍으로 — 슬롯%3 → (월·목)(화·금)(수·토). 순위 잡은 스캔일과 다른 요일(슬롯 기반).
- startup: 주 1회 풀스캔 요일 = 슬롯.
- pro: 풀스캔 3일 패턴 3종 (월·수·금)(화·목·토)(수·금·일), 나머지 날 경량.
- biz: 매일 — 분산 불가(고정 부하).
- 사용자 약속("주 N회")은 유지. 단 UI·약관·요금제 페이지에 "월·목" 같은 **요일 고정 표기**가 있으면 "주 2회"로 정정해야 한다(구현 전 `grep "월·목\|월요일"` 점검).
- 신규 가입 직후 1회 스캔(체험·첫 분석)은 기존 경로 유지(슬롯 무관).
### B. 사전 스캔 재사용으로 서버 중복 제거
- `scan_all`/`scan_basic`에 `skip_naver_brief` 같은 인자를 추가해 사전 스캔 결과가 있으면 서버 브리핑 Playwright를 생략(최대 4건/스캔 절감). 사전 스캔이 실패한 사업장만 서버가 직접 측정.
- 위험: 사전 스캔 결과의 신선도(당일 01:00)·캡챠 중단 시 누락 — 결과 없음이면 기존 경로로 폴백해야 함.
### C. (제품 결정) 고급 플랜 순위 빈도
- startup·pro·biz가 매일 20건(키워드 10개 기준)을 쓰는 것이 고정 부하의 대부분. 스캔 요일에만 측정(주 3회)하면 부하 1/2 이하. 플랜 설명("매일 자동")과 충돌하므로 사용자 승인·문구 수정 필요. 구독자 수요 확인 전에는 보류.
### D. 공정성·안전장치
- 처리 순서를 날짜 시드로 회전(또는 마지막 측정 시각이 오래된 순)해 상한 도달 시 같은 사업장이 계속 굶지 않게 한다.
- 상한 70%·90% 도달 시 운영자 알림(현재는 100%에서 1회). 하루 사용량·재확인 횟수를 로그·관리자 화면에 노출(`naver_playwright_quota_usage()` 이미 있음).
- 상한 계산에 GitHub 사전 스캔(건수 추정)을 합산해 "총 네이버 트래픽"을 같은 기준으로 감시.
### E. 상한 상향은 마지막 수단
- 상한은 리스크 비례 증가를 막는 장치이므로 상향은 의도된 리스크 수용 결정(`NAVER_PLAYWRIGHT_DAILY_CAP`). 서버 업그레이드로 동시성을 늘려도 네이버로 가는 총량은 같다.

## 4. 구현 트리거와 순서
- 트리거(먼저 도달하는 것): 활성 구독 사업장 ≥10곳, 또는 월요일 사용량 ≥150건, 또는 상한 알림 1회 발생.
- 순서: ① 모니터링·70/90% 알림 + 사용량 로그(코드 소규모, 위험 낮음) → ② B 사전 스캔 재사용 → ③ A 요일 슬롯 → ④ D 순서 회전 → ⑤ C 결정.
- 검증: 슬롯 분포 균등성 테스트(UUID 샘플), 요일별 예상 부하 계산 스크립트, 스테이징 없이 라이브이므로 DRY 모드(대상 목록만 로그) 하루 선행.

## 5. 오판 점검
- "상한=네이버 한도"는 오해 — 자체 안전장치. 네이버의 실제 차단 기준은 비공개(미확인).
- 모델 수치는 가정 기반. 실제 일일 사용량은 구독자 데이터가 쌓인 뒤 `_context.rechecks`·상한 사용량으로 재산정.

## 2. 새 대화창(네이버 독립)을 위한 사실 정리

### 2-1. 네이버 접속 지점과 실제 사용량
- 서버 실측(2026-10-29, 저녁 시점 `.naver_quota_state.json`): **총 59페이지**(배치 57) — 경쟁사 크롤 48, AI탭 스캔 4, AI탭 트리거 점검 4, 브리핑 점검 1, 순위(PC·모바일) 2. 상한 600의 약 10%.
- 경쟁사 크롤 48페이지는 전부 **만료된 해지 계정 5곳 + 관리자 계정 3곳**의 경쟁사였다(8곳×6페이지). → §4의 `abb6501`로 수정.
- 사용자 요청 몫(`.naver_usage_meter.json`): 4페이지, 전부 사업장 등록 화면의 가게 찾기(`/business/resolve-place`, 사용자당 시간당 10회·결과 캐시) — 정상 경로.
- 접속은 Playwright(페이지 로드)와 공식 API로 나뉜다. **공식 API 쪽**: 지역검색(`search_request("local")`, 최대 5건 반환), 블로그 검색, DataLab, 검색광고 키워드 도구, 플레이스 ID 자동 조회(`_find_naver_place_id`). **Playwright 쪽**: 키워드 순위 카드 순서(PC·모바일), AI 브리핑·AI탭 노출, 플레이스 통계(리뷰 수·별점·사진), 경쟁사 상세 크롤(페이지 6회), 플레이스 ID 확정(검색 화면+주소 대조).
- **사전 스캔(GitHub Actions `naver_scan.yml`, 매일 01:00 KST)**: GitHub 호스팅 IP에서 브리핑을 측정해 `naver_prescan`에 저장, 서버 02:00 스캔이 같은 접속을 생략한다. 이미 "접속 경로 분산"이 일부 쓰이고 있다는 뜻이며 **법적 평가는 변호사 자문 대상**(사용자가 의도적으로 보류).
- 프록시: `NAVER_PROXY_LIST`는 비어 있다(서버 `backend/.env`). 순위 측정에 프록시 범위("search")를 연결해 두었으나 **프록시를 사지도 쓰지도 않았다**. 범위 설정은 `NAVER_PROXY_SCOPE`(place/search/all).

### 2-2. 공식 API로 대체 가능한 영역의 한계(독립 서비스 설계 때 먼저 볼 것)
- 지역검색 API는 **5건만** 반환 → 순위(상위 5곳 밖)를 알 수 없다. 8월에 순위를 API로 전환했을 때 미노출이 316건 몰린 이상치가 있었다(원인 **미확인**, 이 한계와 맞을 수 있음).
- 블로그 건수·언급 가시성은 이미 공식 API 기반(`naver_visibility.get_naver_visibility_multi`).
- 리뷰 수·별점·소식·사진 같은 플레이스 상세는 공식 API가 없어 Playwright에 의존한다(미확인: 다른 합법 데이터원 존재 여부).
- Kakao 지도·검색은 공식 API 사용 중. 구글 AI Overview는 Serper API.

### 2-3. 하루 600건 상한은 근거 없는 제안값
- 초기 250은 "테스트 데이터 기준 추정 하루 요청의 약 3배 여유", 10-27에 단위를 호출→페이지로 바꾸며 같은 여유로 600(`services/ai_scanner/__init__.py:238-243` 주석: "실측 근거가 없는 제안값").
- 10-27 서버 IP 차단의 유력 원인은 총량이 아니라 **짧은 시간에 몰린 연속 호출(65~70페이지, 1~2분)로 보호장치를 우회한 것**이다(`docs/naver_place_access_protection_2026_10_27.md`). 그것도 확정은 아니다. 속도 기준(1분 12·10분 30·1시간 120)도 제안값.
- 따라서 "300곳 = 상한의 2.4배" 같은 문장은 **우리 상한 대비 상대적 크기**일 뿐 네이버 허용량이 아니다. 네이버의 실제 기준은 비공개이고, 서버에서 시험하면 차단을 재유발하므로 알아낼 방법이 없다. 유일한 근거 수집법은 차단이 없었던 날의 사용량 기록(`.naver_quota_state_history.jsonl`, `naver_block_events`)을 쌓는 것이다.
- 모델(`scripts/naver_load_model.py`)상 사업장 1곳이 주 33페이지(키워드 순위 39%·스캔 28%·경쟁사 27%·통계 6%, 20곳 기준). 300곳 정책 대응표는 `docs/naver_capacity_300_playbook_2026_10_29.md`와 `backend/services/naver_capacity.py` `PLAYBOOK`. **전부 모델 값이며 실측이 아니다.**

- **사용자 결정(2026-10-29)**: 문의·상향 모두 보류, **유료 사용자가 생기면 Supabase 요금제 상향**(Pro $25/월, Micro 포함 — 공식 문서 기준, 결제 화면에서 재확인 필요). Free는 커뮤니티 지원뿐, Pro에도 업타임 SLA 없음, Micro도 공유 CPU라 **상향이 멈춤을 해소한다는 보장은 없다**. 상향 후 같은 스크립트로 전후 비교.

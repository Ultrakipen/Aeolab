# 별점 낮은 리뷰 감지 잡 — 점검·수정 기록 (2026-10-28)

> 계기: "사용자 증가 시 플레이스 대응"(별점 잡이 용량 모델에 빠져 있고 순서 회전이 없다)을 구현하려다, 잡이 **한 번도 동작한 적이 없다**는 것을 발견했다.

## 확인된 사실
| 사실 | 근거 |
|---|---|
| 별점 알림 누적 0건, 활성 구독 4, 대상 사업장(플레이스 ID 있음) 3, 전화번호 등록 사용자 1/2 | 서버 DB 읽기 전용 조회(10-28) |
| 실제 화면에서 별점은 `별점` / `5` / `점` **세 줄**로 렌더링된다. 기존 정규식 3종은 같은 줄의 "5점"을 전제해 리뷰 2,283건짜리 가게(어니언 성수)에서 **0건 일치** | 로컬 Playwright 1페이지 실측 — 본문 5,842자, 줄 구조 출력 |
| 리뷰 탭 기본 정렬은 **추천순**(날짜 10.2·10.14·10.11·9.8 뒤섞임). "최신순" 클릭 후 10.14·10.11·10.2·10.1·9.27… 내림차순 | 같은 실측 |
| 기존 테스트 픽스처 `"2점 매우 불만\n…"`는 실제에 없는 형식 — 결함을 가린 근본 원인 | `tests/test_place_path_coverage.py` 구버전 |
| 기존 `review_id`는 `{플레이스ID}_{순번}` — 한 번 알림이 나가면 이후 새 낮은 별점 리뷰도 같은 ID(`_0`)로 중복 처리되어 걸러진다 | 코드 대조(`notifications.contains`) |
| 알림 문구는 "별점 N점 리뷰가 **등록됐습니다**" — 파서가 동작하면 화면에 있던 예전 리뷰를 방금 등록된 것처럼 알리게 된다 | `kakao_notify.send_low_rating_alert` |

## 수정 (git 커밋 이 문서와 함께, 서버 배포·436개 테스트 통과)
- **파서**: `naver_place_stats.parse_low_rating_reviews` — 실제 줄 구조 기준. 인용문은 방문 정보 줄(점 다음 첫 줄)을 제외한 가장 긴 줄(실측에서 방문 정보가 인용되던 것을 발견·수정). `review_id`는 (플레이스·작성자·본문) 해시. 실제 페이지에 적용해 별점 표식 7~8개·분포 확인.
- **정렬**: 리뷰 탭에서 "최신순"을 누른다. 별점 표식이 있는데 최신순을 못 눌렀으면 `checked=False, reason="sort"`(추천순 목록으로 "새 낮은 별점 없음"을 판단하지 않는다).
- **조회 결과 구조화**: `check_low_rating_reviews_for` → `{checked, reviews, markers, reason}`. 이전엔 막힘·차단·시간 초과가 전부 `[]`라 "낮은 별점 없음"과 구분되지 않았다. 기존 `get_recent_low_rating_reviews`는 목록만 돌려주는 래퍼로 유지.
- **잡**(`jobs.check_low_rating_reviews`): `@_naver_batch_job`(배치 몫), 전화번호 일괄 조회·미등록 사업장은 접속 제외, **마지막 확인 성공이 오래된 순서**(상태 파일 `backend/.naver_low_rating_state.json`, env `NAVER_LOW_RATING_STATE_FILE`), 회로·상한·속도·차단으로 막히면 그 자리에서 멈추고 다음 실행이 못 한 곳부터 이어 감, 실행 요약 로그(`[low_rating] 대상·확인·오류·건너뜀`).
- **기준선**: 처음 확인하는 사업장은 보이는 낮은 별점 리뷰를 "이미 본 것"으로 기록만 하고 알리지 않는다. 이후 **본 적 없는** 리뷰만 알린다(상태 파일의 `seen`).
- **조용한 고장 방지**: 확인된 사업장 2곳 이상에서 별점 표식이 전부 0이면, 또는 전 사업장에서 최신순 클릭이 실패하면 슬랙 경고.
- **용량 모델**(`scripts/naver_load_model.py`): 이 잡을 추가(사업장당 하루 4회×2페이지=8페이지, 전화번호 보유율 100% 가정).

## 용량 영향 (모델, 실측 아님)
| 별점 잡 주기 | 20곳 기준 주간 접속 중 비중 | 모든 개선 적용 시 상한 초과 시점(배치 몫 / 전체) |
|---|---|---|
| 하루 4회(현재, 6시간) | 47%(가장 큰 단일 소비처) | 20곳 / 30곳 |
| 하루 2회 | — | 20곳 / 30곳 |
| 하루 1회 | — | 30곳 / 30곳 |
- 이 소비는 모델에서 빠져 있었을 뿐 **이전에도 실제로 일어났다**(잡이 아무것도 못 찾으면서도 페이지를 썼다) — 이전 "30~40곳" 추정은 낙관적이었다.
- **결정(2026-10-28, 사용자)**: "사용자에게 빈번한 알림은 신뢰 추락이 될 수 있다"며 **주 2회(월·목 10:00)**로 변경·배포. 다음 실행 10/29(목) 10:00 KST(서버에서 트리거로 계산해 확인). 월요일은 주말(금~일) 리뷰, 목요일은 월~수 리뷰를 본다. 알림 지연은 최대 3~4일(월→목 3일, 목→월 4일)이라 "긴급"은 아니다 — 승인 본문에는 주기 문구가 없어 재승인은 불필요(템플릿 이름·"빠른 답변" 문구의 의미만 약해짐).
- 모델 반영(`scripts/naver_load_model.py`): 월·목에만 사업장당 2페이지. 20곳 기준 이 잡의 주간 비중 47% → 약 6%.
- 알림 조건 재확인: **평균 별점 변화가 아니라 새로 보인 1~2점 개별 리뷰**, 사업장당 실행당 최대 1건, 첫 확인은 기준선. 리뷰 수정(5점→1점 동일 본문 등)은 처음 보는 낮은 별점으로 판단해 알림이 갈 수 있고, 낮은 별점 리뷰의 본문 수정은 해시가 바뀌어 재알림될 수 있다(코드 기준 추론, 네이버의 수정 반영은 미확인).
- 지금은 대상이 1~2곳이라 문제 없다. 대상이 **약 10곳을 넘으면** 주기를 하루 1회로 줄이는 것을 권한다(`jobs.py` `check_low_rating_reviews` 등록부의 `hour="*/6"` 한 줄). 알림 지연이 최대 6시간→24시간이 되는 트레이드오프이며 사용자에게 약속된 문구는 없다(프론트 grep 0건).

## 추가 발견 — 발송 실패가 '발송됨'으로 기록되던 결함 (같은 날, 알림 실발송 확인 방법을 찾다가)
- `kakao_notify._send_raw`는 실패(HTTP 오류·응답 `isSuccessful=false`·예외)·키 미설정을 로그와 `notifications`(type notice)에만 남기고 **반환값이 없었다.** 별점 잡은 결과를 확인하지 않고 항상 "발송됨" 이력을 저장해, 실패한 알림이 중복 방지에 걸려 **영영 재시도되지 않았다.** 파서가 항상 0건이라 드러나지 않았을 뿐이다.
- 수정(git 이 문서와 함께): `_send_raw`·`send_low_rating_alert`가 성공만 `True`를 반환(기존 호출처는 반환값을 쓰지 않아 동작 동일). 잡은 실패 시 이력을 남기지 않고, 이번 실행에서 새로 본 리뷰를 "이미 본 것"에서 되돌려 **다음 실행에서 재시도**하며, 슬랙으로 "알림 발송 실패"를 알린다. 변이 검증 6건 잡힘.
- **테스트 오염 교훈**: 전체 실행에서만 실패 — 다른 테스트(`test_competitor_spike_falsy_zero`)가 `services.kakao_notify`를 가짜 모듈로 등록해 두고, 진짜 모듈을 격리 import 하면 `import a.b as c`(패키지 속성)와 `from a.b import X`(sys.modules)가 서로 다른 객체를 가리킨다. 잡이 함수 안에서 `from … import`를 하면 테스트는 `sys.modules` 항목을 직접 교체해야 한다.

## 알림 실발송 확인 방법 (라이브 미확인 항목의 해소 절차)
1. **본문 템플릿 일치**: 코드의 본문 구조는 승인 문서(`docs/kakao_alimtalk_submission_final_v1.0.md` §3-5)와 같다. 알림톡은 치환 후 본문이 등록 템플릿과 공백·줄바꿈·기호까지 일치해야 한다(일반 원칙, [비즈고 설명](https://blog.bizgo.io/inside/alimtalk-template-auto-replace/)).
2. **미확인 위험**: 인용문 `#{리뷰내용}`은 50자로 자르는데 **NHN Cloud의 치환 변수 길이 제한은 공식 수치를 찾지 못했다**(검색에 나온 1,000자는 다른 사업자 기준). 발송이 실패하면 슬랙 "알림 발송 실패"와 `Kakao _send_raw failed` 로그가 남는다.
3. **발송 방식 차이(미확인)**: GROWTH_01 등은 `_send`(`templateParameter` 변수 방식)인데 ALERT_01·SCAN_01·COMP_01/02·NOTICE는 `_send_raw`(완성된 본문 `content`)다. 승인 문서의 ALERT_01 변수는 `#{사업장명}·#{별점}·#{리뷰내용}·#{리뷰링크}`. `content` 방식이 NHN Cloud에서 승인 템플릿으로 받아들여지는지 공식 문서로 확인하지 못했다 — 시험 발송에서 두 방식을 비교하고, 변수 방식이 맞으면 ALERT_01을 `_send`로 옮긴다(본문 일치 위험 제거).
4. **시험 발송(사용자 결정 필요)**: 가짜 리뷰로 사용자 본인 전화번호에 AEOLAB_ALERT_01을 1건 보내 승인 템플릿 일치·변수 길이를 확인한다. 실제 카카오 발송이므로 사용자 승인 후에만 한다.

## 한계·미확인
- **알림이 실제로 발송되는 것은 라이브에서 확인하지 못했다.** 파서·정렬은 실제 페이지로, 잡 흐름은 가짜 DB·가짜 카카오 테스트로만 검증했다. 다음 실행(18:00 KST)은 상태 파일이 없어 첫 확인으로 기준선만 기록한다. 서버에서 점검 함수를 연속 호출하지 않았다(네이버 접속 보호).
- 최신순으로 읽은 목록의 **첫 화면에 보이는 리뷰 수**만 본다(실측 약 7~8개). 하루에 낮은 별점이 그보다 많이 달리면 일부는 못 본다.
- 방문자 리뷰 탭만 본다(블로그 리뷰 제외).
- 카카오 알림 본문 "등록됐습니다"는 승인 템플릿 문구라 바꾸지 않았다. 기준선 처리로 "예전 리뷰를 방금 등록된 것처럼" 알리는 문제는 막았다.
- 용량 모델의 전화번호 보유율 100%는 보수적 가정이다.

## 0. 결론

1. **방향 전환**: "새 기능을 더 만든다"가 아니라 "차단이 왔을 때 서비스가 가치를 유지하는 설계"를 우선한다. (제 판단. 사장님 수요 자료가 없어 입증된 것은 아님)
2. **재방문 엔진(소식 초안)은 차단 대비책이 아니다.** 차단은 측정 기능을 막고, 이 기능은 게시 초안을 만든다. 차단 중 이탈을 줄이는 **선택적 대체 가치**로만 둔다.
3. **정정(이 문서 작성 중 발견)**: 제가 1순위로 권고한 "영향 지도"는 **이미 존재**한다. `commercial_launch_..._11_01.md` §3.1 "네이버 의존 지도", §3.3 "시나리오별 런북", §3.4 "보완 작업"과 `docs/naver_dependency_table_2026_10_29.md`가 있다(제목 확인만 했고 본문은 이번에 다시 읽지 않음). 따라서 새 지도를 만들지 않고 **기존 지도가 현재 코드와 맞는지 대조하고 빠진 부분만 채우는 것**으로 범위를 줄인다. 새 문서를 쌓지 않는다.

## 1. 작업 순서 (모두 읽기 전용, 개발 없음)

### 1-1. 기존 의존 지도·런북의 현행화 점검
- 목적: 11-01 이후 바뀐 코드(킬스위치, 대량 실패 알림, 측정 빠진 스캔 비교 금지 규칙 등)가 지도에 반영됐는지, 지도에 없는 네이버 접속 지점이 생겼는지 확인.
- 방법: 지도의 각 행을 코드의 실제 접속 함수와 대조(함수 단위, 지침 8번). 새 접속 지점은 `tests/test_place_path_coverage.py` 구조 감사가 이미 있으므로 그 결과를 먼저 본다.
- 산출물: 기존 문서에 덧붙이는 "11-04 대조 결과" 절(신규 문서 아님).
- 금지: 서버에서 네이버 점검 함수 연속 호출, 네이버 접속(지침 8번).

### 1-2. 차단 중에도 남는 가치 목록 확정
- 후보(기재 근거는 CLAUDE.md 서술, 코드 재확인 전): 공식 API 기반 기능, ChatGPT·구글 측정, 채널 정보 일치 점검, 리뷰 답변, 소개글·FAQ 생성.
- 각 항목을 "네이버 없이 실제로 도는가"로 분류: 정상 / 제외 후 재정규화 / 중단 / 오표시 위험.
- 판정 기준: 코드 호출 경로와, 가능하면 킬스위치를 켠 상태의 테스트(`T-5` 차단 모의 훈련 자산 재사용)로 확인. 추정만으로 "남는다"고 쓰지 않는다.
- 산출물: 위 §1-1 절에 표 1개.

### 1-3. 사용자 커뮤니케이션 설계
- 차단 중 화면·알림이 무엇을 말할지 정한다. 원칙: 측정 못 한 것은 0점·미노출이 아니라 "확인 전"(지침 9번), 변화 문구는 `change_signal_guard`를 거친다.
- 구독 유지·환불·연장 정책은 사용자 결정 사항이므로 선택지만 정리한다(법적 판단은 변호사 확인 대상).
- 설계만 지금, 코드 변경은 차단 후.

### 1-4. 소식 초안 기능은 선택 모듈로 격하
- 1-1~1-3 결과를 본 뒤 "차단 중 대체 가치로 필요한가"를 판정. 필요 없으면 설계서는 보관만.
- 진행 시 기존 설계(`channel_post_engine_plan`)의 폐기 기준(§8-3, 제안값)·착수 신호(§10-1)를 그대로 사용.

## 1-5. 차단은 영구일 수도 있다 — 3단계로 나눠 설계 (11-04 사용자 질문 반영)

사용자 전제: 차단 시에는 서비스를 유지하되 차단이 풀릴 수도 있다. 영구 차단 가능성은 배제할 수 없다.

| 유형 | 풀릴 가능성 | 근거 수준 |
|---|---|---|
| ① 속도 제한형(IP 일시) | 풀림 | 10-27 서버 IP 제한 사례 후 정기 스캔 복구 정황 [풀린 시점·이유는 직접 확인 못 함]. 개인 블로그의 "5~30분"은 공식 기준 아님 → 채택 안 함 |
| ② 반복 위반형(IP 영구) | **판단 불가** | 공식 기간·기준 자료 못 찾음(검색 2회) |
| ③ 정책형(자동 접근 자체 제한) | 안 풀릴 수 있음 | 8월 기사 제목 "네이버 '크롤링 전쟁'"과 2차 분석 — 본문 미열람, 이용약관 원문 미확인 |

| 단계 | 기간(제안값, 근거 없음) | 설계 방향 |
|---|---|---|
| S-1 일시 | 0~3일 | 측정만 건너뛰고 기록, 화면은 "확인 전", 복구 시 자동 재개, 복구 때 가짜 변화 금지(`change_signal_guard`) |
| S-2 지속 | 수 주 | 네이버 항목 제외·재정규화, 공식 API·글로벌 AI 측정 중심 안내, 대체 가치 제공 |
| S-3 영구 판단 | — | 제품 정의 재결정 — **사용자 판단 사항**, 이 문서는 선택지 정리까지만 |

단계 전환 기준은 근거가 없어 사용자가 정한다. 현재 장치(회로 차단기·킬스위치·상태 배너)가 S-1을 덮는지, S-2 이상에서 막히는 지점은 §1-1 조사에서 확인한다.

## 1-6. 추가 권고 5건과 하지 않을 것 (11-04)
1. **차단 단계별 사용자 약속을 미리 정하기**(우선순위 1): 예) S-1 지속 시 구독 연장, S-2 시 환불 선택권. 기존 소프트 런치 도구(안내 메일 2~4단계, 3일 연장 `subscriber_notice_email.py`·`subscription_extend_days.py`)와 겹치므로 그 단계표에 얹는다. 법적 판단은 변호사 확인 대상, 선택지만 정리.
2. **"마지막으로 확인한 값" 표시를 네이버 전 항목으로 일반화**(우선순위 2): AI탭·AI 브리핑 쪽에는 "마지막 확인" 문구가 코드에 있음(`AiTabPreviewCard.tsx` 등 grep 확인). 순위·리뷰 수·스마트플레이스 점검에도 적용되는지는 **미확인**.
3. **차단 조기 징후 지표**: 응답 지연·재시도율·빈 결과 비율. 현재 존재 여부 미확인, 임계값은 제안값.
4. **네이버 공식 경로 탐색**: 공식 API로 대체 가능한 측정 항목, 제휴·문의 경로. 법적 민감 항목이므로 **사용자 결정 없이 진행하지 않음**.
5. **차단 훈련 주기화**(우선순위 3): 새 접속 지점·알림 추가 시, 또는 월 1회 T-5식 모의 훈련 재실행.
- **하지 않을 것**: 사장님이 네이버 순위를 직접 입력하는 대체 경로. 사유: 사용자 직접 기록이 1건뿐이라 입력 가정에 근거가 없고(`channel_post_engine_plan` §1-2), 측정값·입력값 분리 표시 규칙과 충돌 소지.

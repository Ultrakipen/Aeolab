# AEOlab 상업 서비스 준비 — 점검 이력·비중·잔여 과제 종합 v1.0

> 작성일 2026-07-13. 지금까지 5세대에 걸쳐 파편적으로 쌓인 점검 작업(`docs/master_inspection_plan_v1.0.md`, `docs/commercial_launch_readiness_audit_v1.0.md` 등 20개+ 문서)을 "무엇을 얼마나 점검했는지 + 무엇에 비중을 뒀는지 + 앞으로 뭘 봐야 하는지" 관점으로 재정리한 마스터 요약. 개별 점검의 세부 근거는 각 원본 문서를 참조하고, 이 문서는 **네비게이션 + 비중 분석 + 잔여 과제 목록**에 집중한다.

## 1. 점검 체계 — 두 축

AEOlab의 상업 서비스 점검은 처음부터 설계된 게 아니라 **결함 유형이 발견될 때마다 새 기준이 추가되며 진화**했다(§2 계보 참조). 현재는 두 축으로 수렴했다.

### 축 A — 페이지/기능 단위: 4-레이어 (L1~L4)

| 레이어 | 잡아내는 결함 | 방법 |
|---|---|---|
| L1 사실 정확성/실측 무결성 | 허위 수치, 표시-DB 불일치, 측정 실패를 성공으로 오집계 | 코드 grep + 실제 API 응답값 대조 |
| L2 기능 정합성 | PC/모바일 단절, 라우팅·권한 버그, 네이버 우선순위 위반 | 브라우저 실접속 + 반응형 확인 |
| L3 외부 벤치마크 | 업계 수준 미달(대비율·정보위계·톤) | Nielsen 10휴리스틱 + WCAG 2.1 AA + 실제 경쟁 서비스 스크린샷 비교 |
| L4 실측 재현/동시성 | 권한 우회, 락/세마포어 중첩, TOCTOU | 실제 클릭 시퀀스 + DB 대조 + 동시 요청 재현 |

### 축 B — 서비스 전체 단위: 4개 축 (A~D, "이게 진짜 상업 서비스인가")

| 축 | 관점 | 내용 |
|---|---|---|
| A. 보안 | 침투테스터 | IDOR·권한상승·웹훅서명·rate limit·XSS/SSRF·의존성 취약점 |
| B. 법적/컴플라이언스 | 변호사 | 개인정보처리방침 일치성, 전자상거래법 해지고지, 표시광고법 |
| C. 사업성 | 투자자/재무 | 실비용 계측, 마진율, 경쟁가격, 선행지표 |
| D. 인프라 복원력 | SRE | 백업 성공 여부, SPOF, 장애 알림 커버리지 |

**공통 원칙**: 모든 축에서 "단정 전 반증" — 근거 file:line + 반증 시도 1개씩 확인한 것만 "문제"로 분류(CLAUDE.md 표준).

## 3. 비중 분석 — 어디에 자원이 가장 많이 들어갔는가

실제 세션 수·재점검 횟수 기준으로 보면 명확한 불균형이 있다.

| 영역 | 투입 비중 | 근거 |
|---|---|---|
| **L1(사실정확성)·L2(기능정합성)** | 압도적 1위 — 20회 이상 라운드 | 대시보드·9페이지·구독·대행서비스·관리자 화면이 각 3~11차까지 반복 재점검됨(`naver_briefing_placetype_vs_infotype` 11차 스윕, `dashboard_full_scale_inspection` 등). falsy-zero 스윕, 대비율 800+건 등 "이미 끝났다고 생각한 곳"에서 계속 새 결함이 나와 반복 투입됨 |
| **L3(외부벤치마크)** | 중간 — 1~2회 집중 라운드 | 대시보드+9페이지는 2026-07-09 한 번에 전수 처리(대비율 246건+접근성). 랜딩·요금제·trial·온보딩은 2026-07-11 별도 세션에서 1회 처리 |
| **L4(실측재현/동시성)** | 낮음 — 영역별 1회씩 | 관리자·구독·대행 서비스에만 적용, 나머지(공개 콘텐츠·지원 등)는 미적용 |
| **A(보안)** | 낮음 — 1회 종합 스캔 | 2026-04-13 1차 점검 이후 **3개월간 무점검 상태였다가** 2026-07-11 `/cso` 종합 스캔으로 1회 처리. 이게 가장 큰 공백이었음(F1~F5 HIGH 4건 발견) |
| **B(법적)·D(인프라)** | 낮음 — 1회 | 2026-07-12 1회 처리. D축에서 "DB 백업이 생성 이래 단 한 번도 성공한 적 없었다"는 **점검 안 했으면 몰랐을 P0**가 나옴 |
| **C(사업성)** | 낮음 — 1회, 논의형 | 2026-07-12. 실사용자 0명이라 완벽한 재무모델보다 "계측 인프라 자체가 없었다"(텔레메트리 전무)는 사실 자체가 더 중요한 발견이었음 |

### 이 불균형이 시사하는 것

- **사용자가 매일 보는 화면(L1/L2)에는 압도적으로 많은 반복 검증이 들어갔고, 사용자가 안 보는 곳(A/B/C/D)은 "한 번은 봐야 한다"는 사고에서 뒤늦게(서비스 시작 3개월+ 후) 추가됐다.**
- 그런데 실제로 **가장 심각한 발견(P0/HIGH)은 전부 A/D축에서 나왔다** — DB 백업 0회 성공(D), SSRF/관리자키노출/환불권한우회(A), OpenAI 결제수단 미등록으로 스캔 전면실패가 조용히 폴백되던 것(C, 텔레메트리 신설 중 우연 발견). L1/L2에서는 이 정도 심각도의 발견이 상대적으로 적었다(대부분 UX 문구·오탐 수준).
- **결론**: 반복 횟수와 발견되는 문제의 심각도는 반비례 관계에 가까웠다. L1/L2는 "많이 봐서 계속 사소한 게 나오는" 영역, A/B/C/D는 "적게 봤는데 나오면 크게 나오는" 영역.

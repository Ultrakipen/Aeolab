# 체험 결과의 리뷰 수 자동 수집 — 설계 판단 (2026-10-28)

> 결론: **지금은 구현하지 않는다.** 수요가 아직 없고 네이버 접속 위험만 늘린다. 대신 직접 입력(구현·배포 완료)과 지표로 필요 여부를 판단하고, 트리거 조건이 충족되면 아래 설계로 구현한다.

## 현재 상태 (실측, 서버 DB 읽기 전용 · 코드 대조)
| 사실 | 근거 |
|---|---|
| 체험에 **플레이스 ID가 있으면** 이미 `auto_check_smart_place`가 방문자 리뷰 수를 수집한다 | `routers/scan.py:955` |
| 후보 선택 경로(지역검색 API 결과)는 플레이스 ID가 없다 → 리뷰 수 미수집 | 어니언 성수 체험 URL에 `naver_place_id` 없음(10-28), `scan.py:1040`·`1058` `review_count: None` |
| 체험 기록 누적 257건, 최근 일별 5건 이하(대부분 개발 테스트) | `trial_scans` 읽기 전용 조회 |
| 플레이스 점검이 실제로 된 체험 63건 중 방문자 리뷰 수 수집 **18건(29%)** | 같은 조회 — 점검이 돼도 정확한 수를 못 읽는 경우가 많다(`naver_place_stats` 주석: 정확히 못 읽으면 None) |
| 체험 접속은 IP당 하루 3회로 제한 | CLAUDE.md |

## 왜 지금 만들지 않는가
1. **수요 없음**: 일 5건 이하라 "리뷰 수가 없어 약해 보인다"로 이탈하는 사용자 수를 측정할 표본이 없다.
2. **접속 예산이 공용**: 체험의 플레이스 접속은 일일 상한(600, 배치 420)과 속도 기준을 정기 잡·유료 사용자와 나눠 쓴다. 광고 등으로 체험이 늘면 유료 사용자 몫을 잠식한다. (별점 낮은 리뷰 잡은 20곳 기준 주간 접속의 47%를 쓰던 최대 소비처였으나 2026-10-28 제거됨 — `docs/low_rating_alert_job_2026_10_28.md`.)
3. **성공률이 낮다**: 점검이 돼도 리뷰 수 수집은 29%. 접속을 더 써도 화면에는 여전히 비어 있을 수 있다.
4. **대체 경로가 이미 있다**: 직접 입력 카드(10-28 배포), 후기 많은 순 인기 신호(있을 때만), 구글 지도 평점·리뷰 수.

## 트리거 조건 (하나라도 충족되면 구현 착수)
- 체험이 **일 30건 이상 3일 연속** (실제 방문자 기준 — 봇·개발 테스트 제외).
- `trial_review_input` 이벤트(저장)가 결과 화면 조회 대비 **10% 미만**이면서 결과 화면 이탈이 높다 — 직접 입력이 쓰이지 않는다는 뜻.
- 사용자 인터뷰·문의에서 "리뷰가 많은데 안 보인다"가 2건 이상.

## 구현 설계 (트리거 시)
1. **플레이스 ID 확정**: 후보 확정 직후 `naver_place_resolver.ensure_naver_place_id`(이름 일치 1곳일 때만 확정, 주소 대조)로 ID를 얻는다. 이 단계는 검색 화면 접속(회로·쿼터 적용)이다.
2. **수집**: 기존 `auto_check_smart_place`를 재사용(새 스크래퍼 금지).
3. **공유 캐시**: 플레이스 ID 기준 24시간 캐시 — 같은 가게를 여러 사용자가 체험해도 접속은 1회.
4. **체험 전용 일일 상한**: 정기 잡·유료 몫을 침해하지 않게 체험 자동 수집은 별도 상한(예: 배치 몫을 뺀 사용자 몫의 일부)을 두고, 상한 초과·회로 열림·쿨다운이면 **수집을 건너뛰고 직접 입력 카드로 폴백**한다(체험 응답이 느려지거나 실패하면 안 된다).
5. **옵트인**: 기본은 현재처럼 입력 카드. 사용자가 "리뷰 수 대신 확인해 주세요"를 눌렀을 때만 수집(접속량을 요청 의사 있는 사용자로 제한).
6. **표시 원칙**: 수집값은 측정값("확인된 것"), 입력값은 "입력하신 값" — 둘이 충돌하면 측정값을 우선 표시하고 입력값은 숨긴다(이미 `reviewMeasured`로 입력 카드를 숨기는 로직 있음).
7. **검증**: 테스트는 실제 화면 구조를 본뜬 픽스처로(10-28 별점 잡 교훈), 서버에서 점검 함수를 연속 호출하지 않는다.

## 필요한 지표 (지금 설정돼 있는지)
- `trial_review_input`(action save/clear, has_count, has_rating): **설정됨**(10-28 배포).
- 체험 결과 화면 조회 수·이탈: 기존 `trial_complete` 등 GA4 이벤트 사용 — 실제 방문자 필터 필요.
- 체험 기록의 `smart_place_check.visitor_review_count` 수집률: 위 조회 쿼리로 주기 점검(현재 29%).

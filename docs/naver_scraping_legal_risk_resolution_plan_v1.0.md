## 0. 문제를 정확히 재정의

"회색지대 해결"은 3가지로 나뉜다. 하나만으로는 부족하고, 병행해야 최적이다.

| 축 | 의미 | 이 문서의 답 |
|---|---|---|
| 법적 확정 | 적법/위법 여부를 변호사가 판단 | Phase 0 |
| 위험요인 축소 | 결합된 5개 기법 중 실제로 위험에 기여하는 것만 골라 낮춤(핵심기능은 유지) | Phase 1 |
| 구조 전환 | 애초에 "우회" 프레임 자체가 성립 안 하는 방식으로 데이터 획득 경로를 바꿈 | Phase 2 |

**왜 이게 중요한가**: 기존 문서·핸드오프에 "CAPTCHA 우회 완료"라는 표현이 반복돼 왔는데(`naver_briefing_block_countermeasure_handoff_v1.0.md`), 정확히는 "CAPTCHA를 안 만나는 상태(회피)"이지 "CAPTCHA를 풀어서 통과(우회)"가 아니다. 부산지법 2017노4344 판례는 정확히 "캡차 **우회** 프로그램"을 문제 삼았으므로, 이 구분을 법률자문요청서에 정확히 전달하지 않으면 실제보다 위험도가 과대평가된 채로 자문이 진행될 수 있다. **이 문서 작성 전 CLAUDE.md·핸드오프 문서의 "차단우회" 표현도 이 구분을 반영해 갱신 필요(§5).**

## 2. Phase 0 — 즉시, 무비용, 무위험 (이번 주)

### 2-1. 법률 자문요청서 초안

기존 `naver_scraping_legal_risk_assessment_v1.0.md` 전체 + 위 §1 정정사항을 반영한 자문요청서를 작성해 IT/데이터 전문 변호사에게 발송. 핵심 전달 사항 4가지(변호사가 정확히 판단하려면 반드시 정확히 전달돼야 함 — 1번은 2026-08-08 재검증으로 정정됨):
1. **로그인쿠키는 평상시엔 "자동 로그인"이 아니라 "세션 재사용"이나, 코드베이스에 조건부 자동 재로그인 기능이 존재함** — 매주 월요일 실행되는 `naver_cookie_health` 잡이 NID_AUT 만료를 감지하면 `NAVER_LOGIN_ID`/`NAVER_LOGIN_PW` 환경변수가 설정된 경우 Playwright로 아이디/비번 필드를 채우고 로그인 버튼을 클릭하는 자동 재로그인을 시도함(`jobs.py:6334-6367`). **현재 두 환경변수 모두 서버에 미설정이라 이 경로는 비활성 — 실제 운영은 사람이 수동 로그인해서 얻은 쿠키값을 한 달에 한 번 교체해 재사용하는 방식**(`naver_ai_tab_scanner.py:39`)이 맞다. 다만 이 자동화 코드가 존재한다는 사실 자체를 변호사에게 반드시 알려야 함 — 활성화 여부와 무관하게 코드 존재 자체가 "이 시스템이 자동화된 로그인을 할 수 있는 구조인가"라는 질문의 답이기 때문
2. **CAPTCHA는 우회(풀이)가 아니라 회피+감지** — §1 정정사항 그대로 전달
3. **목적은 제3자 판매·DB 구축이 아니라 고객 본인 사업장 노출 여부 확인** — 기존 문서에 이미 있는 핵심 반증 요소
4. **로그인쿠키+프록시+automation flag 결합기법 사용처는 3곳** — 사업장별 AI브리핑 스캔(`naver_scanner.py`), AI탭 스캔(`naver_ai_tab_scanner.py`), 월 1회 업종확대 모니터링(`jobs.py`의 `briefing_category_expansion_monitor_job`, 월 8쿼리)

**추가 권장(정책, 코드 아님)**: 법률 자문 결과가 나오기 전까지 `NAVER_LOGIN_ID`/`NAVER_LOGIN_PW`를 절대 `.env`에 설정하지 말 것 — 설정하는 순간 dormant 상태였던 자동 재로그인 코드가 실제로 작동하기 시작해, 지금까지의 "세션 재사용" 성격 규정 자체가 깨짐.

### 2-2. 네이버 이용약관 원문 대조 — 이번 세션에서 미완료, 사용자 액션 필요

WebFetch가 `policy.naver.com`, `terms.naver.com` 접근에 실패해 이번 세션에서 원문 조 번호를 직접 확인하지 못했다. **원인 미확인** — 네이버의 AI브리핑 anti-bot 조치와 같은 종류인지, 대형 포털에 흔한 robots.txt 전면차단인지, 도구 자체의 제약인지 구분할 근거가 없어(WebSearch로도 naver.com robots.txt 원문 미확인) 이 실패를 법적 리스크의 "방증"으로 해석하지 않는다(2026-08-08 자체 재검증으로 정정 — 최초 초안엔 "자동화 차단으로 추정, 이 자체가 방증"이라 썼으나 근거 없는 단정이었음). **사용자가 직접 브라우저로 아래 접속 후 "금지행위" 조항 캡처해 변호사에게 전달 필요**:
- https://policy.naver.com/rules/service.html (네이버 이용약관)
- https://policy.naver.com/rules/privacy.html (개인정보처리방침, 참고용)

### 2-3. AEOlab 자체 약관에 목적 고지 추가 (검토용 초안)

`frontend`의 이용약관/개인정보처리방침에 아래 취지 문구 추가 검토 (실제 반영은 사용자 승인 후):
> "AEOlab은 회원이 등록한 사업장의 네이버 AI 브리핑 노출 여부를 확인하기 위해 자동화된 기술적 방법을 사용하며, 이는 회원 본인 사업장의 노출 현황 확인 목적에 한정됩니다."

이 문구 자체가 네이버 약관 위반 여부를 바꾸지는 못하지만, §5 반증요소("고객 본인 확인 목적")를 서비스 차원에서 명문화해 목적의 정당성을 보강하는 효과는 있음.

## 3. Phase 1 — 저위험 기술 완화 (사용자 승인 후 1~2주 내 실행 가능, 핵심기능 유지)

기법별로 "위험 기여도 vs 제거 시 기능 손실"을 대조해 우선순위를 매겼다 — **전부 동시 제거가 아니라 손익비가 좋은 것부터 순차 적용**.

| 우선순위 | 조치 | 위험 감소 근거 | 기능 손실 |
|---|---|---|---|
| 1 (권장) | 프록시 로테이션 폭 축소 — 사업장마다 매번 IP를 바꾸지 않고, 하루 단위로 소수 고정 IP만 순환 | 2017노4344 판례가 **정확히** "캡차우회+다수IP 프로그램" 조합을 문제 삼음 — 로테이션 강도를 낮추면 이 조합의 강도 자체가 약해짐 | 낮음 — IP 차단 감지 시 폴백 로직(`_proxy_circuit_open_until` 등)이 이미 있어 완만한 전환 가능 |
1 (권장) | 요청 빈도를 사람 패턴에 더 가깝게(현재도 `random.randint(2800,4800)` 딜레이 존재 — 사업장 간 딜레이를 조금 더 늘리는 정도) | "대량 자동조회"로 보일 가능성 축소 | 스캔 소요시간 소폭 증가만 |
| 2 (검토) | `--disable-blink-features=AutomationControlled` 유지 여부 | 이 플래그 자체를 문제 삼은 판례는 조사범위 내 없음 — Playwright 표준 관행에 가까워 제거 시 위험 감소 효과 대비 접속 자체가 막혀 서비스 붕괴 가능성이 훨씬 큼 | **제거 비권장** — 손익비 나쁨 |
| 3 (보류) | 로그인쿠키 주입 자체 제거 | 문서화된 "soft block"의 근본 해결책이 이것뿐이라 제거 시 AI브리핑 스캔 기능 자체가 사실상 무력화(`naver_briefing_block_countermeasure_handoff_v1.0.md`) | **제거 불가 — 대신 Phase 2로 구조 전환** |

**결론**: 코드 한두 줄로 "위험을 크게 줄이면서 기능은 그대로"인 조치는 사실상 프록시 로테이션 강도 조절 정도뿐이다. 나머지(로그인쿠키·automation flag)는 지금 방식을 유지하는 한 근본적으로 줄일 수 없는 위험이라는 게 이번 재검토의 솔직한 결론 — 그래서 Phase 2가 필요하다.

## 4. Phase 2 — 구조 전환: 사용자 동의 기반 채널 신설 (중기, 4~8주, 진짜 "해결"에 가장 가까운 방안)

### 핵심 아이디어

지금은 **회사 소유 계정 1개 + 서버 헤드리스 브라우저**로 모든 고객의 스캔을 대신 수행한다. 이 구조 자체가 "타인의 시스템에 위조된 신원으로 자동 접근"이라는 프레임에서 벗어나기 어렵다.

대안: **사업장 소유자 본인이, 본인 소유의 네이버 계정으로 로그인한 상태에서, 본인 브라우저에 설치한 크롬 확장(익스텐션)으로 본인 AI브리핑 노출 여부를 직접 확인**하도록 채널을 하나 더 만든다.

### 왜 법적 성격이 달라지는가

| 요소 | 현재(서버 헤드리스) | 확장 프로그램(신규) |
|---|---|---|
| 로그인 주체 | 회사 소유 계정 1개를 전 고객에 재사용 | 각 사용자 본인 계정, 본인이 직접 로그인 |
| IP | 회사 서버/프록시 | 사용자 본인의 실제 IP |
| 자동화 신호 은닉 | 필요(헤드리스 특성상 필수) | 사실상 불필요 — 브라우저 확장 API는 자동화 프레임워크가 아니라 일반 브라우저 기능이라 "자동화 은닉"이라는 개념 자체가 성립 안 함 |
| 규모 | 서버 1대가 수백 사업장을 대신 조회 (반복·대량 패턴) | 사용자 1명이 본인 것만 조회 (반복성 낮음) |

### 실행 순서 (단계적으로, 1단계부터)

1. **1단계(권장 시작점)**: 사용자가 원할 때 수동으로 클릭하는 최소기능 확장 — "지금 이 페이지의 AI 브리핑에 우리 가게가 나오나요?" 버튼 → 현재 열려있는 네이버 검색결과 DOM만 읽어 AEOlab 서버로 결과 전송. 완전 수동이라 자동화 쟁점 자체가 최소화됨.
2. **2단계(선택적 확장)**: 사용자가 등록한 키워드로 백그라운드 자동 체크 — 이 단계부터는 "사용자 컴퓨터에서의 자동화"라는 유사 쟁점이 다시 생길 수 있음(다만 계정·IP가 본인 소유라는 차이는 유지). 1단계 운영 후 사용자 반응 보고 판단.
3. 기존 서버 방식은 즉시 폐기하지 않고 **병행**(확장 미설치 사용자를 위한 폴백) — 완전 대체가 아니라 저위험 옵션 추가로 시작.

### 참고 선례 (규범적 근거 아님, 시장 참고용)

경쟁사 naeo.kr이 이미 "크롬 익스텐션으로 네이버 에디터 자동 채움" 기능을 상용 운영 중(`project_naeo_kr_mcp_comparison_2026_07_20`). 단, naeo.kr이 법적 검토를 거쳤는지는 확인 불가 — "선례가 있으니 안전하다"는 근거로 쓸 수 없고 **기술적으로 이 패턴이 시장에 이미 존재해 구현 난이도가 비현실적이지 않다는 참고**로만 사용.

## 9. Phase 1.5 — 플레이스 순위 체크를 공식 API로 전환 (2026-08-08, 사용자 제공 API Hub 스크린샷 계기)

사용자가 제공한 네이버 API Hub(NCP) 안내 스크린샷(검색어트렌드·검색API)을 계기로 조사한 결과, **네이버 트래픽의 실제 최대 발생원은 AI브리핑 스캐너가 아니라 키워드 순위체크(`naver_keyword_rank.py`)**였음을 확인(§7 우선순위 산정 근거). 이 기능이 사업장당 평균 4.2개 키워드 × 3채널(PC·모바일·플레이스) = 약 12건/사이클을 Playwright로 스크래핑하고 있었고, Pro/Biz/창업패키지는 이걸 **매일** 실행 중이었음.

**발견**: 3채널 중 "플레이스" 순위는 이미 `services/naver_visibility.py`가 다른 화면(스마트플레이스 체크 등)에서 **공식 지역검색 API**(`local.json`, 무료, 검색API 공유한도 일 25,000건)로 구하고 있던 것과 동일한 데이터. `keyword_search_rank` 점수가 "PC·모바일·플레이스 중 최저 순위"를 쓰도록 설계돼 있어(`score_engine.py:calc_keyword_search_rank_score`) 3채널이 다 필요했던 것이지, 플레이스만큼은 굳이 스크래핑할 필요가 원래 없었음.

**구현**: `naver_keyword_rank.py`의 `_measure_place()`(Playwright, `where=place` 스크래핑) 제거 → `_measure_place_api()`(공식 `local.json` API 재사용, `naver_visibility.py`의 `_get`/`_name_matches` 임포트해 중복구현 없이 통합)로 교체. PC/모바일 채널은 기존 순차 실행 타이밍(봇탐지 회피 목적)을 그대로 유지 — 동시실행으로 바꾸지 않음(1차 구현에서 시도했다가 타이밍 패턴 변경 리스크 인지하고 되돌림).

**효과(계산)**: 사업장당 키워드순위체크 Playwright 요청이 12건→8.4건(약 30% 감소, robots.txt 대상에서 완전히 벗어남). 현재 6개 구독 기준 전체 네이버 도메인 요청량 추정치가 약 85건/일 → 약 66건/일(약 22% 감소)로 하락. **정확도 손실 없음** — 오히려 봇탐지로 인한 스크래핑 실패 가능성이 없는 공식 데이터라 더 안정적.

**검증**: 로컬 backend_venv 런타임 임포트 성공 → 서버 md5 배포 확인 → `pm2 restart` 에러 0건 → 서버에서 실제 API 호출 라이브 테스트(존재하지 않는 가게명 → `None` 정확 반환) 성공.

**남은 것**: PC/모바일 통합검색 순위는 대응 공식 API가 없어 Playwright 유지 — §7의 "전역 요청 상한선"·"쿼리 최소화"는 여전히 유효한 다음 단계.

**남은 갭(의도적 축소범위, 문서화)**: `ai_search_screenshot.py`(스크린샷 캡처, 호출빈도 미확인)는 이번 라운드에서 제외 — 별도 확인 필요. 순수 HTTP(비-Playwright) 기반 naver.com 접근(`blog_search_analyzer.py` 등)은 이 상한선 대상 아님(자동화 브라우저 특유의 봇탐지 리스크가 상대적으로 낮고, robots.txt 전체차단은 원칙적으로 적용되나 이번 라운드는 Playwright 우선 처리).

## 11. 성장 시나리오 대응 — 서비스 미출시 상태 재확인 (2026-08-08)

사용자가 "서비스 미출시, 구독자 0명(이전 세션에서 확인한 6건은 테스트/개발 데이터)"이라고 정정 — §7~10의 "6명 기준 하루 66~90건" 추정치는 실제 런칭 트래픽이 아니라 테스트 데이터 기반이었음을 재확인. 다만 계산식(플랜별 사업장당 요청량)은 재사용 가능.

**트라이얼 트래픽 확인(신규)**:
- **무료체험(비로그인, `/api/scan/trial` → `scan_trial()`)**: `self.chatgpt.sample_5()`만 호출 — **네이버 Playwright 요청 0건**. 성장해도 이 상한선과 무관.
- **가입 후 1회체험(`run_basic_trial` → `_run_full_scan()`)**: 구독자 정기스캔과 동일한 `scan_all()` 재사용(표본만 50으로 축소) — **§10에서 만든 전역 상한선을 이미 그대로 공유**함. 별도 코드 수정 불필요.
- **신규 발견 갭**: 유료구독 스캔과 무료체험이 **같은 하루 예산을 공유**해, 체험 신청이 몰리는 날 유료 구독자(특히 Biz "매일 스캔" 약속)의 정기스캔이 밀려날 수 있음 — 우선순위 분리 미구현 상태(§10 완료 시점엔 인지 못했던 갭).

**50명 구독자 시나리오 계산**: §9~10 산정식(사업장당 Basic 2.6건/일·창업 9~13·Pro 14~18·Biz 13~17)을 6명 시점 플랜 비율(basic1:창업1:pro1:biz3)로 50명까지 단순 확장 시 **하루 530~694건 추정 — 현재 상한(250건)의 2~3배**. 즉 250이라는 기본값은 20명 안팎까지만 버티도록 설계된 값이며 50명 도달 전 반드시 재검토 필요.

**조치**: `_check_data_wiring_readiness_job`(이미 존재하는 "구독 50명→Playwright 자동화 착수", "100명→DataLab 연동" 마일스톤 알림 잡)에 세 번째 조건 추가 — **20명 도달 시 "[DATA-WIRING-READY-NAVER-QUOTA]" 경고**(다른 두 조건보다 낮은 임계치, 위 계산 근거). `NAVER_QUOTA_REVIEWED=true`로 해제 전까지 매일 반복 경고. 이 패턴은 기존에 검증된 "자동조치 없이 사람에게만 알림"(과거 세마포어 데드락 사고로 자동조치 안 하는 원칙, `backend_scaling_trigger_check_job` 주석 참조) 원칙을 그대로 따름.

**재검토 시 고려할 옵션(다음에 실제로 20명 근접 시 설계)**:
1. `NAVER_PLAYWRIGHT_DAILY_CAP` 단순 상향 — 가장 간단하나 "구독자 늘수록 위험 비례 증가" 문제로 회귀
2. 우선순위 버킷 분리(유료구독 vs 무료체험) — `scan_all()`/`check_mention()`까지 소스구분 파라미터를 관통시켜야 해 시그니처 변경 필요, 이번 라운드엔 미착수
3. Phase 2(사용자 계정+크롬 익스텐션) 착수 시점 앞당기기 — 실제 유료고객 50명 규모면 "소규모라 리스크 낮다"는 반증요소 자체가 약해지므로 구조전환 필요성이 커짐

**검증**: `jobs.py` 문법확인+md5 배포확인+pm2 재시작 에러 0건.

## 12. 사용자 증가 대응 종합 로드맵 (2026-08-08)

지금까지 §1~11에서 다룬 것을 구독자 규모별 4단계로 정리. **전 단계에서 자동조치는 없음** — 전부 "사람에게 알림 → 사람이 판단" 원칙(과거 세마포어 데드락 사고 교훈 유지). 법률 자문 결과가 언제 나오느냐가 이 로드맵보다 우선하는 변수 — 자문에서 심각한 문제가 확인되면 구독자 수와 무관하게 즉시 이 로드맵을 재검토해야 함.

| 단계 | 구독자 규모 | 이미 돼있는 것 | 그때 사람이 할 일 |
|---|---|---|---|
| **0단계(현재)** | 0명(미출시) | 상한선 250건/일, 백업계정, 킬스위치, API전환, 우선순위 알림 전부 배포완료 | §2-1 자문요청서 발송(유일한 미완료 항목) |
| **1단계** | 0~20명 | 위 안전망이 그대로 작동, 별도 조치 불필요 | 특별히 없음 — `[naver_quota]` 로그만 가끔 확인 |
| **2단계** | ~20명 | `[DATA-WIRING-READY-NAVER-QUOTA]` 경고 자동 발생(2026-08-08 신설) | §11 옵션 3가지(캡 상향/우선순위분리/Phase2 앞당기기) 중 결정. 자문 결과가 이미 나왔다면 그 내용이 결정에 최우선 반영돼야 함 |
| **3단계** | ~50명 | `[DATA-WIRING-READY-50]` 경고(기존, smart_place Playwright 자동화용) | 이 시점엔 실제 매출이 있는 사업이라 "소규모라 안전하다"는 반증 논리가 약해짐 — Phase 2(구조전환)·Phase 3(네이버 공식 제휴)를 진지하게 착수할 시점 |

**한 줄 요약**: 지금은 아무것도 안 해도 되고, 20명 근처에서 로그가 알아서 알려주면 그때 §11의 3가지 중 하나를 고르면 된다. 유일하게 지금 당장 해야 할 일은 이 로드맵과 무관하게 처음부터 밀려온 §2-1(자문요청서 발송)이다.

## 13. §2-1 법률 자문요청 보류 결정 (2026-08-08, 사용자 결정)

**사용자가 §2-1(자문요청서 발송)을 명시적으로 보류하기로 결정함.** 이 문서 전체에서 여러 차례 "가장 시급하다"고 반복 강조했던 항목이나, 충분한 근거(robots.txt 전체차단·검색정책 조항·자동재로그인 코드 발견 등 §1~4)를 제시한 뒤 나온 사용자의 최종 판단이므로 이 세션에서는 더 이상 재권고하지 않는다. **놓친 게 아니라 의도적 보류임을 다음 세션에 명확히 전달할 것.**

**이 결정이 로드맵에 미치는 영향**:
- §12 로드맵의 "법률 자문 결과가 이 로드맵보다 우선하는 변수"라는 전제가 당분간 성립하지 않음 — 자문 결과 없이 §12의 4단계(0~20~50~100명)를 그대로 진행
- 크롬 익스텐션(Phase 2) 투자 여부도 "자문 결과 보고 결정" 논리가 보류됨 — 대신 §12의 마일스톤 알림(20/50/100명)이 유일한 재검토 트리거로 남음
- 현재 배포된 기술적 완화(상한선·백업계정·킬스위치·API전환)가 앞으로도 계속 "실질적 위험 관리의 전부"가 됨 — 법적 확정 없이 운영을 계속한다는 뜻
- 재검토 시점: 위 마일스톤 도달 시, 또는 사용자가 임의로 다시 판단하고 싶을 때. 강요하지 않음.

## 14. 구조전환(Phase 2) 착수 시점 확정 + 자동 알림 신설 (2026-08-08)

"6가지 완화안 중 장기적 대비는 무엇인지" 질문에 **①사업장간 쿼리캐싱(손해없이 지금 해도 됨)**과 **⑥구조전환(유일하게 "늘수록 위험 커짐" 구조를 뒤집는 근본해법)**을 장기 대비로 추천. 나머지 4개(②빈도하향·③키워드축소·④예산분리·⑤캡상향)는 "늘 때마다 다시 조정해야 하는 임시방편"으로 구분.

**구조전환 착수 시점 = 구독자 50명**으로 확정 — 기존 `smart_place_completeness` 자동화 마일스톤과 동일 지점 재사용(계산상 하루 500건과도 일치, 500건 시나리오 논의와 정합). `_check_data_wiring_readiness_job`에 `[DATA-WIRING-READY-PHASE2]` 조건 신설(`jobs.py`, `PHASE2_EXTENSION_REVIEWED` 플래그로 해제). **조기신호 명시**: `[DATA-WIRING-READY-NAVER-QUOTA]`(20명 임계치)가 50명 도달 전 반복 발생하면 그 자체가 앞당겨야 한다는 신호 — 알림 문구에 포함시킴.

**검증**: `jobs.py` 문법확인+md5 배포확인+pm2 재시작 에러 0건.

**현재 마일스톤 알림 체계 종합(4개)**: 20명(네이버상한 재검토) → 50명(스마트플레이스 자동화 + **구조전환 착수 검토**, 2건 동시) → 100명(DataLab 연동). 전부 자동조치 없이 로그 경고만 — 사람이 새 대화창에서 판단.

# 쓰기 라우트 격리 점검 설계 (2026-11-01)

## 1. 배경
GET 라우트 140개를 서버에서 전수 호출하자 실제 결함이 나왔다(CLAUDE.md '최근 업데이트'의 11-01 항목). 쓰기 라우트(POST/PUT/PATCH/DELETE)는 데이터를 바꾸기 때문에 같은 방식으로 돌리지 않았고, 그래서 **자동 점검의 가장 큰 공백**이다.
같은 날 "읽기 전용"으로 부른 첫 점검이 데이터를 바꿔 버린 사고(`kakao_registered` 덮어쓰기, `ai_usage_log` 실패 행, `business_action_log` 행 — 모두 복원·정리)가 있었으므로, 쓰기 라우트 점검은 **격리가 증명된 방식**으로만 한다.

## 2. 확인한 사실
- 서버 앱의 쓰기 라우트는 **99개**(`app.routes`에서 열거). 정적 키워드 분류(휴리스틱 — 엔드포인트 소스에서 단어를 찾을 뿐 호출하는 서비스는 따라가지 않아 부정확함, 예: 구글 장소 일치 점검이 'payment'로 분류됨): 외부 부작용 표시 없음 36 · AI 17 · 네이버 접속 14 · 관리자 19 · 결제 11 · 알림 발송 10 · 삭제 11 (한 라우트가 여러 분류에 들어갈 수 있어 합이 99를 넘는다; 99개 목록 전체에서 다시 센 값).
- 데이터는 운영 DB(Supabase) 하나뿐이다. 스키마의 완전한 DDL은 저장소에 없다(`scripts/supabase_schema.sql`은 일부만 — `competitors.kakao_place_id` 사고가 그 증거). 따라서 **스테이징 DB를 코드로 재현할 수 없고 사용자가 DB 덤프를 떠야 한다.**
- GET도 쓴다: 방문 시각(`visit-delta`), 사용량 로그(`pioneer-detail`·`condition-search`), 추천 행동 기록(`onboarding-action`). **이 목록은 상태에 따라 달라진다** — 중복 방지가 있는 쓰기는 이미 행이 있으면 시도하지 않아, 첫 점검 이후 재실행한 목록에는 `business_action_log`가 빠져 있었다(행을 지우고 재실행해서야 나옴). 어떤 쓰기 목록도 "완전하다"고 단정하지 말 것.

## 3. 접근안 비교
| 안 | 방법 | 장점 | 단점·필요 조건 |
|---|---|---|---|
| A. 스테이징 DB | 별도 Supabase 프로젝트에 스키마를 복제하고 백엔드를 그쪽에 연결 | 파괴적·결제 라우트까지 점검, DB 제약(UNIQUE·NOT NULL·FK·RLS)까지 검증 | 스키마 DDL이 없어 **사용자가 `pg_dump` 덤프 필요**, 키·환경 이원화, 유지 부담. 구독자가 없는 지금은 과함 |
| B. 운영 DB + 테스트 계정 | 전용 테스트 사용자·사업장을 만들어 실제로 호출 | 실제 DB 제약 검증 | 운영 DB 오염·집계 왜곡, 가로채기 우회 시 실제 사용자 영향, 정리 스크립트 필요. **권장하지 않음** |
| C. 가짜 DB 단위 테스트 | `get_client`를 인메모리 가짜로 교체해 pytest | CI에서 빠르고 격리 완벽 | PostgREST 의미(필터·정렬·count)를 가짜가 재현해야 해서 구현 큼, 충실도 낮음 |
| **D. 드라이런 가로채기** | 쓰기 요청을 DB로 보내지 않고 `httpx` 층에서 가로채 **테이블·컬럼을 스키마 스냅샷에 대조**한 뒤 가짜 성공 응답을 돌려줌. 읽기는 실제 DB, 외부 연결은 차단 | 데이터가 바뀌지 않는데 라우트 전 로직이 실행됨, 구현 작음, 실제 읽기 데이터 사용 | 가짜 응답이라 DB 제약은 검증 못 함, 가로채기가 우회되면 실제로 쓰일 수 있음(→ 실행 전후 값 단위 누수 점검) |

## 4. spike 결과 (D 안, `backend/scripts/route_write_dryrun.py`)
허용 목록 16개 라우트(키워드 추가·삭제, 경쟁사 비활성화·수정, 피드백, 카카오 체크리스트, 행동 기록, 가이드 체크리스트·FAQ 삭제, 대기자 등록, 설정 수정, 게시글, API 키)를 서버에서 호출:
- 라우트 전 로직 실행 **13개 200/400**(422 3개는 자동 생성한 본문이 모자라서 — 생성기 한계).
- **쓰기 11건을 가로챘고** 대상 테이블·컬럼 전부 스키마와 일치(`SCHEMA_PROBLEMS []`), 비-REST(Auth·Storage·rpc) 쓰기 0건.
- **누수 없음을 값 단위로 확인**: 커스텀 키워드 비어 있음, 카카오 체크리스트 `{}`·점수 0, 경쟁사 활성 유지, 대기자·피드백 행 0. (행 수 비교만으로는 PATCH 누수를 못 잡는다 — 스크립트 출력의 행 수 비교는 보조 수단일 뿐이고, 판정은 값 단위로 한다.)
- 라우트가 외부(카카오 API)를 부르려다 차단됨 → 해당 코드는 어제 수정한 "확인 못 함이면 저장 안 함" 경로로 정상 동작.
- 이 spike로는 **새 결함이 나오지 않았다**(허용 목록이 단순 CRUD라서, 이미 스키마 검사가 잡는 종류와 겹침). 가치는 "결함 발견"이 아니라 "격리가 작동함을 증명"한 것.

## 5. 권장
1. **D 안을 상시 점검 도구로 둔다.** 허용 목록을 단계적으로 넓힌다: (1단계 현재 16개) → (2단계) 외부 부작용이 없는 나머지 쓰기 라우트 약 20개 → (3단계) 본문 생성기를 보강하고 AI·네이버 라우트는 외부 차단 상태에서 **오류 경로가 안전하게 끝나는지**만 점검.
2. **파괴적·금전·관리자 일괄 발송 라우트는 D 안에도 넣지 않는다**: 계정·사업장 삭제, 결제·환불·카드 변경, 구독 해지·재활성, 관리자 방송·이메일 시험 발송, 팀원 삭제. 이들은 단위 테스트(C 안)로 핵심 분기만 보고, 실제 실행은 A 안이 생긴 뒤.
3. **A 안(스테이징)은 유료 구독자가 생겨 결제·삭제 경로를 실제로 시험해야 할 때** 한다(사용자 결정 + DB 덤프 필요).
4. 모든 실행에서 안전 점검을 습관화: ①DB 호스트 non-GET 전부 가로채기 ②가로챈 쓰기 목록을 출력 ③실행 전후 **값 단위** 대조 ④외부 연결 차단 ⑤허용 목록 밖 라우트는 호출하지 않음.

## 6. 한계 (알고 쓸 것)
- UNIQUE·NOT NULL·FK·RLS·트리거 같은 DB 제약은 검증하지 못한다.
- 가짜 응답(`id` 하나와 본문 에코)이 실제 응답과 다르면, 쓰기 직후 응답을 읽는 후속 로직은 실제와 다르게 동작할 수 있다.
- `httpx` 밖의 HTTP 라이브러리로 DB에 쓰는 코드가 있으면 가로채지 못한다(현재 `supabase-py`는 `httpx`). 새 코드가 다른 클라이언트를 도입하면 이 도구를 다시 확인한다.
- 상태 의존 쓰기(중복 방지)는 시점에 따라 시도 여부가 달라 한 번의 실행 결과가 완전하지 않다.
- 자동 생성 본문은 필수 필드만 채워 비즈니스 규칙(길이·조합)에 걸려 422가 나올 수 있다.

## 7. 사용자 결정이 필요한 것
1. A 안(스테이징 DB)을 언제 할지 — 구독자 발생 시점으로 미루는 것을 권장. 하게 되면 Supabase에서 DB 덤프(스키마)를 받아 주셔야 한다.
2. D 안의 허용 목록을 넓혀도 되는지(2단계). 데이터가 바뀌지 않는 방식이지만 운영 DB를 읽는다.
3. 점검 도구를 배포 후 정기 절차(예: 배포 때마다 GET 점검 + D 안 점검)로 둘지.

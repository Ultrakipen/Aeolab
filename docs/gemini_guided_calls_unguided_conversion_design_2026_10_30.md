## 2. 전환안
**핵심**: 새 질문을 하지 않고, 이미 하는 비유도 샘플(`sample_recommend`)의 추천 목록 전체를 재사용해 경쟁사·내 가게를 같은 방법으로 대조한다.

1. `sample_recommend` 결과에 `place_counts`(정규화 이름 → 등장 횟수, 상위 30개 등 상한)를 추가한다. 지금의 `top_places`는 **상위 5곳뿐이라 특정 경쟁사 판정에 쓸 수 없다**(설계 초안의 오판을 점검에서 정정).
2. 경쟁사 노출 = `place_counts`에서 `names_match`로 찾은 횟수 / `sample_size`. 목록에 없으면 "이 표본에서 0회" — 내 가게와 같은 방법의 측정값이라 공정 비교가 된다.
3. 질의 상세(`{키워드} 예약` 등)는 질의 변형을 `sample_recommend`의 질의 목록에 넣어 같은 방식으로 측정.
4. 공유 캐시(`probe_cache`)가 켜져 있으면 표본이 공유되므로 경쟁사 비교 추가 호출은 0이다.

## 3. 효과 / 위험
- 효과: 스캔당 추가 호출 약 10회 감소(경쟁사 5곳 가정, [추정]), 유도형 환각 제거, 한도(하루 500) 여유, 개인정보(소개글) 전송 경로 축소(조건 검색 제외).
- 위험·의미 변화:
  - 경쟁사 화면의 "Gemini AI 단일 측정 기반 추정" 라벨과 수치 의미가 바뀐다(예/아니오 → 표본 N회 중 K회).
  - 과거 기록과 연속성이 끊긴다(전후 비교 그래프에 단절 표시 필요).
  - 지역 소도시의 경쟁사는 일반 명칭으로만 추천될 수 있어 "0회"가 많아질 수 있다 → "확인 안 됨"과 "0회"를 구분해 표시해야 한다(신뢰 원칙 9).
  - 표본이 20~50개일 때 낮은 빈도의 경쟁사는 신뢰구간이 넓다.

## 4. 구현 순서(승인 시)
1. `sample_recommend`에 `place_counts` 추가 + 캐시에 목록 보존 확인(테스트).
2. 경쟁사 비교 계산부(`scan.py` 두 곳, `jobs.py` 두 곳)를 `place_counts` 기반으로 교체, 옛 키(`exposure_freq` 등) 호환 유지.
3. 화면 문구·라벨 정정(PC/모바일), 인기 가게(어니언 성수·하라식당)로 결과 화면 대조.
4. 변이 검증과 실제 응답 픽스처 테스트.
5. 서버 반영 후 다음 야간 스캔으로 호출 수 감소 실측(`/admin/naver-access`의 `ai_capacity`).

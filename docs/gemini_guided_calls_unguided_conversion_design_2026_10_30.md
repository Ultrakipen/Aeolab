# Gemini 유도형 호출(가게명을 질문에 넣는 호출) 비유도 전환 설계안 (2026-10-30)

> 상태: **경쟁사 노출 판정 4곳 구현·배포 완료(2026-10-30, 사용자 승인)**. 내 가게 질의 상세·조건 검색·액션 재스캔·경쟁사 소개문 보강(`_enrich_competitor_excerpts`)은 아직 유도형(아래 §6).
> 표기: **[확인]** 코드로 확인 / **[추정]** / **[미확인]**.

## 1. 현황 (호출 지점, 코드 확인)
스캔 본체(`sample_recommend`, 비유도)와 별개로 아래 호출이 가게명을 질문에 넣는다(유도형).

- 이 호출들은 모두 `_throttle`(4.5초 간격)을 거치므로 풀스캔 1회에 경쟁사 수 + 약 7~10회가 추가로 대기열에 쌓인다 [확인: 호출 지점 grep].
- 유도형 문제: 가게명을 넣어 "추천되나?"를 물으면 환각으로 "추천됨"이 부풀 수 있다(ChatGPT에서 실사업장 43~95/100, 실존하지 않는 가게도 노출로 판정 — CLAUDE.md 2026-09-28). Gemini의 같은 편향은 **미측정**.

## 2. 전환안
**핵심**: 새 질문을 하지 않고, 이미 하는 비유도 샘플(`sample_recommend`)의 추천 목록 전체를 재사용해 경쟁사·내 가게를 같은 방법으로 대조한다.

1. `sample_recommend` 결과에 `place_counts`(정규화 이름 → 등장 횟수, 상위 30개 등 상한)를 추가한다. 지금의 `top_places`는 **상위 5곳뿐이라 특정 경쟁사 판정에 쓸 수 없다**(설계 초안의 오판을 점검에서 정정).
2. 경쟁사 노출 = `place_counts`에서 `names_match`로 찾은 횟수 / `sample_size`. 목록에 없으면 "이 표본에서 0회" — 내 가게와 같은 방법의 측정값이라 공정 비교가 된다.
3. 질의 상세(`{키워드} 예약` 등)는 질의 변형을 `sample_recommend`의 질의 목록에 넣어 같은 방식으로 측정.
4. 공유 캐시(`probe_cache`)가 켜져 있으면 표본이 공유되므로 경쟁사 비교 추가 호출은 0이다.

## 3. 효과 / 위험
- 효과: 스캔당 추가 호출 약 10회 감소(경쟁사 5곳 가정, [추정]), 유도형 환각 제거, 한도(하루 500) 여유, 개인정보(소개글) 전송 경로 축소(조건 검색 제외).
- 위험·의미 변화:
  - 경쟁사 화면의 "Gemini AI 단일 측정 기반 추정" 라벨과 수치 의미가 바뀐다(예/아니오 → 표본 N회 중 K회).
  - 과거 기록과 연속성이 끊긴다(전후 비교 그래프에 단절 표시 필요).
  - 지역 소도시의 경쟁사는 일반 명칭으로만 추천될 수 있어 "0회"가 많아질 수 있다 → "확인 안 됨"과 "0회"를 구분해 표시해야 한다(신뢰 원칙 9).
  - 표본이 20~50개일 때 낮은 빈도의 경쟁사는 신뢰구간이 넓다.

## 4. 구현 순서(승인 시)
1. `sample_recommend`에 `place_counts` 추가 + 캐시에 목록 보존 확인(테스트).
2. 경쟁사 비교 계산부(`scan.py` 두 곳, `jobs.py` 두 곳)를 `place_counts` 기반으로 교체, 옛 키(`exposure_freq` 등) 호환 유지.
3. 화면 문구·라벨 정정(PC/모바일), 인기 가게(어니언 성수·하라식당)로 결과 화면 대조.
4. 변이 검증과 실제 응답 픽스처 테스트.
5. 서버 반영 후 다음 야간 스캔으로 호출 수 감소 실측(`/admin/naver-access`의 `ai_capacity`).

## 5. 결정 필요
- 경쟁사 비교의 의미를 "이름을 물었을 때"에서 "추천 목록에 나오는 빈도"로 바꿔도 되는가?
- 과거 값과의 단절을 화면에서 어떻게 표시할 것인가(주석 vs 새 기준선)?

## 6. 구현 결과와 점검에서 정정된 설계 (2026-10-30)
- **구현**: `services/competitor_ai_exposure.py`(`competitor_exposure`·`compact_for_storage`·`score_fields`), 스캐너 `sample_recommend`가 `place_counts`(이름별 등장 표본 수, 표본당 1회)와 `place_counts_truncated`를 반환. 교체한 호출: `scan.py`(`_enrich_scan_background`, 가입 후 체험 백그라운드 풀스캔), `jobs.py`(`daily_scan_all`), `competitor.py`(`_scan_new_competitor`). 근거 플랫폼은 Gemini 우선·없으면 ChatGPT, 둘 다 없으면 갱신 생략(0으로 저장하지 않음). 화면(`CompetitorsClient.tsx`)은 새 항목에 "같은 질문 N회 중 K회"를 표시하고 과거 항목은 "과거 방식" 안내를 붙인다.
- **정정 1 — 상한**: 초안의 "상위 30개 저장"은 틀렸다. 실측(하라식당, 질의 4개·100표본)에서 서로 다른 이름이 **430개**, 전체 JSON 14.5KB. 메모리 안에서는 전체(상한 600)로 대조하고 **저장·응답 직전에 상위 40개(1.8KB)로 압축**한다(전체를 저장하면 스캔 1회당 gemini+chatgpt 약 29KB — 사용자·스캔 수가 늘면 DB가 빠르게 불어남). 저장본으로 대조할 때 목록에 없으면 "0회"가 아니라 "확인 불가"(신규 경쟁사 등록 직후 일부는 다음 스캔에서 반영).
- **정정 2 — 점수 척도**: `compute_competitor_score`의 `freq_bonus=min(20, freq*2)`는 단일 호출(0/1) 기준이라 등장 비율을 0~10으로 환산해 넣는다(미언급 0, 언급 40~60). 공식 자체는 변경하지 않음.
- **정정 3 — 표시**: 경쟁사 카드의 "네이버 AI 노출됨/미노출(추정)" 배지는 `naver_exposure_confirmed`·`multi_ai_exposure`가 같은 값(경쟁사 AI 신호 하나)을 복제한 것이라 새 항목에서는 쓰지 않는다.
- **의미 변화(알림)**: 과거 항목은 "가게 이름을 직접 물은 단일 측정", 새 항목은 "같은 질문 표본 중 등장 횟수"라 점수 추이 비교가 이 지점에서 끊긴다. 소도시 경쟁사는 대부분 0회(하라식당 100표본·경쟁사 나나로쿠 0/100)로 나올 수 있다.
- **미구현(§1 표의 나머지)**: 내 가게 질의 상세(`scan.py` 2회×3), 조건 검색(소개글 포함 — 화면에 "실제 노출 횟수와는 다릅니다" 표시), 액션 재스캔(`jobs.py`), 경쟁사 소개문 보강 잡(새 항목은 건너뜀). 질의 상세는 호출 수가 오히려 늘지 않게 질의 변형을 본 스캔의 질의 목록에 합치는 방식을 먼저 설계해야 한다.

## 7. 전환 구간 처리 결정 (2026-10-30, 사용자)
- **측정 방식 변경 시점 표시(추이 그래프·타임라인 마커, 순위 안내문)는 만들지 않는다.** 근거(사용자): 현재 외부 사용자가 없는 개발 단계라 과거 점수와 이어서 볼 사람이 없다. 실사용자가 생기기 전에 점수 기록을 새 방식 기준으로 새로 시작하는 것을 전제로 한다.
- **유지하는 것**: 변화·급등 알림의 방식 전환 가드(`basis_changed`) — 비용이 거의 없고 오발송을 막는다.
- **재검토 조건**: 실사용자가 생긴 뒤 측정 방식이나 점수 산식을 다시 바꿀 때는 그 시점에 변경 표시를 같이 설계한다.
- **"언급됨" 기준(표본 1회 이상)은 유지** — 내 가게 판정과 같은 기준이라 비대칭이 없다. 새 방식 데이터가 2~3주 쌓인 뒤 경쟁사 점수의 표본 흔들림 폭을 실측해 재검토.
- `competitor_snapshots`는 읽는 곳이 없어(쓰기 전용) 집계 영향 없음 — 읽는 기능을 만들 때 방식 구분을 함께 넣는다.

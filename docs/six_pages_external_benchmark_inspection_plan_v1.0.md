## §2. 통합 점검 절차 — 개선 가이드 세션에서 배운 교훈 반영

### §2-A. 기본 7단계 (기존 방법론, 변경 없음)

1. 과거 이력 확인 (§1 참조 — 이미 정리됨, 재확인만)
2. 코드 레벨 재검증 (`Read`/`Grep`으로 직접 확인)
3. 라이브 브라우저 직접 접속 — **로그인 필요**. 이 Windows 환경은 `browse` 스킬의 `cookie-import-browser`가 DPAPI 복호화 실패로 작동 안 함(2026-07-09 확인, `project_guide_page_ux_benchmark_2026_07_09` 참조). **세션 시작 시 사용자에게 테스트 계정 로그인 정보를 요청하거나 `handoff`로 직접 로그인받을 것.** 코드 정적분석만으로 끝내지 말 것 — 실제로 이번 세션에서 로그인 후 실계정으로 확인해 여러 수정사항의 정상 동작을 검증했다.
4. 외부 기준 조사 (§3 페이지별 후보 참조, 필요시 추가 WebSearch)
5. 반증 시도 후 확정 (CLAUDE.md "문제 분류 검증 의무")
6. 확정된 것만 수정 (md5 선확인 → 최소 변경 → scp → 서버 grep → 빌드 → PM2 재시작 → 에러로그 확인 → **라이브 재접속 재확인**)
7. push 전 서버 드리프트 확인

### §2-B. 신규 통합 — 개선 가이드 2라운드에서 발견한 4개 축 (처음부터 §2-A의 4번 단계에 포함할 것)

> 개선 가이드 점검 때는 이 4개 축을 나중에(2라운드로) 추가했다. 이번엔 **처음부터 1회 점검에 포함**해 비효율을 줄인다.

1. **성능(TTFB)**: 대상 페이지 + 비교군 페이지(예: `/dashboard`) 둘 다 측정해 대조할 것. 이 서버는 vCPU2/RAM4GB로 TTFB가 원래 높다(2800ms대 실측 확인됨) — **페이지 특정 문제로 착각해 재보고하지 말 것**. 대조군보다 유의미하게(예: 2배 이상) 느릴 때만 실제 문제로 취급.
2. **WCAG 2.1 AA 접근성** — 2가지를 반드시 실측할 것:
   - **대비율**: `getComputedStyle`이 최신 Chromium에서 `lab()` 색공간으로 반환될 수 있어 단순 `rgb()` 파싱이 깨진다(개선 가이드 세션에서 실제로 겪음) — **반드시 canvas 2D `fillStyle`+`getImageData`로 sRGB 변환 후 계산**. 기준: 일반 텍스트 4.5:1, 큰 텍스트(18.66px+ 또는 14px+bold) 3:1. `text-gray-400`(rgb 153,161,175)은 2.60:1로 실패, `text-gray-500`(107,114,128)은 4.83:1로 통과 — 이 프로젝트의 대표적 실패/통과 색상값으로 재사용 가능.
   - **`aria-expanded` 누락**: 접기/펼치기 버튼을 셀 때 **아이콘 스왑 패턴(`condition ? <ChevronUp/> : <ChevronDown/>`)과 회전 패턴(`<ChevronDown className={... rotate-180 ...}>`) 둘 다 잡히는 방법으로 셀 것**. 정규식 하나로 페어 매칭하면 회전 패턴을 놓쳐 과소 카운트한다(실제로 "5곳"→"9곳" 정정된 사례 있음). `grep -B8 "ChevronUp className\|ChevronDown className"`처럼 앞뒤 컨텍스트를 넓게 보고 각 후보의 실제 `<button>` 여부를 개별 확인할 것.
3. **시각 위계(NN/G Aesthetic & Minimalist Design / Visual Hierarchy)**: 스크린샷에서 H1 위치·주요 CTA 대비·배지 색상 일관성 확인. **문제를 못 찾으면 "문제 없음"이라고 정직하게 보고할 것** — 개선 가이드 세션에서 이 축은 실제로 문제가 없어서 그대로 보고했다. 억지로 지적사항을 만들지 말 것.
4. **카피 톤 일관성**: 페이지 전체 한국어 톤(존댓말 수준, 소상공인 친화적 어휘 등)이 문서/카드마다 다르지 않은지. 큰 문제 없으면 마찬가지로 정직히 보고.

### §2-C. 이미지/아이콘 등 "0건이라 문제 없음"도 정직히 보고

개선 가이드 페이지엔 `<img>` 태그가 0개였다(alt 텍스트 문제 자체가 성립 안 함). 페이지에 따라 이미지가 없을 수 있다 — 없으면 "해당 없음"이라고 명시할 것, 억지로 대체 문제를 찾지 말 것.

## §3. 페이지별 외부 벤치마크 조사 후보 (2026-07-09 사전 조사 완료분)

> 전부 이번 문서 작성 중 WebSearch로 확인한 실제 출처. 새 세션에서 그대로 인용하거나, 필요시 추가 검색할 것 — 단 "한 번 조사한 자료를 다른 유형 페이지에 억지로 재활용하지 말 것" 원칙 유지.

| 페이지 | 페이지 유형 | 벤치마크 후보 |
|---|---|---|

| 리뷰 답변 | 리뷰 관리 인박스 | Podium/Birdeye 관행 — "통합 인박스, AI 답변 초안+인간 승인 필수 유지, 응답속도가 검색순위에 실제 영향"([birdeye.com](https://birdeye.com/blog/google-reviews/)). 이 페이지가 AI 초안을 자동 게시가 아닌 "편집 후 승인" 흐름으로 설계됐는지 확인 |

## §4. 실행 순서 제안

1. **변화 기록** — 회귀 확인(빠름) + §2-B 4축 신규 적용. 가장 짧게 끝날 항목.
2. **블로그 진단** — 개선 가이드와 동일 카테고리(SEO 감사 도구)라 방법론 재사용 용이.
3. **리뷰 답변 / AI 광고 대비** — 인박스·모니터링류로 유사 원리, 이어서 진행 가능.
4. **소개글·콘텐츠** — AI 생성 콘텐츠 특유의 "편집 가능한 초안" 투명성 이슈 집중.
5. **창업 시장 분석** — 데이터 신뢰도 표시(실측 vs 추정 구분) 집중, 이미 DataLab 연동 완료 상태라 "출처 표시 UX"만 점검하면 됨.

각 페이지 종료 시 `docs/external_benchmark_commercial_quality_v1.0.md` §3에 결과 추가하고 §4에서 제거 — 이 문서가 갱신되는 단일 진행 로그.

# 대행 서비스 계좌입금 + 현금영수증 전환 계획 (Plan B) v1.0

> 작성 2026-09-30 | 상태: **계획만 — 구현 착수 안 함.** 착수 트리거는 §1의 토스 회신.
> 배경: 토스가 대행 서비스(단건 결제)를 "광고 서비스 업종"으로 분류해 **단건 MID 추가 신청 + 내부 추가 검토**를 요구. 추가 심사비 여부·금액은 미확인(토스 공식 이용요금 페이지 원문은 열지 못했고, 검색 결과에는 가입비 22만원+연관리비 11만원=33만원만 보임 — 사용자가 낸 33만원이 이것일 가능성).
> 사용자 지시: 단건 MID 추가에 별도 비용이 들면 대행 서비스는 **요금 안내 → 고객 요청 → 판매자 계좌 입금 → 현금영수증 발급** 방식으로 운영.

## 0. 한 줄 요약

기존 상태 머신(`received → paid → in_progress → completed`)을 그대로 두고, **"paid로 넘기는 방법"만 토스 confirm → 관리자 입금 확인으로 교체**한다. 환불은 토스 취소 API 대신 수동 계좌환불 + 현금영수증 취소로 바꾼다. 신규 상태값은 필요 없다.

## 2. Plan B 운영 흐름 (사용자 관점 + 운영자 관점)

```
[고객] /delivery/new 에서 패키지·사업장·의뢰내용 작성 + 위임 동의 + 약관/환불 동의
   └─ 증빙 선택: 현금영수증(소득공제용 / 지출증빙용) · 세금계산서 · 발급 안 함
   └─ 신청 → 주문 생성(status=received = "입금 대기"), 화면에 입금 안내(계좌·금액·입금자명·기한)
[운영자] 신규 신청 알림(이메일+Slack — 기존 send_operator_alert 재사용)
[고객] 입금 (입금자명 = 주문번호 코드 또는 사업장명)
[운영자] 은행 앱에서 입금 확인 → 관리자 화면 "입금 확인" 버튼
   └─ paid 전환 + paid_at 기록 + 카카오 DELIVERY_01 + 운영자 알림 (기존 confirm 후처리 재사용)
[운영자] 홈택스에서 현금영수증(또는 세금계산서) 발급 → 관리자 화면에 발급 체크 + 승인번호 기록
[이후] in_progress → completed 는 기존 흐름 그대로
[환불] 7일 자료 미제출/환불 요청 승인 → 운영자가 계좌로 수동 환불 → "환불 완료" 처리 + 현금영수증 취소 발급
```

**기존 기능 재사용 가능한 것 (코드 확인)**
- 상태 머신·완료 보고서·메시지·재작업·후기: 변경 없음.
- 미입금 자동취소: `delivery_auto_cancel_job`(`jobs.py:5521`, received 7일 경과 취소) — 그대로 "입금 기한 초과 취소"로 동작. 기한을 7일에서 줄일지는 §7 결정사항.
- 후처리 묶음(paid_at 기록·카카오·운영자 알림·이메일): `confirm_delivery_payment`(`delivery.py:732`) 안에 있음 → **함수로 추출해 토스 confirm과 입금 확인이 공유**하게 한다.

### 3-1. 2026-10-01 사용자 확인 반영 후 남은 미해결 항목

- **S6 (가격이 VAT 포함인지)** — 일반과세자이므로 **가장 먼저 정해야 함**. 표시가 69,000/89,000/139,000원이 VAT 포함이면 공급가액 62,727/80,909/126,364원 + 세액 6,273/8,091/12,636원(원 단위 반올림 기준, 세무사 확인). 별도라면 고객 부담이 10% 늘어 표시가와 실제 청구액이 달라지므로 화면·약관 수정 필요.
- **S4 (의무발행업종 해당 여부)**: 미확인. 해당하면 10만원 이상 건(139,000원)은 소비자 요구 없이도 발급해야 함.
- **S7 (결제대금예치 안내 의무)**: 미확인. 원문 확인 필요.
- **환불 시 증빙 정정**: 세금계산서를 발행한 건을 환불하면 수정세금계산서가 필요하다는 일반 지식이 있으나 **원문 미확인** — 세무사 확인. 현금영수증도 취소 발급이 필요(계획서 §2).
- **세금계산서 발행 기한**: 일반적으로 익월 10일 등 기한이 있으나 미확인 — 세무사 확인 후 `delivery_receipt_reminder_job`의 알림 기준에 반영.

## 4. 코드 변경 범위

### 4.1 DB (SQL 수동 실행 — Supabase SQL Editor)

`delivery_orders`에 컬럼 추가. `payment_key`는 스키마 파일 기준 nullable(`supabase_schema.sql:1799`, `payment_key TEXT`)이라 계좌 주문은 NULL로 둔다. 라이브 DB 제약은 직접 조회하지 않았으므로 구현 전 확인. `paid_at`은 v6.2b 마이그레이션(`:2287`) 실행이 전제.

```sql
ALTER TABLE delivery_orders
  ADD COLUMN IF NOT EXISTS payment_method text NOT NULL DEFAULT 'toss'
    CHECK (payment_method IN ('toss','bank')),
  ADD COLUMN IF NOT EXISTS depositor_name text,
  ADD COLUMN IF NOT EXISTS deposit_confirmed_at timestamptz,
  ADD COLUMN IF NOT EXISTS proof_type text
    CHECK (proof_type IN ('cash_receipt_income','cash_receipt_business','tax_invoice','none')),
  ADD COLUMN IF NOT EXISTS proof_identifier text,      -- 휴대폰/사업자번호. 민감정보: 최소 수집, 마스킹 표시
  ADD COLUMN IF NOT EXISTS receipt_issued_at timestamptz,
  ADD COLUMN IF NOT EXISTS receipt_approval_no text,
  ADD COLUMN IF NOT EXISTS receipt_cancelled_at timestamptz;
```

- 환불 계좌는 신청 시가 아니라 **환불 요청 시점에만** 받는다(수집 최소화). 저장 방식(암호화/환불 후 삭제)은 구현 시 결정.
- 기존 주문은 `DEFAULT 'toss'`라 영향 없음. 라이브 실주문은 0건(2026-07-17 운영 매뉴얼 기록).
- `scripts/supabase_schema.sql`에도 ALTER 섹션 추가(프로젝트 규칙).

| `(public)/terms/page.tsx` 제5조의2 | 결제수단(계좌입금), 입금 기한, 증빙 발급, 환불 방식(계좌 이체·현금영수증 취소) |

**병행 방식 권장**: `DELIVERY_PAYMENT_MODE=toss|bank` 플래그. 토스 답이 늦게 오거나 나중에 단건 MID를 열 때 코드를 다시 짜지 않아도 된다. 플래그 기본값은 현재 동작(`toss`)으로 두어 배포만으로 화면이 바뀌지 않게 한다.

## 5. 토스 심사와의 충돌 방지 (타이밍)

- 토스가 확인한 결제경로 파일에 **단건 결제 화면이 이미 포함**돼 있다. Plan B로 결정하면 홈페이지에서 단건 결제 경로가 사라지므로 **토스 회신 후에** 화면을 바꾼다. 심사 중에 화면이 먼저 바뀌면 제출 자료와 실제 사이트가 어긋난다.
- 토스에는 "대행 서비스는 계좌입금으로 운영하며 단건 결제는 신청하지 않는다"를 명시 회신하고, 빌링(구독) 심사만 진행하도록 한다.
- 심사용 테스트 계정(`toss-review@aeolab.co.kr`)은 심사 통과 전 삭제 금지(메모리 기록 참조).

## 6. 검증 계획 (구현 시)

1. 로컬 pytest: 상태 전이(`received→paid` 입금확인, 이미 paid면 409), 환불 분기(bank는 토스 미호출), 자동환불 잡 bank skip, `_finalize_paid` 토스 경로 회귀 없음.
2. 라이브 종단: QA 계정으로 계좌 주문 생성 → 입금 안내 표시 → 관리자 입금 확인 → paid 전환·카카오/이메일 → 증빙 기록 → 환불 수동 처리. **테스트 주문·계정은 끝나면 삭제**(어제 대행 결제창 확인 때와 동일 절차).
3. PC·모바일 스크린샷(입금 안내 카드 가독성, 계좌 복사 버튼).
4. 기존 토스 경로 회귀(플래그 `toss`에서 결제창이 여전히 뜨는지).

| D5 | 증빙 발급 기한 알림 | S4(의무발행업종 여부) 확인 결과에 따라 5일 이내 알림 여부 결정 |

## 8. 하지 않는 것 / 비교한 대안

- **계좌이체 자동 확인(오픈뱅킹·은행 API)**: 비용·심사·유지보수가 크고 주문량이 0건이라 제외.
- **PG 가상계좌(토스 등)**: PG 계약이 다시 필요해 이번 문제(추가 비용)와 같은 종류의 비용이 생길 수 있음. 토스 회신 전에는 판단 불가.
- **빌링 MID로 1회 청구**: 계약상 허용 여부를 토스가 확인해야 함(§1 질문 4). 허용되는지 모르는 상태에서 코드를 만들지 않는다.
- **소비자 개인정보 최소화**: 증빙 식별번호는 필요할 때만 받고 화면에는 마스킹.

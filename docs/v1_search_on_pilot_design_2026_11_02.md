# V-1 파일럿 설계 — ChatGPT '기억 모드' vs '웹 검색 켬' 자동 측정 (2026-11-02)

## 1. 무엇을 알고 싶은가
우리 점수의 ChatGPT 측정은 가게 이름 없이 추천을 나열시키는 **기억 모드(검색 없음)** 다. 소비자가 보는 화면은 대개 **검색을 켠 답**이다. 수기 예비 결과(1~3회)에서는 기억 모드 0이던 4곳 중 3곳이 검색 켬에서 상위로 올랐다. 이것이 (a) 실제 괴리인지 (b) 개인화·표본 변동인지 (c) 우리 API로 재현 가능한지를 알고 싶다.

## 3. 설계
- **가게 5곳**(프로토콜과 동일): 어니언 성수(양성 대조, 기억 25/50), 하라식당(지역 인기, 0/50), 대호흑돼지(0 대조, 동태탕), 힐링하우스마사지(0/100), 홍뮤직스튜디오(0/50).
- **질문**: 프로토콜의 Q1(짧은 질의)·Q4(긴 자연어). **가게 이름은 질문에 넣지 않는다**(테스트로 고정).
- **두 암(같은 모델·같은 질문·같은 추론 설정)**: ①검색 켬 ②검색 끔. 두 암의 차이는 검색 도구 하나뿐이다(테스트로 고정). 검색 끔 암은 "모델 자체의 표본 변동"을 분리하는 대조군이다.
- **반복 3회** → 가게당 검색 켬 6, 검색 끔 6 (5곳 × 2질문 × 3회 × 2암 = **60호출**).
- **예상 비용 약 $1.7**(검색 30 × $0.055 + 검색 끔 약 $0.01), 사전 상한 추정 $2.0, 실행 상한 $3·70회(닿으면 즉시 중단).
- **기록**: 노출 여부·목록 순위·인용 도메인·모델이 쓴 검색어·검색 호출 수·토큰·비용·답변 원문(2,500자까지).
- **안전**: 네이버 접속 없음, DB 쓰기 없음, 운영 점수·알림에 반영하지 않음. 실행기는 `backend/scripts/v1_search_on_pilot.py`(기본은 계획만 출력, `--run`이 있어야 호출), 집계는 `v1_pilot_summarize.py`.

## 4. 판정 규칙 (결과를 보기 **전에** 고정 — 사후 끼워 맞춤 방지)
| 관찰 | 해석 | 조치 후보 (모두 사용자 결정) |
|---|---|---|
| 기억 모드 0인 가게 중 **2곳 이상**이 검색 켬(API)에서 6회 중 1회 이상 등장하고, 수기 화면과 방향이 같다 | **과소 반영이 실재**하고 API 검색 도구가 소비자 화면의 대리 지표로 쓸 만하다 | 화면에서 기억 모드/검색 켬을 **분리 표시**, 검색 켬 샘플 측정을 유료 기능으로 검토(§6 비용) |
| 검색 켬(API)에서 거의 안 나오는데 수기 화면(UI)에서는 나온다 | **API 검색 도구는 소비자 화면을 재현하지 못한다**(개인화·검색 구성 차이) — 자동화로는 V-1에 답할 수 없다 | 자동 측정 접근 포기, 수기 표본 주기 점검 또는 불확실성 문구 유지 |
| 검색 켬과 기억 모드 모두 0 | 현행 측정이 대체로 일치 | 현행 유지(문구 보정은 이미 반영됨) |
| 기억 모드 노출(어니언)인데 검색 켬에서 0 | 기억 모드 **과대 반영** | 문구·표현 보정 설계 |
| 검색 끔 암의 6회 사이 편차가 크다 | 모델 표본 변동이 큼 → 위 비교의 신뢰 낮음 | 반복 수를 늘린 재시험 |
**어떤 경우에도 이 파일럿 한 번으로 점수 모델을 바꾸지 않는다.** 표본(가게 5곳, 질문 2개, 3회)은 방향성만 준다.

## 5. 한계 (결과 해석 전에 알아 둘 것)
- **API의 `web_search` 도구 ≠ ChatGPT 앱의 검색 켬.** 검색 구성·개인화·메모리·로그인·후속 질문 유도가 다를 수 있다. 첫 스모크에서 이미 하라식당이 API 검색 답에 없었다(수기 화면은 3회 중 2회 등장). 그래서 §4 둘째 행이 가능한 결과다.
- 모델이 검색을 안 쓸 수 있고(`tool_choice=auto`), 내부 검색 횟수·검색어는 모델이 정한다 → 호출마다 달라진다.
- 가게 5곳 중 일부는 관리자·본인 소유라 일반 사장님을 대표하지 않는다. 지역 시장이 얇은 업종(편곡 4곳)이 있다.
- 비용: 모델이 내부 검색 횟수를 정하므로 호출당 비용이 변한다(스모크 1건 기준 $0.055).

## 6. 제품화했을 때의 비용 (결과와 무관하게 알아 둘 것) [확인된 단가 기반 계산]
- 검색 켬 1질문 ≈ $0.055(약 75원). 사업장 1곳이 한 번 스캔에서 2질문 × 3회를 하면 6질문 ≈ $0.33(약 450원).
- Basic(17,900원, 주 2회 스캔 = 월 약 8회)에 그대로 넣으면 월 약 $2.6(약 3,600원) = 매출의 약 20% → **매 스캔 전수 측정은 비현실적**. 가능한 형태: 월 1회·질문 1개·반복 없이(≈ $0.055/월) 같은 **저빈도 샘플 점검**, 또는 상위 요금제 전용.

## 7. 결과

**§4 판정 (사전 고정 규칙 적용)**
- 첫째 행("기억 모드 0 가게 중 2곳 이상이 검색 켬에서 등장 + 수기와 방향 일치") **미충족** — 4곳 중 1곳(홍뮤직)만 등장.
- **둘째 행 해당**: 수기 화면에서는 상위로 나온 하라식당(2/3)·힐링하우스(2/2)가 API 검색 켬에서는 각 0/6. → **API `web_search` 도구는 소비자가 보는 검색 켬 화면을 재현하지 못한다. 이 방법으로는 V-1("기억 모드가 소비자 화면과 얼마나 다른가")에 자동으로 답할 수 없다.**
- 셋째/넷째 행: 과대 반영 없음(어니언은 검색 켬에서도 3/6 등장). 검색 끔 암은 가게별로 안정적(0/6 ×4)이라 표본 변동이 결과를 좌우한 것은 아니다.
- 홍뮤직 1곳의 과소 반영(검색 켬 2/6, 인용 도메인 soomgo·spacecloud 등)은 "검색을 켜면 일부 가게는 오른다"는 방향성은 보이나 1곳이라 일반화 불가.

**해석상 주의 [미확인]**
- 수기 화면과 API가 다른 이유(개인화·로그인 메모리·검색 구성·질문 문구)는 이 실험으로 가를 수 없다. 수기 결과도 1~3회 예비값이다.
- 어니언의 검색 끔 6/6은 스캔의 기억 모드 25/50과 다르다 — 스캔과 파일럿의 질문 문구·표본 수 차이 때문일 수 있으나 확인하지 못했다. 파일럿의 '검색 끔'은 스캔 점수의 대체 측정이 아니다.
- 가게 5곳·질문 2개·3회로 방향성만 준다. 점수 모델은 바꾸지 않는다.

**다음 조치 (사용자 결정 사항)**
1. 자동 측정 접근은 **보류/포기** 권고 — 같은 모델 API 검색이 화면을 못 따라가므로 비용($0.055/질문)을 들여 제품화할 근거가 약하다(§6).
2. 현행 유지: 화면·알림 문구는 이미 "이번 측정에서는 확인되지 않았고 검색을 켠 화면에서는 다를 수 있다"로 보정됨 — 이 파일럿 결과는 그 문구가 **필요하다는 쪽**(수기에서 오르는 가게가 API에선 안 오름 = 불확실성이 큼)을 지지한다.
3. 더 알고 싶다면 수기 표본을 늘리는 방법(가게당 5~10회, 사용자 계정 상태 기록)뿐이며 비용은 시간. 보류 중인 리허설·자문과 별개로 언제든 가능.

## 2. 과제 01 — 처음 쓰는 사용자가 인기/비인기 가게 스캔 결과를 믿을 수 있게 하는 정보

### 2-1. 목표
스캔 결과를 처음 본 사장님이 "이 숫자·문구가 어디서 나왔는지"를 스스로 확인할 수 있어야 한다. **인기 가게**는 "우리가 저평가될 리 없다"는 불신을, **비인기 가게**는 "측정이 안 된 건지 정말 없는 건지" 또는 "낮은 결과에 좌절해 떠나는" 문제를 막는다.

### 2-2. 이미 한 것 (인기 가게 쪽, 10-25~27, 상세는 `popular_shop_trust_improvement_handoff_v1.0.md` §2)
- 플레이스 ID 자동 확정(이름·주소 대조, 모호하면 저장 안 함) → 유명 가게가 ID 없이 0점이 되던 문제 해소.
- 측정 못 한 항목은 0점이 아니라 **제외 후 재정규화**(`score_engine._renormalized_track1`, 순위 None은 `_smart_place_base_rank_aware`).
- 화면의 측정 실패 판정 통일(`frontend/lib/naverMeasure.ts` ↔ 백엔드 `_is_naver_unmeasured`), 순위 실측 우선(`lib/keywordExposure.ts` ↔ `strength_signals.py`, 한쪽 변경 시 양쪽).
- 상단 카드: 라벨 "AI 검색 준비도 · 양호/개선 중/보강 단계/시작 전", 직전 성공 결과 날짜 표시, "측정으로 확인된 점" 강점 카드.
- 이번 세션 추가: **순위 측정이 차단 화면을 "미노출 0점"으로 저장하던 결함**을 수정(차단 감지 → 측정 불가, 점수 평균에서 제외). 근거: 이전 `_place_card_rank`에 감지가 없었고 점수는 error 없는 전부-None 행을 0점으로 평균했다.

### 2-3. 아직 안 한 것 / 새로 넣어야 할 관점
1. **비인기 가게 관점은 이번 문서에서 처음 정리하는 것이며 사례 검증이 없다.** 기존 신뢰도 문서는 인기 가게(저평가 불신) 중심이다. 비인기 가게에 대해서는 실제 사용자·사례 데이터가 없으므로 추측으로 설계하지 말고, 먼저 `trial_scans`·`scan_results`의 실제 비인기 가게 결과를 직접 읽어 "화면에서 무엇이 좌절·불신을 만드는지" 목록부터 만든다(구독자가 0명이면 시험 계정·체험 기록으로).
2. **근거 노출 정보(후보, 구현 전 사용자 결정 필요)** — 모두 실측 가능한 것만, 더미 금지:

## 4. 과제 02-1 — 유료 서비스의 IP 우회를 적용할 수 있는가

### 4-1. 결론 (먼저)
- **기술적으로는 가능하다.** 코드가 이미 프록시를 지원하고, 과거에 실제 가동한 실측이 있다.
- **그러나 "차단을 막아 주는 수단"이라는 근거는 없고, 법적으로 가장 민감한 결합 지점이다.** 변호사 자문 전에는 켜지 않는 것을 권한다. 결정은 사용자.

### 4-2. 기술적으로 확인된 사실
- 코드: 플레이스 점검·통계·경쟁사 크롤·ID 확정·브리핑·AI탭 스캐너가 `get_proxy_config()`를 사용(`services/ai_scanner/__init__.py`). 풀에서 5회 호출마다 다음 항목으로 교체(`NAVER_PROXY_ROTATION_BATCH`). 연속 인증/연결 실패 시 30분간 직접 접속으로 폴백하는 회로 있음.
- 실운영 이력(메모리 `project_dataimpulse_to_decodo_proxy_migration_2026_08_05`): 한국 주거용(Residential) 프록시를 DataImpulse → Decodo로 전환해 2026-08-05 가동, `captcha_detected=false`로 정상 측정 확인. 형식 `gate.decodo.com:7000:user-<username>-country-kr:<password>`. **회전형 게이트웨이 1개라 "다중 IP 풀"이 아니었다**(배치 로테이션은 실효 없었음).
- **새 프록시 업체로 바꿀 때마다 iwinv 콘솔의 외부 아웃바운드 방화벽에 해당 포트(예: 7000)를 등록해야 한다**(두 번 재발한 원인). 서버 내부 ufw가 아니라 클라우드 콘솔 보안그룹.
- Chromium은 인증 있는 SOCKS5를 지원하지 않아 **HTTP 프록시만** 가능.
- 이후 상태: 10-25 Webshare 5개 프록시가 407("계정 목록에 없음")로 8일 이상 실패(무료 플랜 전환, 한국 프록시 없음) → `NAVER_PROXY_LIST`를 비우고 직접 접속. 원본은 서버 `.env.bak_proxy_*`.
- 비용(2026-08 시점): Decodo Residential 3GB 약 $11.25/월(실제 $3.75/GB 구독 구간). **가격은 업체 헤드라인과 실결제가가 두 번 달랐으므로 반드시 결제 페이지에서 재확인**.
- 사용량 추정: 2026-08 코드 추적으로 50명 기준 월 1.5~2.5GB. 이후 구조(경쟁사 크롤·점검·순위)가 늘었으므로 **재계산 필요**. 사용자 500명이면 단순 비례로 15~25GB 같은 규모지만 이는 비례 가정(미검증)이다.

### 4-3. 이 방안의 한계 (오판 방지)
1. **IP를 바꿔도 요청 패턴이 같으면 새 IP도 같은 이유로 제한될 수 있다.** 차단 기준이 IP가 아니라 속도·패턴일 가능성을 배제하지 못했다. 프록시는 "속도 기준·총량 감소 없이 쓰면" 위험을 늘릴 뿐이다.
2. **법적**: 쟁점은 "IP 변경" 자체가 아니라 **로그인 쿠키 주입(신원) + 자동화 은닉 + IP 로테이션이 결합**된 구조다(`naver_scraping_legal_risk_assessment_v1.0.md`). robots.txt `Disallow: /` 전체 차단이 확인되어 "유리한 가정 하나가 무너진" 상태. 회색지대이며 변호사 자문 필요 항목으로 분류되어 있다.
3. 프록시를 거치는 쿠키 로그인 세션이 계정 이상 탐지를 부를 가능성은 가설일 뿐 미검증(과거 프록시+쿠키 조합에서 CAPTCHA 없이 측정된 실측은 있음).
4. 프록시 비용은 사용자 수에 비례(GB 과금) — 단가 구조 재계산 필요(마진율은 `docs/plan_limits_v1.0.md`, 현재 API·PG 비용만 반영).

### 4-4. 이 과제에서 할 일
- 법적 판단은 하지 말고 **선택지와 근거를 정리해 사용자에게 제시**. 켜기로 결정되면: 업체 실결제가 재확인 → 한국 주거용 프록시 → iwinv 아웃바운드 포트 등록 → `backend/.env`의 `NAVER_PROXY_LIST` 설정(값은 출력·`source` 금지, `dotenv_values`로 읽기) → `pm2 restart aeolab-backend --update-env` → 로컬 대조 테스트부터.
- 대안(프록시 없이): 과제 02의 ①②③ + ⑧(사용자 본인 환경 수집)이 더 근본적이다.

## 5. 과제 03 — 사용자 300~500명 이상 대응

### 5-1. 현재 용량 (코드 기준 모델, 실측 아님 — `python scripts/naver_load_model.py`)
가정: 사용자 = 사업장 1곳, 키워드 3개, 경쟁사 3곳, 플랜 구성 basic 70%/startup 10%/pro 15%/biz 5%, 사용자 수동 스캔 0.2회/사업장/일(근거 없음).

| 규모 | 현재 구조 하루 최대 페이지 | 전부 적용(슬롯 분산·사전스캔·경쟁사 캐시·경쟁사 요일 분산·중복 30%) 최대 / 평균 |
|---|---|---|
| 20곳 | 약 730 | 약 280 |
| 300곳 | 약 10,900 | 약 3,800 / 평균 2,100 |
| 500곳 | 약 18,200 | 약 6,300 / 평균 3,500 |

- 상한을 처음 넘는 사업장 수: 현재 구조 약 20곳 → 전부 적용 시 약 50곳. **300~500곳은 지금 구조로 불가**.
- 500곳 전부 적용 평균 구성(주당 환산 일평균): 경쟁사 크롤 1,500(43%) / 키워드 순위 1,200(34%) / 스캔 657(19%) / 통계 143(4%). **순위 카드 공유 캐시의 효과는 이 모델에 반영되지 않았다**(같은 검색어 사업장이 생겨야 나타남).
- 속도 기준과의 관계: 평균 3,500/일은 시간당 약 146페이지로, 현재 속도 기준 1시간 120페이지(연속 가동 시 하루 최대 2,880)를 **넘는다**. 즉 한도를 올리지 않는 한 속도 기준이 처리량의 물리적 상한이 된다. 한도를 올리는 것은 차단 위험을 올린다 — 이것이 구조 변경이 필요한 이유.
- 상한 600/일 대비 필요 감소량: 평균 3,500 → 600이면 약 6배, 최대일 6,300 → 420(배치 몫)이면 약 15배.

### 5-2. 해법 후보 (효과는 추정, 구현 전 반드시 별도 검증)
| 방안 | 기대 | 제약 |

| 사용자 본인 환경 수집(크롬 익스텐션, Phase 2) | 플레이스·순위(전체의 약 77%)를 서버 IP에서 사용자 IP로 이동, 법적 쟁점도 완화 | 신규 개발 규모 큼, 사용자 설치 필요, 약관 검토 |

## 6. 오판 방지 규칙 (이 주제에서 실제로 틀렸던 것들)
1. "정기 스캔은 지연이 없다" → 틀림(브리핑 2.8~4.8초·AI탭 무작위·사업장당 20~240초 시작 대기가 있음).
2. "플레이스 접속이 상한에서 빠져 있다" → 틀림(별칭 `_check_naver_quota`를 grep이 놓침). 호출 그래프는 별칭까지 grep.
3. "IP 변경이 법적으로 가장 민감" → 과장. 쟁점은 로그인 위조 + 자동화 은닉 + IP 로테이션의 **결합**.
4. "순위 측정은 전부 공식 API로 전환" → 부분만(place_rank만 API, PC/모바일은 Playwright).
5. "점검이 스캔마다 반복된다" → 과장(정기 스캔 `daily_scan_all`은 `check_smart_place_completeness`를 호출하지 않음).
6. 용량 수치(40~50곳 한계 등)는 **모델 값**이다. 실측처럼 말하지 말 것. 속도 기준값을 "검증된 안전선"이라고 말하지 말 것.
7. 서버에서 네이버를 검증하다 IP가 차단됐다 — 구조 확인은 로컬 Playwright, 서버 호출은 최소.
8. `.env` 변수의 존재 ≠ 런타임 적용. `backend/.env`(백엔드가 읽음) vs 루트 `.env`(읽지 않음)를 혼동하지 말 것.
9. 구독자·방문자 수는 실측 전까지 0명으로 가정(과거 메모리 문구 재인용 금지).
10. P0/P1 보고 전 "근거 file:line + 반증 시도 file:line"을 직접 본다. 에이전트 보고는 방향만.
